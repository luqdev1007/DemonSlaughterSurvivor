# ARCHITECTURE.md

Правила архитектуры. Обновляется при появлении нового слоя, системы или паттерна. Держать коротким — иначе перестанет обновляться.

---

## 1. Принципы

1. **Симуляция не знает о Unity.** ECS оперирует данными. Вьюхи — тупые отображатели.
2. **Один владелец у каждого объекта.** Непонятно, кто создал и кто уничтожит — архитектура сломана.
3. **Данные отдельно от поведения.** Компоненты — только поля, системы — только логика.
4. **Конфиги — не код.** Всё балансируемое живёт в ScriptableObject.
5. **Детерминированный порядок.** Порядок систем задан явно и читается сверху вниз.
6. **Ничто про игрока не хардкодится.** Игрок — сущность, собираемая из `CharacterConfig`.
7. **Расширяемость важнее лаконичности.** Планируются пострелизные обновления: новый персонаж, способность, перк или предмет должны добавляться данными и набором компонентов, без правки боевых систем. Если новый контент требует правки системы — модель спроектирована плохо.

## 2. Слои

```
┌──────────────────────────────────────────┐
│ Bootstrap        точка входа, скоупы DI  │
├──────────────────────────────────────────┤
│ UI / Meta        экраны, сейвы, прокачка │  ← VContainer, R3, UniTask, DOTween
├──────────────────────────────────────────┤
│ Services         загрузка, аудио, ввод   │  ← VContainer, Input System
├══════════════════════════════════════════┤  ← ГРАНИЦА
│ Simulation       ECS: компоненты/системы │  ← LeoECS Lite, без Unity API
├──────────────────────────────────────────┤
│ View             вьюхи, пулы, VFX        │  ← MonoBehaviour, DOTween
└──────────────────────────────────────────┘
```

Зависимости только вниз. `Simulation` не ссылается на `UI`, `View` не ссылается на `Services`.

## 3. Граница ECS

**В ECS:** игрок, враги, снаряды, установленные объекты, пикапы; здоровье, урон, скорость, кулдауны, опыт; спавн, ИИ, движение, коллизии, урон, способности; состояние забега.

**Вне ECS:** загрузка сцен и ресурсов; сейв/лоад, мета, инвентарь; UI и его стейт; аудио, настройки, локализация; считывание сырого ввода.

**Игрок — сущность ECS**, без исключений.

**Вьюхи — не сущности.** У сущности компонент `View` со ссылкой на `IView` — интерфейс из `Game.Core`, за которым стоит `MonoBehaviour` вьюхи. Симуляция отдаёт вьюхе **целевую** позицию раз в тик (группа 12), а что рисовать в конкретном кадре, решает сама вьюха. Прямой записи в `Transform` из системы больше нет: тик идёт 60 раз в секунду, кадров при 148 fps втрое больше, и 68.5% из них не выполняют ни одного тика — без интерполяции внутри вьюхи картинка идёт ступенями по 16.7 мс, и как только за игроком поедет камера, ступенями пойдёт весь кадр, а не один силуэт.

**Поворот вьюхи не интерполируется.** Он берётся из `Facing`, а `Facing` уже ограничен угловой скоростью в симуляции (§6) — то есть меняется малыми шагами, а не скачками. Ступень поворота видна несравнимо слабее ступени позиции: за позицией едет камера и вместе с ней весь кадр, за поворотом — только силуэт персонажа. **Условие пересмотра:** появление мгновенных разворотов (телепорт, отбрасывание, смена цели рывка).

**Камера — вне ECS.** Ни компонента, ни системы: камера ничего не решает в симуляции. Владеет ею `ICameraService` — интерфейс в `Game.Core`, реализация в `Game.View`, регистрация `Lifetime.Scoped` в скоупе забега. Риг создаётся из префаба в конструкторе сервиса и уничтожается в `Dispose`, то есть у объекта один владелец и время жизни ровно в забег. Ни `Camera.main`, ни `GameObject.Find`, ни `RegisterComponentInHierarchy` — сценовых камер в аренах нет вовсе. Единственная связь с ECS — передача цели: `Transform` вьюхи игрока, которая появляется только внутри симуляции, уже после сборки скоупа.

## 4. Реестр контента и стабильные ID

Пострелизные обновления делают это обязательным, а не желательным.

- У каждой единицы контента — **строковый ID, зафиксированный навсегда**: персонажи, способности, оружие, перки, предметы, апгрейды, уровни.
- ID не равен имени ассета и не зависит от порядка в списках.
- `ContentRegistry`: ID → конфиг. Сейвы, дроп-таблицы и мета ссылаются на ID, а не на объекты.
- Переименование ассета или перестановка в списке **не имеет права ломать сейв**.

Реестр заодно — готовая точка расширения под Addressables, если DLC будет грузиться отдельно.

## 5. Пайплайн статов — единая точка сборки

Источников модификаторов пять: общая ветка меты, персональные перки, предметы, апгрейды забега, временные эффекты. Если каждый правит компоненты напрямую, числа становятся неотлаживаемыми, а UI — невозможным.

```
BaseStat (CharacterConfig)
  → мета: общая ветка
  → мета: персональные перки
  → предметы (4 слота)
  → апгрейды забега
  → временные эффекты (баффы, ярость, ауры)
= FinalStat
```

Правила:
- **Порядок применения фиксирован:** сначала все аддитивные модификаторы, затем все мультипликативные. Иначе порядок взятия апгрейдов влияет на результат — классический источник необъяснимых чисел.
- **Пересчёт по событию**, не каждый кадр. Изменился источник — пересобрали финальные статы.
- **Модификатор знает свой источник** — для UI («откуда у меня +40% урона») и для корректного снятия.
- Новый источник подключается в пайплайн, не трогая боевые системы.

## 6. Ввод

**Поток:** `InputService` (Input System, вне ECS) → нормализованный `InputState` (компонент на игроке) → системы.

Сырой ввод в ECS не читается никогда.

- **Направление задаётся только движением (WASD).** Мышь направление не задаёт.
- **`Facing` — отдельный компонент от `Velocity`.** Игрок отпустил клавиши — скорость нулевая, взгляд сохраняется. Иначе персонаж сбрасывается в дефолтное направление.
- **Поворот идёт с ограниченной угловой скоростью.** `FaceVelocitySystem` доворачивает `Facing` к направлению `Velocity` через `Vector3.RotateTowards` не быстрее `TurnSpeed` градусов в секунду (`CharacterConfig`, стат персонажа). Мгновенный разворот читается как рывок картинки, а на клавиатуре ещё и врёт: клавиши диагонали отпускаются не одновременно, и последние два-три тика движения — кардинальные, отчего взгляд на отпускании «щёлкал» с диагонали на сторону. Ограничение скорости съедает этот хвост.
- **`Facing` — единичный вектор.** Он таким рождается (`Vector3.forward` при спавне), а `RotateTowards` с нулевым изменением длины его таким и оставляет — длина `Velocity` в `Facing` больше не протекает. `StartDashSystem` всё равно нормализует при чтении: страховка стоит один sqrt на рывок.
- **Угол камеры — общие данные уровня, а не два независимых числа.** `LevelConfig.CameraYaw` читают двое: `ReadMoveInputSystem`, чтобы спроецировать ввод, и `ICameraService`, чтобы поставить камеру. Пока камеру ставили руками в сцене, совпадение держалось на договорённости; разъехавшись, эти два угла дают симптом «управление ведёт вбок», а искать его будут в движении. Поэтому источник ровно один, и камеры в сценах арен нет — она создаётся из данных. Рядом с углом лежат `CameraPitch` и `CameraDistance`: отдельного `CameraConfig` нет, потому что все три числа описывают одно — посадку камеры над ареной, а арена и есть уровень. Всё остальное (damping, lens, blend) настраивается на префабе рига, а не дублируется в конфиге.
- **Буферизация обязательна.** Нажатие незадолго до конца кулдауна срабатывает при его окончании. Без буфера управление ощущается глухим при технически корректном коде. Окно — **120 мс**, лежит в `InputConfig`, а не в `CharacterConfig`: отзывчивость управления — свойство игры, а не персонажа.
- **Нажатие латчится в сервисе ввода.** Симуляция идёт фиксированным шагом, и при fps выше 60 бывают кадры без единого тика — замерено 68.5% кадров при 148 fps. Признак «нажато в этом кадре», прочитанный из системы, в такой кадр теряется целиком. `IInputService` поднимает флаг по событию `InputAction` и гасит его при потреблении симуляцией (`ConsumeDashPressed`). Буфер-компонент в мире и латч в сервисе решают разные задачи и нужны оба. Сервис ввода живёт в проектном скоупе и переживает забег, поэтому латч сбрасывается на старте забега (`ResetLatches`) — иначе нажатие в меню срабатывает первым тиком следующего забега.

## 7. Способности

Три активных слота: **рывок · ульта · артефакт**. Все три — частные случаи одной модели.

`AbilityDefinition` **не содержит логику** — он указывает набор компонентов-эффектов:

| Способность | Композиция |
|---|---|
| Рывок берсерка | `Dash(Forward)` + `Invulnerable` + `PushAway` |
| Телепорт мага | `Blink(Forward)` + `Invulnerable` |
| Кульбит рейнджера | `Dash(Backward)` + `Invulnerable` |

Эффекты переиспользуются между способностями и персонажами. Новая способность = конфиг + комбинация существующих эффектов; новый эффект добавляется, только когда его действительно нет.

**Направление — параметр, а не константа.** `Forward` / `Backward` / `Self` / `TargetPoint`. Захардкоженное «по взгляду» сломается на кульбите рейнджера.

**Длительность способности живёт в тиках, не в секундах.** Симуляция идёт фиксированным шагом, и способность длится целое число тиков. Секунды из конфига переводятся в тики округлением **в момент старта**, а производные величины (скорость рывка) считаются уже из округлённой длительности — иначе пройденная дистанция квантуется шагом и врёт на конфигах, не кратных 1/60. Число в конфиге — заявка, фактическая длительность — ближайшее кратное шагу.

**Неуязвимость — один механизм.** I-frames от рывка и i-frames после получения урона — один компонент, не два параллельных.

**Ресурсы ульты** — общий компонент `UltimateCharge` и разные системы-накопители на персонажа:

| Персонаж | Ресурс | Накопление | Поощряет |
|---|---|---|---|
| Берсерк | Ярость | Нанесённый и полученный урон, decay по времени | Не выходить из боя |
| Рейнджер | Сосредоточенность | Время без получения урона | Чистую игру |
| Маг | Заряд с элиток | Подбор дропа с элитных врагов | Приоритет целей |

**Зависимость:** ресурс мага завязан на спавн элиток — спавнер обязан гарантировать их появление по таймеру, иначе персонаж остаётся без ульты не по своей вине. Это требование к системе спавна.

**Артефакт** — предмет, дающий способность. То есть предмет обязан уметь предоставлять поведение, а не только модификаторы статов.

## 8. Атаки: наведение и жизненный цикл

**Наведение** — параметр оружия/способности: по взгляду · ближайший враг · вокруг себя · установка в точке.

**Жизненный цикл** различается принципиально и не сводится к «нанести урон»:

| Тип | Пример | Живёт | Ключевые компоненты |
|---|---|---|---|
| Мгновенный | взмах меча | один кадр | — |
| Снаряд | стрела | до попадания/дистанции | `Lifetime`, `Pierce` |
| Аура | выжигающее поле | пока активна, следует за владельцем | `AttachedTo`, `TickInterval` |
| Установленный | ловушка, кольцо льда | сам по себе | `Placed`, `TriggerCondition`, `Lifetime` |

Установленные объекты — **самостоятельные сущности**: своя позиция, своя регистрация в spatial hash, своё владение. Обязательно решить, что с ними происходит при смерти владельца и при завершении забега.

Заложить только «мгновенный + снаряд» нельзя — ауры и ловушки заявлены в дизайне и приедут костылями.

## 9. Персонажи, режимы, время жизни забега

**`CharacterConfig`:** ID, базовые статы, стартовое оружие, три способности, одно правило-модификатор, слоты предметов.

**`RunContext`** — параметры забега: режим, персонаж, источник уровня, условие победы, правила меты. Создаётся до запуска симуляции; системы читают его, а не глобальное состояние. Ссылки на контент внутри — **только стабильные строковые ID** (§4), не прямые ссылки на конфиги: иначе `RunContext` нельзя объявить в нейтральном `Game.Core`.

Стори-мод и бесконечный режим — два `RunContext`, а не две ветки кода.

**Два уровня корня композиции.** Проектный корень живёт всё приложение: сервисы, `ContentRegistry`, мета и сейвы (§16), настройки — регистрации `Lifetime.Singleton`. Корень забега живёт ровно один забег: `RunContext`, `EcsWorld` и `EcsSystems`, сервисы симуляции (§12), вьюхи, пулы, HUD — регистрации `Lifetime.Scoped`. Рестарт забега — это разбор корня забега и создание нового; проектный корень при этом не трогается и о рестарте не знает, поэтому валюта и мета переживают смерть игрока сами собой, без кода сохранения состояния.

**Ссылка допустима только вниз**, от забега к проекту. Проектный объект не имеет права держать ссылку на объект уровня забега — итог забега уходит в мету копией данных, а не ссылкой на живой объект. Нарушение этого правила даёт ссылку на разобранный мир и проявляется на втором забеге, а не на первом.

## 10. Порядок систем

Новая система добавляется в существующую группу, а не в конец списка.

```
1.  Input          — InputState → намерения
2.  Abilities      — кулдауны, заряды, активация способностей
3.  Spawn          — таймлайн волн, гарантия элиток, мини-босс
4.  AI             — выбор цели, желаемое направление
5.  Movement       — скорости, Facing, обновление spatial hash
6.  Weapons        — кулдауны автоатак, создание атак
7.  AttackLifetime — снаряды, ауры, установленные объекты
8.  Collision      — пересечения через spatial hash
9.  Damage         — неуязвимость, применение урона
10. Death          — смерти, дроп, опыт, валюта
11. Progression    — уровни, выбор апгрейда, заряд ульты
12. ViewSync       — перенос состояния во вьюхи
13. Cleanup        — удаление one-frame компонентов
```

`Abilities` до `Movement` — рывок должен успеть изменить скорость в том же кадре.

**Одноразовые события** — компоненты, создаваемые в кадре и удаляемые в `Cleanup`. Никаких C#-событий и `Action` внутри симуляции.

## 11. Модель апгрейдов — компонентная

**Решение принято.** Апгрейд не правит числа, а **добавляет компоненты и включает системы**.

Причина: заявлены апгрейды вроде «второй заряд рывка», «ульта оставляет след», «ловушка срабатывает дважды». Числовая модель их не выражает — потребовались бы флаги-костыли. Плюс пострелизные обновления обязаны добавлять поведение, а не только множители.

Требования к каждому апгрейду:
- **идемпотентность** — взят дважды, поведение предсказуемо;
- **независимость от порядка** взятия;
- **стабильный ID** (см. §4).

## 12. Spatial hash

Физика Unity не тянет 500+ агентов с покадровыми запросами.

- Мир разбит на ячейки фиксированного размера (**TBD**, ориентир — 2× радиуса частой атаки).
- Регистрация в ячейке на шаге `Movement`; установленные объекты регистрируются один раз.
- Поиск ближайших = обход 9 соседних ячеек.
- Структуры переиспользуются между кадрами, без аллокаций.

Игра логически 2D (движение по плоскости), 3D — только визуал. Сетка двумерная.

## 13. Рендер толпы

1. **Этап 1 (сейчас):** префабы + пул. Хватает до ~150 врагов.
2. **Этап 2:** отказ от `Animator` в пользу простых состояний.
3. **Этап 3:** `RenderMeshInstanced` + vertex animation texture.

Переход — только после профилирования. Вьюхи с начала прячутся за интерфейсом, чтобы замена не трогала симуляцию.

## 14. Структура папок

```
Assets/
  _Project/
    Bootstrap/        точка входа, LifetimeScope, инициализация ECS
    Configs/          персонажи, враги, оружие, способности, эффекты, волны, апгрейды, перки, предметы
    Core/             утилиты, интерфейсы сервисов, math, ContentRegistry
    Services/         реализации сервисов: ввод, аудио, загрузка сцен, файловый I/O сейвов
    Simulation/
      Components/     только данные
      Systems/        по группам из §10
      Services/       spatial hash, фабрики сущностей, пайплайн статов
    View/             вьюхи, пулы, VFX
    UI/               экраны, HUD, презентеры
    Meta/             сейвы, мета-прокачка, инвентарь, стори-прогресс
    Art/ Audio/ Prefabs/ Scenes/
```

**Компоненты одной темы — один файл.** `MovementComponents.cs`, `CommonComponents.cs`, `TagComponents.cs`, `AbilityComponents.cs`. Файл на компонент даёт каталог из сотни файлов по три строки; файл на всё — конфликты слияния и потерю темы.

**Системы — один файл на систему**, имя файла равно имени класса.

`Core/` держит **интерфейсы** сервисов, `Services/` — их реализации. Не путать с `Simulation/Services/`: там сервисы симуляции (spatial hash, фабрики сущностей, пайплайн статов), которые живут внутри ECS-границы и наружу не выходят.

## 15. Assembly Definitions

```
Game.Core         → (нет зависимостей от проекта)
Game.Configs      → Core
Game.Services     → Core, Configs
Game.Simulation   → Core, Configs
Game.View         → Core, Configs
Game.UI           → Core, Configs
Game.Meta         → Core, Configs
Game.Bootstrap    → всё вышеперечисленное
```

`Game.Simulation` не зависит от `Game.View` и `Game.UI`.

**`Game.Core` содержит типы `UnityEngine`** — `Vector2`, `Vector3`, `Transform`, `GameObject` ради `IInputService` и `IViewFactory`, и перечисления, общие для `Game.Configs` и `Game.Simulation` (`DashDirection`). Это осознанная уступка: свой векторный тип и непрозрачные хендлы вместо `Transform` стоят дороже, чем дают. Пересматривать здесь, если `Game.Core` понадобится вне Unity.

**Вьюху создаёт симуляция, а не ищет в сцене.** `IViewFactory` объявлен в `Game.Core`, реализация — в `Game.View`, префаб приезжает из `CharacterConfig`. Связать объект, положенный в сцену руками, со скоупом забега нечем: `CreateChild` вешает скоуп забега под проектный корень в `DontDestroyOnLoad`, а `RegisterComponentInHierarchy` ищет в сцене своего скоупа. Это же и шов под пул вьюх шага 4.

**`Game.View` дополнительно ссылается на `Unity.Cinemachine`.** Камера — часть слоя вьюх, и Cinemachine не имеет права протечь ни в `Game.Simulation` (там `overrideReferences`), ни в `Game.Core`: наружу торчит только `ICameraService` с `Transform` в сигнатуре.

**Соседи по слою не ссылаются друг на друга.** `Game.UI` не видит `Game.Meta`, `Game.View` не видит `Game.Services`. Связь — через интерфейс, объявленный в `Game.Core`.

**`Game.Simulation` не ссылается на `VContainer`.** Это то, чем граница двух DI держится физически: без ссылки система не может достать контейнер, и единственный оставшийся путь передать в неё сервис — `EcsSystems.Inject()` через LeoECS Lite DI.

**`Game.Simulation` компилируется с `overrideReferences: true` и пустым `precompiledReferences`.** Список ссылок asmdef не управляет precompiled-библиотеками: dll вне asmdef (пакеты NuGet в `Assets/Packages`) автоматически видны всем сборкам проекта. Без этого флага `using R3;` внутри ECS-системы компилируется, и запрет из `CLAUDE.md` §7 держится дисциплиной, а не компилятором.

**Объекты на сцене инжектятся сценовым `LifetimeScope`.** Проектный корень живёт префабом в `DontDestroyOnLoad` и объекты загружаемых сцен не видит. Сцена, которой нужны сервисы, кладёт собственный `LifetimeScope`: родителя ему не указывают — VContainer сам находит корневой скоуп, — а её `MonoBehaviour` регистрируются `RegisterComponentInHierarchy<T>()`, который ищет только в сцене своего скоупа и форсирует резолв при построении контейнера. Значит инъекция происходит до первого кадра, а отсутствующий компонент падает сразу, а не `null`-ом по первому обращению.

`autoReferenced: false` у всех сборок проекта: `Assembly-CSharp` в проекте не используется, и забытый вне asmdef скрипт должен падать с ошибкой, а не молча компилироваться.

## 16. Сейвы

- JSON, версионирование с первого дня: `{ "version": 1, ... }`.
- Все ссылки на контент — по стабильным ID (§4).
- **Четыре независимых блока:**
  - аккаунтная мета — валюты, общая ветка перков;
  - прогресс персонажей — персональные ветки, разблокировки;
  - инвентарь — предметы и их уровни;
  - стори-прогресс — пройденные воспоминания, сбрасывается «Новой игрой».
- Миграции — явные методы `Migrate_1_to_2()`, а не «попробуем распарсить».
- Запись атомарная: временный файл → замена.

## 17. Выстраданные правила

Правила, полученные не из теории, а из уже сломанного в этом проекте. Баг искался дольше часа и причина оказалась архитектурной — сюда добавляется строка. Самый ценный раздел в долгой перспективе.

Формат: **правило — что происходит при нарушении.**

- _(пусто — появится после первого дорогого бага)_

Как это выглядит в зрелом проекте (для ориентира, из соседнего проекта):
- *Один реактивный флаг — один писатель.* Два писателя дают тихий orphaning: состояние рассинхронизировано, ошибки нет.
- *`Dispose()` стейт-машины обязан звать `Exit()`.* Иначе при жёстком teardown сцены глобальные сервисы остаются грязными.
