1. Урон по врагам: «сильнейшее событие на цель за тик»
==========================================================================
Да, действует для любой цели с Health, в том числе для врагов: отбор в
ApplyDamageSystem.cs:61-69 не смотрит на тип цели. Ничьи — первое событие в
порядке фильтра (сравнение «<=», :65).
Что теряется у более слабого события по той же цели в тот же тик:
  - урон целиком (в Health вычитается только сильнейшее, :86);
  - DamageApplied (:88) — а его читают AccumulateRageSystem (ярость за
    попадание, :16, :61) и PlayHitFeedbackSystem (:11, фидбэк удара);
  - KillingBlow от него (:91-95).
Неуязвимости у врагов нет (EnemyFactory HitInvulnerability не выдаёт), поэтому
следующего тика это не касается — только совпадение в одном тике.
Замер (зонд, сид 987654321, 5340 тиков, события считались сразу после
ApplyDamageSystem, до MarkDeadSystem — иначе убитые к группе 13 уже удалены):
  стоя:        153 события по врагам, применены все 153, тиков «враг с ≥2
               событиями» — 0; снимок md5 2438d51bd8ab36e4fd0dd3c168a90d1b
  стоя с Q:    148 событий, все применены, совпадений 0, 4 включения режима;
               md5 32a9a75fcc9086364302f8d40532d663
  Оба md5 совпали с эталоном отчёта 039 — это второй прогон каждого сценария
  на одном коде (первым был 451f1ae), побайтово.
Почему 0: сегодня единственный источник урона по врагам — меч (AdvanceSwingSystem
:147): одно оружие, один живой взмах, одно попадание на врага за взмах.
Значение для шага 7: контрудар, прыжок и шлейф — это второй, третий и четвёртый
источник. Совпадение «меч + перк по одному врагу в одном тике» станет обычным, и
более слабый удар будет потерян молча, вместе с фидбэком.

  Б. Правило только для героя (сегодня оно нужно ему: контактный урон от
     нескольких врагов, замер — 1959 тиков с ≥2 событиями по герою за прогон
     стоя), по врагам — сумма всех событий. Цена: ветка в ApplyDamageSystem,
     KillingBlow — от последнего/сильнейшего, DamageApplied на каждое событие.
  В. Правило «сильнейшее за тик на пару (источник, цель)». Цена: ключ словаря

2. Ярость: кто копит и как отсечь урон перков
==========================================================================
AccumulateRageSystem, группа 11 (RunSystems.cs, «11. Progression»).
Читает сущности Inc<DamageEvent, DamageApplied> (:16) — то есть только
применённые события. Нанесённое: DamageEvent.Source == герой → +DealtPerHit
(:61-64), плоско за событие. Полученное: Target == герой →
+DamageApplied.Amount / MaxHealth × ReceivedScale (:67-70). Любое из двух
сбрасывает TicksSinceCombat (:79) — то есть держит ярость от спада.
Способы отсечь урон перков, не меняя Source:
  1. Тег-компонент на сущности события (например PerkDamage), Exc в фильтре
     :16. Цена: одна строка в фильтре + Add у каждого перка-источника; забытый
     Add = молча копит ярость. Событие остаётся одного типа для ApplyDamage и
     фидбэка.
  2. Поле в DamageEvent (вид урона: оружие / перк / контакт). Цена: поле в
     структуре, все производители пишут его явно (сегодня два — :147 и
     DetectContactDamageSystem:94); значение по умолчанию надо выбрать так,
     чтобы забытое поле не копило (то есть «не копит» по умолчанию, а меч
     ставит «оружие» явно). Даёт и UI/фидбэку различать источник.
  3. Отдельная сущность-источник: Source = герой, но рядом PerkSource { Id }
     или OwnerLink-подобная ссылка на перк. По сути вариант 1 с данными.
  4. Отдельный тип события перка, применяемый той же ApplyDamageSystem. Цена:
     второй фильтр и второй поток событий через ApplyDamage, фидбэк и
     ярость — дублирование, высокая.
  Открыто для решения: сбрасывает ли урон перка паузу спада (inCombat, :65) —
  при варианте 1/2 это выбирается одной строкой.

6. Толчок от точки
==========================================================================
Да, без правки SweepDashPushSystem: Pushed — простой компонент
{ Velocity, RemainingTicks, TotalTicks } (Components/CombatComponents.cs:18-23),
сервиса нет. Новая система ставит направление от героя к врагу (и разрыв ничьей
при совпадении позиций — как SweepDashPushSystem.cs:115-120).
Его потребители: ApplyPushSystem ставит скорость с линейным затуханием по
времени (ApplyPushSystem.cs:22-33), ApplyMoveSpeedSystem исключает Pushed
(:9), ResolveBodyOverlapSystem пропускает отброшенных (:85).
Враг, у которого Pushed уже есть: EcsPool.Add на висящий компонент бросает
«already attached» ТОЛЬКО в DEBUG (ecslite components.cs:183); в билде проверки
нет и пул портится молча. Значит Has обязателен. Выбор: пропустить (как
SweepDashPushSystem.cs:92), перезаписать (Get и новая скорость/тики), сложить.
Важно: запас запроса контактного урона учитывает скорость толчка только рывка —
EnemyMotionBounds.PushSpeed = character.Dash.PushSpeed (EnemyMotionBounds.cs:44),
CandidateSlack (:49-55). Толчок прыжка быстрее рывка (сегодня 5 м/с) молча
занизит запас → контактный урон может не увидеть врага. Выход: максимум по
всем источникам толчка в EnemyMotionBounds.From.

11. Вьюха для VFX-префаба без аниматора
==========================================================================
Может. ViewPool требует на корне префаба только ViewInterpolator
(View/ViewPool.cs:238-243); Animator ищется опционально (:249), при null
Rebind пропускается (:107-111), Configure безопасен (HasParameter при null →
false). Все методы IView у ViewInterpolator есть и без аниматора — no-op.
Обязательно для симуляции: компонент View на сущности. Позицию переносит
SyncViewSystem — фильтр Inc<Position, Facing, View> (:10): без Facing сегмент не
синхронизируется, но Create ставит вьюху сразу на позицию (неподвижному сегменту
этого хватает). Release сегодня не зовёт ни одна система (враги — Retire, прочие
— ViewPool.Dispose), система жизни сегмента обязана звать Release сама.
Рендереры VFX-префаба попадут в список дизолва/мигания своей вьюхи — это их
собственная вьюха, конфликта нет (правило §8 CLAUDE — про потомков вьюхи героя).

13. Длительность ульты и AttackSpeed
==========================================================================
Длительность — свойство конфига, не стат: BerserkAbilityConfig.DurationSeconds,
в тики переводит StartBerserkSystem.cs:48 при старте. StatId под неё нет
(Core/StatId.cs, 1–8). Перк «продление ульты» потребует либо новый StatId
(номер 9, таблица заморожена StatIdTableTests — дописывается, не
переиспользуется), либо чтения уровня перка в StartBerserkSystem.
AttackSpeed читает только StartSwingSystem: кулдаун ÷ AttackSpeed (:83),
упреждение (:138), снимок длительности и скорости взмаха (:162-173). Больше
нигде в симуляции; во вьюхе — параметр аниматора через PlayAttack
(ViewInterpolator.cs:177-180). На рывок, ульту, будущие перки сам не действует.

14. Прерывание взмаха особой атакой
==========================================================================
InterruptSwingSystem (группа 6, перед StartSwingSystem): для каждой Swing —
если владельца нет, он Dead или Dashing, сущность Swing удаляется, у оружия
снимается Swinging (:22-34). Кулдаун (WeaponReady.Remaining) не трогается.
StartSwingSystem не стартует, если владелец Dead или Dashing (:64).
Вьюха о прерывании не знает: события нет. Картинку слеша обрывает только
переход слоя Attack Any State → Empty по IsDashing (Berserk.controller); на
смерть перехода нет.
Что потребуется, чтобы Spin/Jump прерывали слеш и запрещали новый:
  А. Маркер «особая атака идёт» на герое + условие в двух местах:
     InterruptSwingSystem :28 и StartSwingSystem :64. Плюс во вьюхе — переход
     слоя Attack в Empty по этому состоянию (как по IsDashing). Цена: две строки
     и параметр аниматора.
  Б. Общий маркер «руки заняты», который ставят рывок, особые атаки (и, если
     нужно, смерть), а взмах проверяет только его. Цена: рефакторинг рывка —
     одно изменение — одна причина, отдельным заходом.
  Рекомендация: А сейчас, Б — когда занятых состояний станет больше трёх.
