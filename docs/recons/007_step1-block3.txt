2. ПРИНЯТЫЕ РЕШЕНИЯ
--------------------------------------------------------------------------------

Все три записаны в журнал PROGRESS.md от 2026-08-21 полностью. Здесь —
заголовки и то, чего в журнале нет.

Решение А. «Мультисценность — сцена на уровень, LoadSceneMode.Single».
    Закрывает открытый вопрос ARCHITECTURE.md §18. Коротко: аддитивная
    загрузка нужна прежде всего ради постоянной сцены, а постоянной сцены
    в проекте нет — проектный корень живёт в DontDestroyOnLoad.

Решение Б. «Забег запускает RunLauncher проектного уровня, скоуп забега
    создаётся кодом». Закрывает Р-3 отчёта 006. Ключевое: RunLifetimeScope
    НЕ лежит объектом в сцене Gameplay. Причина механическая — сценовый скоуп
    строит себя в Awake, до того как ему можно передать RunContext, и
    единственный штатный способ передать параметры такому скоупу это
    статический стек LifetimeScope.Enqueue, то есть глобальное состояние.

Решение В. «Game.Simulation закрывается от precompiled-библиотек».
    Закрывает пункт техдолга CLAUDE.md §8 в части симуляции.

Чего в журнале нет:

  - Решения А и Б связаны сильнее, чем кажется. Если бы мультисценность была
    аддитивной, вариант «скоуп лежит в сцене уровня» стал бы заметно
    привлекательнее: сцена уровня выгружалась бы отдельно и уносила скоуп
    с собой. При Single этот аргумент исчезает, и остаётся только минус
    с передачей RunContext. Решать их порознь было нельзя — потому они и
    стояли в отчёте 006 парой.

  - Обратная сторона решения Б названа явно: объект скоупа забега висит под
    проектным корнем в DontDestroyOnLoad и выгрузкой сцены не уничтожается.
    Владелец назван, но защиты от «забыл Dispose» нет никакой, и первый
    симптом — удвоенный тик на втором забеге.

4. ПРОВЕРКА ПОВЕДЕНИЕМ — ЧТО ПРОВЕРЕНО ЭКСПЕРИМЕНТОМ
--------------------------------------------------------------------------------

LeoECS Lite d46f3b2, LeoECS Lite DI 482b14e, Unity 6000.4.11f1.
Всё ниже наблюдалось, а не предполагалось.

Порядок вызовов:
  1. Правильная последовательность Add → Inject → Init заполняет всё:
     EcsWorldInject, EcsPoolInject, EcsFilterInject и EcsCustomInject.
  2. Inject, вызванный ДО Add, не заполняет НИЧЕГО — включая мир, пулы и
     фильтры. Ни ошибки, ни предупреждения. Все поля остаются null, падение
     приходит позже, в первом Run.
  3. EcsCustomInject<T>, для которого не передан объект подходящего типа,
     остаётся null. Молча.
  4. Поле-инъект, помеченное readonly, заполняется нормально: рефлексия
     справляется. То есть readonly можно и нужно ставить.

Порядок выполнения:
  5. Run идёт в порядке добавления систем: добавили A, потом B — каждый кадр
     A, затем B.
  6. Destroy идёт в ОБРАТНОМ порядке: сначала B, потом A. Зеркалит поведение
     VContainer из блока 2.

Владение и разбор:
  7. systems.Destroy() мир не уничтожает: world.IsAlive() остаётся true.
  8. Забытый world.Destroy() не даёт ни ошибки, ни предупреждения. Мир просто
     продолжает жить со всеми сущностями.
  9. world.Destroy() при наличии сущности без компонентов бросает
     «Empty entity detected before EcsWorld.Destroy()». Проверка живёт под
     #if DEBUG — в билде её нет, а утечка останется.
 10. По исходнику (не проверялось запуском, но код однозначный): Run до Init
     бросает «Cant run without initialization», Add после Init — «Cant add
     system after initialization». Обе проверки тоже только под DEBUG.

Границы сборок:
 11. using R3; внутри Game.Simulation КОМПИЛИРУЕТСЯ, хотя ссылки на пакет R3
     у сборки нет: R3.dll из Assets/Packages подмешивается автоматически,
     потому что лежит вне asmdef.
 12. После overrideReferences: true и пустого precompiledReferences тот же
     using даёт CS0246. Проверено на живом проекте.
 13. Цена правки — ноль: LeoECS Lite и LeoECS Lite DI подключены как
     asmdef-пакеты и не задеты, сборка компилируется, число подмешанных

5. РИСКИ И НЕЗАКРЫТОЕ
--------------------------------------------------------------------------------

Р-1. ДОКУМЕНТАЦИЯ ВПЕРЕДИ КОДА, и это создано этой сессией.
     ARCHITECTURE.md §15 описывает overrideReferences: true у Game.Simulation
     как действующее правило, но в Assets/_Project/Simulation/Game.Simulation.asmdef
     правки нет — я проверил её экспериментом и откатил, потому что asmdef
     правит разработчик.

     Нужны два поля:
       "overrideReferences": true,
       "precompiledReferences": []

     Пока это не сделано, документ врёт, а красная линия CLAUDE.md §7 про R3
     внутри ECS-систем держится только вниманием. Это первый пункт §6.

Р-2. Кода блока нет, скелет не проверен компиляцией. Скелет урока 04
     опирается на реальные сигнатуры LeoECS и VContainer, но целиком, как
     работающая связка, ещё не собирался. Ошибки в нём возможны и всплывут
     при написании.

Р-3. Владение миром при появлении сервисов симуляции. Сейчас EcsWorld создаёт
     и уничтожает RunEntryPoint, и это чисто. Но на шаге 3 появится spatial
     hash, которому мир нужен в конструкторе, — а мир к моменту построения
     графа ещё не создан. Два выхода: либо мир становится Scoped-регистрацией
     через фабрику и получает явную обёртку-владельца, либо сервисы симуляции
     получают мир не через конструктор, а на Init. Решать на шаге 3, не раньше:
     сейчас данных для выбора нет.

Р-4. Группа Cleanup (§10, пункт 13) пуста, и механизма удаления one-frame
     компонентов не существует. Он понадобится вместе с первым компонентом
     с суффиксом Event — это шаг 4 (боёвка). Если про него забыть, события
     начнут жить вечно, и симптом будет «урон применяется повторно», а не
     «нет системы очистки».

Р-5. GetShared / EcsSharedInject намеренно не используются: выбран один
     механизм передачи сервисов — EcsCustomInject через Inject(...). Если
     кто-то однажды применит shared-объект, в проекте станет два пути
     передачи данных в системы, и вопрос «где искать эту зависимость»
     перестанет иметь один ответ.

Р-6. DEBUG-проверки LeoECS в билде отсутствуют. Утечка пустых сущностей,
     Run до Init, Add после Init — всё это ловится только в редакторе.
     Аргумент к тому, чтобы регулярно гонять забег в редакторе, а не только
     в билде.

Р-7. Открытым остаётся Р-7 отчёта 006 (EditorBuildSettings, Gameplay
     enabled 0 → 1) и Р-8 (Missing на Canvas в MainMenu).

Р-8. Открытыми остаются риски отчёта 005: состав сервисов не фиксирован
     намеренно, вопрос про Presenter между UI и Meta, противоречие Simulation
     и ScriptableObject, два механизма загрузки (Resources и Addressables).
     Последний стоит пересмотреть: папка Resources из проекта ушла, а
     Addressables, судя по артефактам сборки, живы.
