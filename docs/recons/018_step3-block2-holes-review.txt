2. ГЛАВНОЕ: ПРОЕКТ НЕ СОБИРАЛСЯ НА HEAD
----------------------------------------

Коммит 17d2939 содержит ошибку компиляции. Не «предупреждение», не
«подозрительное место» — красный CS0815, при котором Unity не компилирует
ни одну сборку и play mode не запускается вовсе:

  Assets\_Project\Simulation\Services\WeightedEnemyPicker.cs(26,17):
  error CS0815: Cannot assign <null> to an implicitly-typed variable

Строка 26 в сдаваемом виде:      var entry = null;
Строка 42 в сдаваемом виде:      return entry;

Вторая строка сломана независимо от первой: `entry` — это `WeightedEnemy`,
а метод объявлен возвращающим `EnemyConfig`. То есть даже если бы `var`
вывелся, файл упал бы на CS0029.

ЧТО ИЗ ЭТОГО СЛЕДУЕТ ПРАКТИЧЕСКИ, и это важнее самой опечатки: код уехал в
коммит, ни разу не будучи скомпилированным. Это тот же класс события, что
CLAUDE.md §6.7 («чистая консоль не означает "работает"»), только с другой
стороны — здесь консоль была НЕ чистая, и её просто никто не открыл перед
коммитом. Дешёвая привычка, закрывающая этот класс целиком: перед `git commit`
переключиться в Unity и посмотреть, что счётчик ошибок ноль. Одно движение.


3. ДЫРКА 1 — ResolveSpawnCount. ЗАПОЛНЕНА ВЕРНО
------------------------------------------------

Сданное тело (SpawnWaveSystem.cs:160-172):

  accumulator += ratePerSecond * deltaSeconds;
  int result = (int)accumulator;
  accumulator -= result;
  if (liveCount + result > liveLimit)
      result = liveLimit - liveCount;
  return Math.Max(0, result);

ВЫБРАННЫЙ ВАРИАНТ — В1-Б («сколько накопилось, столько и за тик»).
Контракт отчёта 017 §10 выполнен по всем пунктам: возврат всегда >= 0,
накопитель обновляется и только здесь, аллокаций нет, дробь не теряется.

ПОЛИТИКА НАКОПИТЕЛЯ ПРИ УПОРЕ В LIMIT — а вот тут выбран вариант, которого в
разборе 017 не было, и он лучше всех трёх названных. Отчёт предлагал (а) не
прибавлять, (б) прибавлять и копить долг, (в) обнулять. Сданный код делает
(г): прибавляет и СПИСЫВАЕТ целую часть полностью, а урезает только
возвращаемое число. Долг не копится (требование задачи), при этом честная
дробь текущего тика не теряется, в отличие от (в). Отдельно отмечаю: это не
случайность формы — порядок строк (сначала списать, потом урезать) и есть всё
решение; поменяй их местами, и получится (б).

ЗАМЕРЫ (прямой вызов метода через рефлексию, execute_code, delta = 1/60):

  темп 1/с, 600 тиков (10 с)   -> всего 9,   максимум за тик 1
  темп 25/с, 600 тиков         -> всего 250, максимум за тик 1
  темп 120/с, 600 тиков        -> всего 1200, максимум за тик 2
  темп 200/с, 600 тиков        -> всего 2000, максимум за тик 4
  темп 0/с                     -> всего 0
  темп 600/с, живых 28, потолок 30 -> 2 (урезано с 10), накопитель 9.5e-07
  живых 45 при потолке 30      -> 0
  темп 10/с, 300 тиков ВПРИТЫК К ПОТОЛКУ -> заспавнено 0, накопитель 0.0
     первый тик после освобождения потолка -> 0 (взрыва долга НЕТ)
     следующие 60 тиков -> 10 (темп восстановился ровно)

Ловушка «период в целых тиках» (25/с -> 2.4 тика) обойдена: 250 из 250.
Ловушка «взрыв долга» обойдена: 0 вместо 50 накопленных за 5 секунд у потолка.

Про «всего 9 вместо 10» при темпе 1/с: 600 × (1/60) в float даёт 9.999999,
десятый спавн приходит одним тиком позже. Это фаза, не потеря — та же
недобранная дробь, что отчёт 017 разобрал в замере 1.

ЧТО НЕ ДЕФЕКТ, НО СТОИТ ЗНАТЬ (расплата варианта В1-Б, названная в 017):
при темпе выше 60/с спавн идёт пачками. Замерено: на 200/с в одном тике
рождается до 4 врагов. Сегодня в конфиге максимум 2/с, так что не стреляет;
выстрелит на поздних волнах, когда 500 Instantiate соберутся в один тик.

РИСК, КОТОРЫЙ ВИДЕН РЯДОМ И КОТОРЫЙ Я НЕ ЧИНИЛ (CLAUDE.md §6.4):
отрицательный `ratePerSecond` уводит накопитель в минус без дна. Замер: темп
-5/с за 600 тиков даёт накопитель -0.9999999 и продолжает падать; спавнов 0,
ошибки нет. Отрицательный темп в конфиге не запрещён ничем — ни инспектором,
ни `Validate` в системе. Симптом при опечатке в ассете будет «волна молчит»
без единого сообщения. Место для проверки очевидное — `SpawnWaveSystem.Validate`,
который уже ходит по всем волнам и уже умеет бросать с внятным текстом.
Это правка агентской части каркаса, не дырки; жду отдельной задачи.


4. ДЫРКА 2 — WeightedEnemyPicker.Pick. ПОЧИНЕНА, ДАЛЬШЕ ВЕРНА
--------------------------------------------------------------

ВЫБРАННЫЙ ВАРИАНТ — В2-А (две итерации: сумма, затем курсор), со строгим
неравенством `cursor > target` и пропуском записей с весом <= 0. Обе ловушки
из контракта обойдены осознанно: нормализации весов нет, нулевой вес
недостижим.

ЧТО ИСПРАВЛЕНО (единственная правка кода за сессию, две строки):

  было (26):  var entry = null;
  стало:      WeightedEnemy entry = null;

  было (42):  return entry;
  стало:      return entry.Enemy;

Обе правки восстанавливают ЗАМЫСЕЛ автора, а не подменяют его: `entry`
существует ровно затем, чтобы запомнить последнюю запись с положительным
весом и вернуть её, если курсор из-за ошибки float так и не превысил target
при roll, близком к единице. Это правильный запасной путь, он просто не
компилировался. `entry.Enemy` безопасен без проверки на null: до этой строки
доходят только когда `total > 0`, а значит хотя бы одна запись с весом > 0
существует и была присвоена в цикле.

ЗАМЕРЫ (execute_code, реальные ассеты Enemy_Devil и Enemy_Troll):

  A. веса 3:1, 100 000 равномерных бросков
     -> devil 75000, troll 25000, null 0. Пропорция точная.
  B. первая запись с весом 0, вторая с весом 5, 100 000 бросков
     -> запись с нулевым весом выбрана 0 раз; Pick(list, 0f) -> devil.
        Ловушка «target = 0 достаёт нулевую запись» не сработала.
  C. запись с весом -4 рядом с весом 1
     -> отрицательная выбрана 0 раз, сумма ею не испорчена.
  D. пустой список -> null; все веса нулевые -> null. Оба законных null.
  E. roll = 0.99999994 (максимум, который может отдать SimulationRandom:
     24 бита / 2^24) -> возвращается последняя запись, не null.
  F. 64 записи по 0.1 (сумма копится с ошибкой float), 16 825 бросков
     по всему диапазону -> null не вернулся ни разу.

Замер F — тот самый, ради которого нужен запасной путь: он показывает, что
на сегодняшних данных путь недостижим, но стоит он одну ссылку.

СТИЛЬ, НЕ ЧИНИЛ: локальные счётчики названы `i`, тогда как весь остальной код
блока (SpawnWaveSystem, ResolveMaxGuaranteedCount, Validate) пишет `index`.
CLAUDE.md §5 про локальные переменные молчит, так что это не нарушение
конвенции, а расхождение внутри одного блока. Решать автору.

Р-2. Техдолг CLAUDE.md §8, пункт «Границы арены — одно число в LevelConfig»,
     стал острее, чем описан. На момент отчёта 015 в нём стояло
     `SpawnRadius = 18` против `ArenaRadius = 30`. В сдаваемом ассете
     Waves_Gameplay `_spawnRadius: 30`, то есть радиус кольца спавна теперь
     РАВЕН радиусу арены.
     Что это значит численно. `RingSpawnPlacement.Resolve` строит точку на
     кольце вокруг ИГРОКА, а потом прижимает её к кругу арены вокруг ORIGIN.
     Пока игрок в центре, |точка| = 30.000 — ровно на границе прижатия,
     условие `distance <= arenaRadius` ещё выполняется, прижатия нет.
     Стоит игроку отойти на d метров — дальняя половина кольца оказывается
     на 30 + d и вся прижимается на одну дугу окружности радиуса 30.
     То есть при `SpawnRadius == ArenaRadius` вырождение начинается с ПЕРВОГО
     ЖЕ шага игрока, а не «когда игрок отойдёт от центра». В отчёте 015 при
     радиусе 18 запас был 12 метров.
     Это не дефект кода — код делает ровно то, что написано. Это конфликт
     двух чисел в двух ассетах, и он относится к тому же решению уровня,
     что уже записано в §8. Отдельным пунктом заводить не стал, но текст
     существующего пункта стоит дополнить: конфликт больше не «схлопывается,
     как только игрок отходит», он схлопнут уже в нуле.
