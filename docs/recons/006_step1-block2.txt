2. ПРИНЯТЫЕ РЕШЕНИЯ
--------------------------------------------------------------------------------

Оба записаны в журнал решений PROGRESS.md от 2026-08-20 полностью. Здесь —
только заголовки и то, чего в журнале нет.

Решение А. «Два уровня корня композиции: проектный и корень забега».
    Что на каком уровне, кто кого пересоздаёт при рестарте, что переживает
    смерть игрока, а что нет — в журнале. Опирается на ARCHITECTURE.md §9
    (RunContext), §16 (четыре блока сейва) и GDD.md §6 (валюта переживает
    смерть).

Решение Б. «Запуск не с той сцены — корневой префаб в VContainerSettings».
    Выбран вариант, которого в списке блока 1 не было. Префаб скоупа кладётся
    в поле RootLifetimeScope ассета VContainerSettings, ассет — в Preloaded
    Assets, и библиотека сама поднимает корень в DontDestroyOnLoad при
    загрузке первой сцены.

    Почему не три варианта из урока 02, 2.4: он единственный не заводит
    второго пути инициализации. Ручной старт с Bootstrap (вариант а) стоит
    клика на каждый прогон; хук (б) и автономный сценовый скоуп (в) дают
    второй путь, а значит баги, воспроизводимые через раз.

    Граница решения: префаб поднимает сервисы, но не создаёт RunContext.
    Запуск прямо с Gameplay обязан падать с внятным VContainerException,
    а не подниматься с дефолтным забегом.

Чего в журнале нет и что стоит держать в голове:

  - Решение Б делает проектный корень префабом, поэтому в сцене Bootstrap
    объекта скоупа быть не должно вообще — иначе корней окажется два.
    Объект из сцены удалён.
  - Решение Б добавляет одну хрупкую точку: ссылку на ассет в Preloaded
    Assets. Она не защищена ничем и теряется при мердже ProjectSettings.asset.
  - Пункт меню Assets → Create → VContainer → VContainer Settings сам кладёт
    созданный ассет в Preloaded Assets. Отдельно добавлять руками не нужно,
    но проверить глазами — обязательно.

3. РЕВЬЮ КОДА — ЧТО НАШЛОСЬ И ЧТО ИСПРАВЛЕНО
--------------------------------------------------------------------------------

Первая версия кода запускалась и работала. Ревью нашло четыре вещи, все
исправлены в этой же сессии.

3.1. `using Unity.ProjectAuditor.Editor;` в SceneLoader.cs — сломало бы билд.

     Редакторный неймспейс в runtime-сборке. В редакторе компилировался,
     в player-сборке дал бы CS0246. Проверено списками ссылок:

       Game.Services, EDITOR-компиляция:  UnityEditor.ProjectAuditorModule.dll
                                          подключён автоматически
       Game.Services, PLAYER-компиляция:  Game.Core, UniTask, R3.Unity,
                                          Unity.InputSystem, UnityEngine.UI
                                          — ProjectAuditor отсутствует

     Подсунуто автоимпортом IDE. Удалено. Вывод общего характера ушёл
     в CLAUDE.md §8: чистая консоль не значит, что билд соберётся.

3.2. `using R3;` в ProjectLifetimeScope — лишний, но интересен причиной.

     Game.Bootstrap.asmdef на пакет R3 не ссылается, а компилировалось.
     Причина: R3.dll из Assets/Packages лежит вне asmdef и подмешивается
     во все сборки проекта напрямую. Проверено — в списке ссылок
     Game.Bootstrap стоит путь к dll, а не имя пакета.

     Следствие шире одного using и записано в CLAUDE.md §8: R3 виден и из
     Game.Simulation, то есть запрет §7 на подписки R3 внутри ECS-систем
     держится дисциплиной, а не компилятором.

3.3. `using Game.Services;` в BootstrapEntryPoint — удалён.

     Не использовался, но важен как симптом. Корню знать Game.Services
     положено, он регистрирует реализации. Точке входа — нет: она работает
     через ISceneLoader из Game.Core. Из такого using через месяц вырастает
     прямая ссылка на реализацию.

3.4. `RegisterInstance(_loadingScreenPrefab)` — удалён.

     Регистрация без потребителя. Два конкретных минуса помимо «объявлено
     заранее»: занимает единственный в контейнере слот типа GameObject,
     так что второй префаб этим способом уже не зарегистрировать; и при
     пустом поле в инспекторе в контейнер уехал бы null без возражений.
     Поле [SerializeField] оставлено — ссылка на префаб назначена и не
     мешает, предупреждения компилятора не даёт.

Мелочи, исправлены заодно: `_sceneLoader` стало readonly, промежуточные
переменные `UniTask task = ...; return task;` убраны в обоих файлах.

Что осталось как есть по решению разработчика: идентификатор сцены —
строковый литерал "MainMenu" в BootstrapEntryPoint. Решение осознанное,
записано в CLAUDE.md §8 с условием возврата.

3.5. Предупреждение, которое разбиралось отдельно.

     Вывод: застрявший артефакт импорта, скорее всего след от попытки

7. ЧТО ПРОВЕРЕНО ЭКСПЕРИМЕНТОМ — СПРАВОЧНЫЙ СПИСОК
--------------------------------------------------------------------------------

VContainer git 5103bfc, Unity 6000.4.11f1. Всё ниже наблюдалось, а не
предполагалось. Список полезен тем, что переспрашивать его дороже, чем читать.

Порядок жизненного цикла:
  1. Configure, конструкторы, IInitializable.Initialize и
     IPostInitializable.PostInitialize выполняются синхронно внутри Awake
     скоупа, в кадре 0.
  2. Awake обычных MonoBehaviour идёт после Awake скоупа
     ([DefaultExecutionOrder(-5000)]).
  3. В кадре 1: IStartable.Start → MonoBehaviour.Start → IPostStartable.PostStart.
     То есть Start точки входа раньше Start вьюхи, а PostStart — позже.
  4. Внутри кадра: FixedTick → Tick → LateTick.
  5. Dispose идёт в порядке, обратном созданию: точка входа уничтожается
     раньше сервиса, от которого зависела.

Времена жизни:
  6. Дочерний скоуп без собственной регистрации отдаёт тот же экземпляр
     родительского Singleton.
  7. Тот же тип, повторно объявленный Singleton'ом в дочернем скоупе, даёт
     ВТОРОЙ экземпляр. Ошибок нет.
  8. Scoped стабилен внутри своего скоупа, при Dispose скоупа уничтожается,
     родительские объекты не трогаются.
  9. Второй дочерний скоуп получает свежие Scoped и те же родительские
     Singleton — это и есть модель рестарта забега.
 10. Transient отдаёт новый объект на каждый Resolve, и Dispose ему не
     вызывается никогда.
 11. Объект из RegisterInstance тоже не получает Dispose никогда.

Регистрации:
 12. Две отдельные регистрации одного класса роняют построение контейнера:
     System.ArgumentException «An item with the same key has already been
     added. Key: (Тип, )». Падает внутри Awake скоупа.
 13. Две РАЗНЫЕ реализации под одним интерфейсом собираются молча: Resolve
     отдаёт последнюю зарегистрированную, IReadOnlyList<T> отдаёт обе.
 14. Попытка достать регистрацию дочернего скоупа из родительского —
     VContainerException.

Запуск и корень:
 15. Сцена, где лежит только дочерний скоуп, при назначенном
     VContainerSettings.RootLifetimeScope запускается: префаб корня
     инстанцируется в DontDestroyOnLoad, дочерний скоуп находит его
     родителем, зависимости резолвятся.
 16. Без назначенного префаба та же сцена даёт VContainerException
     «No such registration of type: ...» — осиротевший скоуп строится как
     собственный корень. Не NullReferenceException.
 17. При DisableDomainReload VContainer работает корректно во втором и
     третьем прогоне Play подряд; ломается только собственное
     static-состояние.

Сборки и компиляция:
 18. Модули UnityEditor.* автоматически подключаются к EDITOR-компиляции
     любой сборки и отсутствуют в PLAYER-компиляции. Редакторный using
     в runtime-сборке ловится только сборкой билда.
 19. Precompiled-dll вне asmdef (NuGet-пакеты в Assets/Packages) видны всем
     сборкам проекта напрямую, минуя список ссылок asmdef.
 20. Unity генерирует .csproj только для сборок, содержащих хотя бы один
     скрипт (подтверждает errata к уроку 01: пустые asmdef в решении не
     видны).

Unity, попутно:
 21. Класс MonoBehaviour, чьё имя не совпадает с именем файла, не получает
     ссылки на скрипт при сохранении в сцену или префаб: m_Script: {fileID: 0},
     компонент становится Missing. Один MonoBehaviour — один одноимённый файл.
 22. Play Mode не крутит кадры, когда редактор не в фокусе, а
     Application.runInBackground = false. Для любых замеров через MCP это
     нужно учитывать, иначе кажется, что игра зависла на первом кадре.
 23. Приватное поле с [SerializeField], которое нигде не читается,
     предупреждения компилятора не даёт.
