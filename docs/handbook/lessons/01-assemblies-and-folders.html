01 · Сборки, папки, корень namespace

шаг 1 роадмапа (бутстрап) · блок 0 · 2026-08-19
Доки проекта: ARCHITECTURE.md §2, §14, §15 · CLAUDE.md §5, §7 · журнал решений PROGRESS.md

Почему этот блок первый, а не восьмой: код пишется по ходу шага. Пока нет asmdef, всё падает в Assembly-CSharp. Перенос кода под asmdef позже — это смена имени сборки, а ссылки на MonoBehaviour в сценах и префабах хранятся как пара «GUID скрипта плюс имя сборки». Меняешь сборку — получаешь Missing Script по всему проекту, молча, без единой ошибки в консоли. В этом проекте это, судя по мёртвым DemonSlaughter.*.csproj в корне, уже один раз произошло.

Теория

1.1 Что делает Unity без asmdef

Все скрипты в Assets/ компилируются в одну сборку — Assembly-CSharp.dll (плюс Assembly-CSharp-firstpass для Plugins/ и *-Editor для Editor/). Одна сборка = каждый класс видит каждый класс. Никаких границ не существует физически, только в голове разработчика.

1.2 Что даёт asmdef

Assembly Definition — файл, объявляющий: «папка и всё под ней компилируется в отдельную сборку с таким-то именем и вот такими ссылками». Три следствия:

  • (а) Время компиляции. Правишь файл в Game.Simulation — пересобирается Game.Simulation и то, что на неё ссылается. Game.UI и Game.Meta не трогаются. На старте это экономия секунд, на проекте с сотней систем — минут в день.
  • (б) Граница, которую держит компилятор. Если Game.Simulation не ссылается на Game.View, то using Game.View — ошибка компиляции. Не замечание на ревью, не «надо бы почистить». Ошибка сборки. Код ошибки зависит от того, существует ли корень имени: если целиком неизвестно (using VContainer) — это CS0246, а если известен только корень (Game есть, Game.View не видна) — CS0234. Разница чисто диагностическая, границу держат обе.
  • (в) Явный, читаемый граф зависимостей. Открыл asmdef — увидел, от чего зависит слой. Без него граф существует только как сумма всех using в проекте, и никто его не знает целиком.

Пункт (б) — единственная причина, по которой asmdef обязателен здесь. ARCHITECTURE.md §2 говорит «зависимости только вниз». Правило, не подкреплённое компилятором, — это пожелание. Пожелания протекают в два часа ночи, когда до починки бага остался один using.

1.3 Альтернативы и почему они хуже

  • Только namespace-конвенция плюс самодисциплина. Работает ровно до первого аврала. В соло-разработке ревьюера, который поймает нарушение, не существует.
  • Внешние анализаторы (NDepend, кастомные Roslyn-правила). Работает, но это ещё одна инфраструктура, которую надо ставить, настраивать и чинить после апдейта Unity. Asmdef уже в коробке.
  • Одна сборка «пока проект маленький». Соблазнительно и дёшево сегодня. Цена приходит потом: перенос в asmdef на 300 файлах — это разбор циклических зависимостей, которые к тому моменту уже сплелись.

1.4 Обратная сторона

Asmdef превращает циклическую зависимость из «оно как-то работает» в ошибку компиляции всего проекта разом. Это плюс, но означает: направление зависимостей надо задать правильно с первого дня, а не разруливать на ходу.

1.5 Главная теоретическая идея блока: направление зависимости не равно направлению потока данных

Симуляция порождает данные, которые нужны View. Поток данных идёт из Simulation в View. Зависимость за потоком не следует: Game.Simulation не имеет права знать про Game.View. В этом проекте не следует и обратная — Game.View тоже не ссылается на Game.Simulation (ARCHITECTURE.md §15): вьюхи не должны знать про ECS. Оба слоя встречаются на интерфейсе, объявленном в Game.Core: симуляция его вызывает, вьюха реализует.

Когда нижнему слою всё-таки нужно позвать верхний, зависимость инвертируется: интерфейс объявляется на нейтральном уровне (Game.Core), реализация живёт наверху, нижний слой работает с интерфейсом. Это Dependency Inversion, и в блоке 1 (composition root) он же объяснит, почему синглтоны запрещены: синглтон — это способ достать верхний слой из нижнего, минуя всякую инверсию.

Привязка к стеку

2.1 Граф из ARCHITECTURE.md §15 и что в нём не сходится

Заявлено было:

Game.Core         → (нет зависимостей от проекта)
Game.Configs      → Core
Game.Simulation   → Core, Configs
Game.View         → Core, Configs
Game.UI           → Core, Configs

Три дырки, которые пришлось закрыть до создания файлов:

Дырка 1. Слоя Services в §15 не было

В §2 слой Services есть (загрузка, аудио, ввод), в §15 сборки под него нет. InputService, аудио, загрузчик сцен, файловый I/O сейвов — жить им негде.

Решение проекта

Заведена восьмая сборка Game.Services → Core, Configs: Game.Core держит только интерфейсы, Game.Services — реализации. Обоснование и рассмотренные варианты — журнал решений PROGRESS.md, запись от 2026-08-19.

Дырка 2. Game.UI не видит Game.Meta

А HUD обязан показывать валюту, экран меты — ветку перков. Это не ошибка доки, это намеренная жёсткость: связь идёт через интерфейс в Game.Core (например, IMetaProgress), Game.Meta его реализует, Game.UI потребляет. Так же связываются любые два соседа по слою.

Запомнить как правило: соседи не ссылаются друг на друга, соседи встречаются в Core.

Дырка 3. Симуляция и ScriptableObject

Game.Simulation → Game.Configs, а конфиги — это ScriptableObject, то есть UnityEngine.Object. При этом ARCHITECTURE.md §1 говорит «симуляция не знает о Unity». Формально противоречие. Практически решается на границе: Bootstrap читает SO и складывает из них plain-структуры, а системы получают снимок данных, а не ссылку на ассет. Это тема блока 5, но помнить нужно уже сейчас — от неё зависит, ссылается ли Game.Simulation на Game.Configs вообще.

Граница двух DI

Ключевой момент, который и есть граница двух DI из ARCHITECTURE.md:

Game.Simulation ссылается на Leopotam.EcsLite и Leopotam.EcsLite.Di, и НЕ ссылается на VContainer.

Это не стилистика. Пока в Game.Simulation нет ссылки на VContainer, ни одна система физически не может дёрнуть контейнер, объявить VContainer-атрибут инъекции или зарезолвить зависимость на лету. Единственный оставшийся путь передать сервис в систему — тот, что зафиксирован в журнале решений: EcsSystems.Inject() и поля с атрибутами LeoECS Lite DI. Решение из PROGRESS.md становится не договорённостью, а свойством сборки.

DOTween.dll лежит в Assets/Plugins и в .meta не помечен как explicitly referenced — значит доступен всем сборкам автоматически, отдельная настройка precompiledReferences не нужна. Если позже понадобится запретить DOTween в Simulation — это делается флагом overrideReferences на самой Simulation.

2.3 noEngineReferences у Game.Simulation

Был соблазн поставить у Game.Simulation noEngineReferences: true и получить буквальное «симуляция не знает о Unity»: не скомпилируется ничего из UnityEngine.

Что строгий режим даёт реально:

  • Time.deltaTime внутри системы становится невозможен. А это настоящий класс багов: deltaTime обязан приходить в тик снаружи, иначе детерминизм и пауза ломаются молча.
  • UnityEngine.Random внутри симуляции — тот же класс багов.

Что он стоит:

  • Нет Vector2/Vector3, Mathf, Quaternion. Нужен свой математический слой или Unity.Mathematics.
  • Каждый конфиг придётся конвертировать в свои типы, включая позиции.
  • Пакет LeoECS Lite сам по себе engine-free, так что он не мешает — мешает объём ручной работы.
Решение проекта

Выбран noEngineReferences: false. Портируемость симуляции на сервер проекту не нужна, а математический слой — неделя работы в обмен на чистоту, которой никто не воспользуется. Два названных класса багов закрыты дешевле: deltaTime приходит параметром в тик (блок 1 шага 1), рандом — собственным сервисом с фиксируемым сидом, который всё равно нужен для воспроизводимых забегов. Обоснование целиком — журнал решений PROGRESS.md, запись от 2026-08-19.

Практическая граница вместо формальной: Game.Simulation может использовать Vector2/Vector3/Mathf как типы-значения, но не имеет права трогать GameObject, MonoBehaviour, Transform, Time, Physics, SceneManager, Resources. Запрет на GameObject и MonoBehaviour при этом обеспечен не дисциплиной, а тем, что Game.Simulation не видит Game.View.

Скелет API

Здесь скелет — это не сигнатуры классов (классов в блоке нет), а содержимое asmdef. Ниже поля, которые надо заполнить осознанно; остальные оставить по умолчанию.

3.1 Форма файла

{
    "name": "Game.Core",
    "rootNamespace": "Game.Core",
    "references": [],
    "includePlatforms": [],
    "excludePlatforms": [],
    "allowUnsafeCode": false,
    "overrideReferences": false,
    "precompiledReferences": [],
    "autoReferenced": false,
    "defineConstraints": [],
    "versionDefines": [],
    "noEngineReferences": false
}

Про поля, которые важны:

ПолеЧем важно
name Имя сборки. Совпадает с именем файла. После первого коммита не переименовывается никогда — см. подводные камни.
rootNamespace Unity подставит его в шапку каждого нового скрипта в этой папке. Пустое поле = скрипты без namespace = массовая правка через полгода. Заполнять обязательно.
references Ссылки. Unity по умолчанию пишет их как GUID:xxxxxxxx — нечитаемо, но переживает переименование сборок. Оставить как есть, на строковые имена не переключать.
autoReferenced Если true, Assembly-CSharp автоматически видит эту сборку. Assembly-CSharp в проекте не нужен вообще — ставим false во всех восьми. Это ещё и страховка: случайный .cs, забытый вне asmdef, не скомпилируется и сразу себя обнаружит.

  • Корневые DemonSlaughter.*.csproj и Assembly-CSharp*.csproj — мёртвые артефакты, лежат в .gitignore, удаляются вручную после регенерации.

Подводные камни

Симптомы, а не теория.

Переименовал asmdef — компоненты отвалились

Симптом: в сценах и префабах Missing (Mono Script), консоль чистая, код компилируется. Причина: ссылка на скрипт хранится как GUID плюс имя сборки. Вывод: имя asmdef фиксируется один раз. Если менять всё же надо — до того, как хоть один скрипт из неё повешен на префаб.

Циклическая зависимость

Симптом: «Assembly with name X has cyclic references», и не компилируется НИЧЕГО, включая сборки, к циклу не относящиеся. IDE при этом показывает старое состояние и выглядит здоровой — легко потерять полчаса, доверяя ей. Профилактика: порядок создания из 3.3 и правило «соседи встречаются в Core».

Забыл asmdef в новой папке

Симптом: код компилируется и видит вообще всё, границы «работают» ровно до момента, когда обнаружится, что не работают. При autoReferenced: false у всех сборок такой файл, наоборот, сразу упадёт с CS0246 — поэтому false и ставим.

Editor-код в runtime-сборке

Симптом: в редакторе всё зелено, билд падает на UnityEditor. Причина: UnityEditor доступен в Play Mode и недоступен в билде. Всё, что использует UnityEditor, живёт в сборке с includePlatforms: ["Editor"], без исключений. Директива UNITY_EDITOR внутри runtime-сборки — рабочий, но грязный обход; для инспекторов и валидаторов нужна именно Editor-сборка.

Ссылка на пакет по имени пакета

Симптом: в списке references нужного не находится. Причина: искать надо Leopotam.EcsLite, а не com.leopotam.ecslite. Имя сборки не равно имени пакета.

rootNamespace пустой

Симптом: через месяц половина файлов без namespace, а исправление — массовое переименование, ломающее ссылки на MonoBehaviour (см. первый пункт). Заполнять сразу.

Смена apiCompatibilityLevel или платформы после создания сборок

Симптом: часть сборок собирается, часть — нет. В проекте .NET Standard 2.1, NuGet-пакеты (R3 и его зависимости) собраны под него. Уровень не трогать.

Пустая сборка не видна в IDE

asmdef без единого .cs — не ошибка: он компилируется в пустую dll, предупреждений нет, скелет папок можно создать целиком заранее. Но Unity генерирует .csproj только для сборок, в которых есть хотя бы один скрипт, и в решение (.sln/.slnx) попадают только сгенерированные проекты.

Симптом: открыл решение — сборок проекта в нём нет вообще; создал первый скрипт — он не принадлежит ни одному проекту, using на соседний слой подчёркнут красным, автодополнение пустое. Выглядит как сломанные asmdef, хотя asmdef в порядке и Unity компилирует без единой ошибки.

Следствие, важное на практике: пока сборка пуста, IDE про неё не знает, и проверять границы по красным подчёркиваниям бесполезно. Источник правды — консоль Unity, а не редактор. Сборка появится в решении сама, как только в ней окажется первый настоящий файл.

Рядом живёт вторая ловушка того же рода: .csproj и .sln от прошлых состояний проекта не удаляются автоматически. Осиротевший файл решения со старым именем проекта открывается пустым — и это тоже читается как «asmdef не работают».

Чек-лист приёмки

  • В Assets/_Project есть восемь папок по §14 и восемь asmdef по §15.
  • У всех восьми заполнен rootNamespace вида Game.<Layer>.
  • У всех восьми autoReferenced: false.
  • Проект компилируется, консоль чистая.
  • Assets/_Project/Develop удалён.
  • Осиротевшие .csproj и .sln от прошлых состояний проекта удалены вручную — Unity их не убирает. Game.*.csproj при этом появятся не сразу: проект генерируется только для сборки, в которой есть хотя бы один скрипт (см. «Пустая сборка не видна в IDE»).
  • Главная проверка: временный файл в Assets/_Project/Simulation со строкой using Game.View даёт CS0234 («View does not exist in the namespace Game»). После проверки файл удалить. Без этого шага блок не принят — всё остальное можно сделать правильно на вид и ошибиться в ссылках.
  • Обратная сторона: using Game.Simulation из файла в Assets/_Project/View тоже даёт CS0234. View и Simulation — соседи, прямой ссылки между ними нет ни в одну сторону; связь пойдёт через интерфейс в Game.Core (см. 1.5 и 2.1).
  • Проверка, что ссылки вообще расставлены, а не забыты все разом: using Game.Core из файла в Assets/_Project/View компилируется. Важно: namespace существует только если его кто-то объявил — пока Game.Core пуста, этот using тоже упадёт, и упадёт по другой причине. Значит в пробнике для Core должен лежать хоть один тип.
  • В Game.Simulation.asmdef в references отсутствует VContainer.
  • using VContainer в файле внутри Simulation даёт CS0246 — здесь именно 246, потому что корня VContainer компилятор не знает вовсе.
  • Отдельно, вне сборок: manifest.json содержит семь запиненных SHA, Unity переоткрыт, Package Manager не показывает изменений и не тянет ничего заново.
