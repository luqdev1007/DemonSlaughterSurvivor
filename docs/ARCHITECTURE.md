# ARCHITECTURE.md

Правила архитектуры. Обновляется при появлении нового слоя, системы или паттерна. Держать коротким — иначе перестанет обновляться.

---

## 1. Принципы

1. **Симуляция не знает о Unity.** ECS оперирует данными. Вьюхи — тупые отображатели.
2. **Один владелец у каждого объекта.** Непонятно, кто создал и кто уничтожит — архитектура сломана.
3. **Данные отдельно от поведения.** Компоненты — только поля, системы — только логика.
4. **Конфиги — не код.** Всё балансируемое живёт в ScriptableObject.
5. **Детерминированный порядок.** Порядок систем задан явно и читается сверху вниз.
6. **Ничто про игрока не хардкодится.** Игрок — сущность, собираемая из `CharacterConfig`.
7. **Расширяемость важнее лаконичности.** Планируются пострелизные обновления: новый персонаж, способность, перк или предмет должны добавляться данными и набором компонентов, без правки боевых систем. Если новый контент требует правки системы — модель спроектирована плохо.

## 2. Слои

```
┌──────────────────────────────────────────┐
│ Bootstrap        точка входа, скоупы DI  │
├──────────────────────────────────────────┤
│ UI / Meta        экраны, сейвы, прокачка │  ← VContainer, R3, UniTask, DOTween
├──────────────────────────────────────────┤
│ Services         загрузка, аудио, ввод   │  ← VContainer, Input System
├══════════════════════════════════════════┤  ← ГРАНИЦА
│ Simulation       ECS: компоненты/системы │  ← LeoECS Lite, без Unity API
├──────────────────────────────────────────┤
│ View             вьюхи, пулы, VFX        │  ← MonoBehaviour, DOTween
└──────────────────────────────────────────┘
```

Зависимости только вниз. `Simulation` не ссылается на `UI`, `View` не ссылается на `Services`.

## 3. Граница ECS

**В ECS:** игрок, враги, снаряды, установленные объекты, пикапы; здоровье, урон, скорость, кулдауны, опыт; спавн, ИИ, движение, коллизии, урон, способности; состояние забега.

**Вне ECS:** загрузка сцен и ресурсов; сейв/лоад, мета, инвентарь; UI и его стейт; аудио, настройки, локализация; считывание сырого ввода.

**Игрок — сущность ECS**, без исключений.

**Вьюхи — не сущности.** У сущности компонент `View` со ссылкой на `IView` — интерфейс из `Game.Core`, за которым стоит `MonoBehaviour` вьюхи. Симуляция отдаёт вьюхе **целевую** позицию раз в тик (группа 12), а что рисовать в конкретном кадре, решает сама вьюха. Прямой записи в `Transform` из системы больше нет: тик идёт 60 раз в секунду, кадров при 148 fps втрое больше, и 68.5% из них не выполняют ни одного тика — без интерполяции внутри вьюхи картинка идёт ступенями по 16.7 мс, и как только за игроком поедет камера, ступенями пойдёт весь кадр, а не один силуэт.

**Поворот вьюхи не интерполируется.** Он берётся из `Facing`, а `Facing` уже ограничен угловой скоростью в симуляции (§6) — то есть меняется малыми шагами, а не скачками. Ступень поворота видна несравнимо слабее ступени позиции: за позицией едет камера и вместе с ней весь кадр, за поворотом — только силуэт персонажа. **Условие пересмотра:** появление мгновенных разворотов (телепорт, отбрасывание, смена цели рывка).

**Фидбэк — методы `IView`, которые зовёт группа 12** (2026-09-25, блок 6 шага 4). `PlayHit`, `SetInvulnerable`, `PlayDeath`, `Dissolve`: симуляция говорит *что* случилось, вьюха решает *как* это выглядит. Вспышка удара — `MaterialPropertyBlock` по **применённому** урону (`ApplyDamageSystem` метит выбранное событие тегом `DamageApplied`), игроку не играется, сегодня выключена данными. Мигание — включение рендереров. Смерть врага — триггер `Death` аниматора; смерть героя — `Dissolve()`, явно, только из `PlayDeathFeedbackSystem` с фильтром `Player`: подмена материалов копиями шаблона на шейдере `Game/Dissolve`, копии делает пул один раз на исходный материал. Тайминги и числа — `FeedbackConfig` (`feedback.default`), ссылка из `LevelConfig`. `PlayHitFeedbackSystem` разворачивает цель через `EcsPackedEntity.Unpack` — враг, убитый этим же ударом, к группе 12 уже удалён, и вспышка для него молча пропускается.

**Откуда пришёл смертельный удар.** Каждый источник урона обязан заполнить `DamageEvent.SourcePosition` в момент рождения события — позицию, а не ссылку: источник (снаряд шага 5) может не дожить до группы 9. `ApplyDamageSystem` на ударе, после которого HP стало ≤ 0, копирует её в `KillingBlow { SourcePosition }` на цели. Это единственное место, где смерть узнаёт о своей причине.

**Смерть врага доигрывает отвязанная вьюха.** `ReapDeadEnemiesSystem` удаляет сущность в тике смерти, как и раньше, а вьюху отдаёт не в `Release`, а в `IViewFactory.Retire(view, seconds, direction)`: направление — от `KillingBlow.SourcePosition` к врагу, без `KillingBlow` — нулевое. Пул добавляет к нему случайный разброс силы и угла, запускает клип смерти и отлёт (баллистика во вьюхе, пол y = 0, трение) и возвращает вьюху на полку сам, когда она отыграла. Симуляция о вьюхе после этого не знает ничего — труп в мире не живёт.

**HUD — вне ECS, связь через `IPlayerVitalsSink`** (интерфейс в `Game.Core`). `PublishPlayerVitalsSystem` (группа 12) кладёт HP раз в тик; реализация `PlayerVitals` в `Game.UI` держит два `ReactiveProperty` R3, которые гасят повторные значения, и `HudPresenter` перерисовывает полосу только на смене. Подписок R3 в симуляции нет: система видит интерфейс с одним методом.

**Камера — вне ECS.** Ни компонента, ни системы: камера ничего не решает в симуляции. Владеет ею `ICameraService` — интерфейс в `Game.Core`, реализация в `Game.View`, регистрация `Lifetime.Scoped` в скоупе забега. Риг создаётся из префаба в конструкторе сервиса и уничтожается в `Dispose`, то есть у объекта один владелец и время жизни ровно в забег. Ни `Camera.main`, ни `GameObject.Find`, ни `RegisterComponentInHierarchy` — сценовых камер в аренах нет вовсе. Единственная связь с ECS — передача цели: `Transform` вьюхи игрока, которая появляется только внутри симуляции, уже после сборки скоупа.

## 4. Реестр контента и стабильные ID

Пострелизные обновления делают это обязательным, а не желательным.

- У каждой единицы контента — **строковый ID, зафиксированный навсегда**: персонажи, способности, оружие, перки, предметы, апгрейды, уровни.
- ID не равен имени ассета и не зависит от порядка в списках.
- `ContentRegistry`: ID → конфиг. Сейвы, дроп-таблицы и мета ссылаются на ID, а не на объекты.
- Переименование ассета или перестановка в списке **не имеет права ломать сейв**.

Реестр заодно — готовая точка расширения под Addressables, если DLC будет грузиться отдельно.

## 5. Пайплайн статов — единая точка сборки

Источников модификаторов пять: общая ветка меты, персональные перки, предметы, апгрейды забега, временные эффекты. Если каждый правит компоненты напрямую, числа становятся неотлаживаемыми, а UI — невозможным.

```
BaseStat (CharacterConfig)
  → мета: общая ветка
  → мета: персональные перки
  → предметы (4 слота)
  → апгрейды забега
  → временные эффекты (баффы, режим ульты, ауры)
= FinalStat
```

Правила:
- **Порядок применения фиксирован:** сначала все аддитивные модификаторы, затем все мультипликативные. Иначе порядок взятия апгрейдов влияет на результат — классический источник необъяснимых чисел.
- **Пересчёт по событию**, не каждый кадр. Изменился источник — пересобрали финальные статы.
- **Модификатор знает свой источник** — для UI («откуда у меня +40% урона») и для корректного снятия.
- Новый источник подключается в пайплайн, не трогая боевые системы.

**Реализация (с 2026-09-26, шаг 5 блок 2).**

- **Модификатор — сущность** `StatModifier { Target, Stat, Op, Value, SourceId }`, по образцу `DamageEvent`. Добавить или снять его можно только через `Services/StatModifiers` (`Add`, `RemoveBySource`, `MarkDirty`) — единственная точка, как `Invulnerability.Grant`. Ключ модификатора — `(Target, Stat, SourceId)`: повторный `Add` с тем же ключом заменяет, а не удваивает. Повторное взятие апгрейда забега поднимает его уровень, а модификатор с тем же ключом `(Target, Stat, SourceId)` заменяется — `StatModifiers.Add` (решение 2026-10-03).
- **Итоговые компоненты не изменились для читателей.** `MoveSpeed`, `MaxHealth`, `ContactDamage` получили поле `Base`, `DashStats` — `CooldownBase`; рождение пишет базу и итог, пайплайн переписывает итог. Ни одна боевая система не правилась.
- **Формула:** `(base + Σflat) × (1 + Σincreased) × Π(1 + more)` (`StatFormula`). Апгрейды — `Increased`, складываются; временные эффекты (режим ульты, элитки) — `More`, множат. Сама ярость модификатором не является — это ресурс (§7); модификаторы вешает режим ульты. Число балансовое, пересмотр — шаг 7.
- **Пересчёт — `RecomputeStatsSystem`, конец группы 3**, по тегу `StatsDirty`. Тег ставит `StatModifiers`, а также рождение (`SpawnPlayerSystem`, `EnemyFactory`) — поэтому каждый рождённый проходит пересчёт и сторож. Источники из групп 6–11 видны читателям со следующего тика: отставание не больше тика, принято. Модификаторы цели сортируются по `(Stat, SourceId, Op, Value)` вставками, без аллокаций: порядок добавления не влияет на итог даже в последнем бите float (проверено тестом на наборе, где наивная сумма от порядка зависит).
- **`MaxHealth` растёт дельтой, падает обрезкой.** Рост на Δ прибавляет Δ к `Health`, падение обрезает `Health` до нового максимума; мёртвого не лечит. Отсюда же начальное заполнение: +10 от меты при рождении дают 110/110 без особого случая. **Правило: временные эффекты не таргетят `MaxHealth`** — иначе мигающий бафф лечит при каждом появлении.
- **Статы в секундах остаются секундами** (`DashStats.Cooldown`); в тики переводит потребитель в момент старта (§7).
- **Наследование от владельца.** Сущность с `OwnerLink` получает модификаторы владельца по тем статам, компоненты которых несёт сама; грязный владелец делает грязными своих подчинённых. Это шов под оружие (блок 3): «+20% урона оружия» висит на герое и доходит до любого оружия, в том числе взятого позже. Следствие, которое надо помнить: будущий призыв с `MaxHealth` и `OwnerLink` унаследует мета-бонус героя к HP.
- **Мета до забега — `RunContext.StartModifiers`**, неизменяемая копия `StatModifierSpec[]`, её собирает `RunLauncher` (сегодня пустая). `SpawnPlayerSystem` превращает её в модификаторы. Ссылка идёт только вниз, симуляция не видит `Game.Meta`.
- **Уборка — `SweepOrphanModifiersSystem`, группа 13**, перед перестроением индекса: модификатор, чья цель не разворачивается, удаляется.
- **Сторож скорости врага.** Самая быстрая скорость врагов таймлайна выводится **в одной точке** — `EnemyMotionBounds.From` (`WaveTimelineValidator.ResolveMaxMoveSpeed` от `LevelConfig.Waves`, с 2026-09-27); `RunEntryPoint` инжектирует готовый `EnemyMotionBounds`, и системы читают его, а не зовут вывод сами. `DetectContactDamageSystem` строит из него запас запроса (§12), `RecomputeStatsSystem` после пересчёта каждого врага бросает `InvalidOperationException`, если итоговая скорость выше: адрес — id и позиция врага, итог, база, максимум, список модификаторов скорости. Замедление проходит, ускорение сверх таймлайна падает громко.
- **Стат или свойство.** Статы: `MoveSpeed` (герой и враг), `MaxHealth` (герой и враг), `ContactDamage`, `DashCooldown`, `WeaponDamage`, `WeaponCooldown`, `AttackSpeed` (с 2026-09-28, блок 2 шага 6: множитель, база 1, итог обязан быть > 0 — иначе `RecomputeStatsSystem` бросает с адресом и списком модификаторов; оружие наследует модификаторы героя по этим статам), `DamageTaken` (с блока 3 шага 6: множитель получаемого урона на герое, база 1, итог > 0; применяется в `ApplyDamageSystem` **после** выбора сильнейшего события за тик — выбор идёт по сырому `DamageEvent.Amount`, а в `Health` вычитается и в `DamageApplied.Amount` пишется уже умноженное; `DamageEvent` остаётся сырым). Свойства (прямая запись, пайплайн не трогает): `TurnSpeed`, `BodyRadius`, `HitInvulnerability`, остальные числа рывка, `Separation`. `StatId` и `StatOp` — `enum` в `Game.Core` с явными значениями, номера не переиспользуются; таблица заморожена тестом `StatIdTableTests`.

## 6. Ввод

**Поток:** `InputService` (Input System, вне ECS) → системы группы 1 → **намерение на действие** компонентом игрока: `MoveIntent`, `DashRequest`, `UltimateRequest`. Единого компонента `InputState`, который обещала прежняя формулировка, в коде нет и **не заводится, пока нет потребителя** (решение 2026-10-03, журнал `PROGRESS.md`): каждая система читает ровно одно своё намерение, а нажатия доставляет `IInputService` латчами — `ConsumeDashPressed`, `ConsumeUltimatePressed`, сброс `ResetLatches`.

**Устройства.** Геймпад запланирован (ребайндинг и Steam-аудитория, `GDD.md` §10), но сегодня в `GameControls.inputactions` **привязок геймпада нет ни одной, в том числе для движения**, и схем управления нет. Клавиатура: WASD, пробел — рывок, Q — ульта.

Сырой ввод в ECS не читается никогда.

- **Направление задаётся только движением (WASD).** Мышь направление не задаёт.
- **`Facing` — отдельный компонент от `Velocity`.** Игрок отпустил клавиши — скорость нулевая, взгляд сохраняется. Иначе персонаж сбрасывается в дефолтное направление.
- **Поворот идёт с ограниченной угловой скоростью.** `FaceVelocitySystem` доворачивает `Facing` к направлению `Velocity` через `Vector3.RotateTowards` не быстрее `TurnSpeed` градусов в секунду (`CharacterConfig`, стат персонажа). Мгновенный разворот читается как рывок картинки, а на клавиатуре ещё и врёт: клавиши диагонали отпускаются не одновременно, и последние два-три тика движения — кардинальные, отчего взгляд на отпускании «щёлкал» с диагонали на сторону. Ограничение скорости съедает этот хвост.
- **`Facing` — единичный вектор.** Он таким рождается (`Vector3.forward` при спавне), а `RotateTowards` с нулевым изменением длины его таким и оставляет — длина `Velocity` в `Facing` больше не протекает. `StartDashSystem` всё равно нормализует при чтении: страховка стоит один sqrt на рывок.
- **Угол камеры — общие данные уровня, а не два независимых числа.** `LevelConfig.CameraYaw` читают двое: `ReadMoveInputSystem`, чтобы спроецировать ввод, и `ICameraService`, чтобы поставить камеру. Пока камеру ставили руками в сцене, совпадение держалось на договорённости; разъехавшись, эти два угла дают симптом «управление ведёт вбок», а искать его будут в движении. Поэтому источник ровно один, и камеры в сценах арен нет — она создаётся из данных. Рядом с углом лежат `CameraPitch` и `CameraDistance`: отдельного `CameraConfig` нет, потому что все три числа описывают одно — посадку камеры над ареной, а арена и есть уровень. Всё остальное (damping, lens, blend) настраивается на префабе рига, а не дублируется в конфиге.
- **Буферизация обязательна.** Нажатие незадолго до конца кулдауна срабатывает при его окончании. Без буфера управление ощущается глухим при технически корректном коде. Окно — **120 мс**, лежит в `InputConfig`, а не в `CharacterConfig`: отзывчивость управления — свойство игры, а не персонажа.
- **Нажатие латчится в сервисе ввода.** Симуляция идёт фиксированным шагом, и при fps выше 60 бывают кадры без единого тика — замерено 68.5% кадров при 148 fps. Признак «нажато в этом кадре», прочитанный из системы, в такой кадр теряется целиком. `IInputService` поднимает флаг по событию `InputAction` и гасит его при потреблении симуляцией (`ConsumeDashPressed`). Буфер-компонент в мире и латч в сервисе решают разные задачи и нужны оба. Сервис ввода живёт в проектном скоупе и переживает забег, поэтому латч сбрасывается на старте забега (`ResetLatches`) — иначе нажатие в меню срабатывает первым тиком следующего забега.

## 7. Способности

Три активных слота: **рывок · ульта · артефакт**. Все три — частные случаи одной модели.

`AbilityDefinition` **не содержит логику** — он указывает набор компонентов-эффектов:

| Способность | Композиция |
|---|---|
| Рывок берсерка | `Dash(Forward)` + `Invulnerable` + `PushAway` |
| Телепорт мага | `Blink(Forward)` + `Invulnerable` |
| Кульбит рейнджера | `Dash(Backward)` + `Invulnerable` |

Эффекты переиспользуются между способностями и персонажами. Новая способность = конфиг + комбинация существующих эффектов; новый эффект добавляется, только когда его действительно нет.

**Направление — параметр, а не константа.** `Forward` / `Backward` / `Self` / `TargetPoint`. Захардкоженное «по взгляду» сломается на кульбите рейнджера.

**Длительность способности живёт в тиках, не в секундах.** Симуляция идёт фиксированным шагом, и способность длится целое число тиков. Секунды из конфига переводятся в тики округлением **в момент старта**, а производные величины (скорость рывка) считаются уже из округлённой длительности — иначе пройденная дистанция квантуется шагом и врёт на конфигах, не кратных 1/60. Число в конфиге — заявка, фактическая длительность — ближайшее кратное шагу.

**Неуязвимость — один механизм.** I-frames от рывка и i-frames после получения урона — один компонент, не два параллельных. С 2026-09-24 выдающих двое (`StartDashSystem` и `ApplyDamageSystem`), поэтому правило слияния — **по максимуму** — живёт в одном месте (`Services/Invulnerability`), а не копируется: сумма дала бы бессмертие на цепочке рывков, перезапись позволила бы короткому источнику срезать длинный.

**Источник, выдающий `Invulnerable` до группы 9, прибавляет один тик к желаемой длительности защиты** (`Invulnerability.TicksSpentBeforeDamage`, с 2026-09-26). `TickInvulnerabilitySystem` списывает тик в группе 9 **до** `ApplyDamageSystem`, поэтому выданное в группе 2 уже в этом же тике теряет единицу, и N выданных тиков защищают N − 1. Источники, выдающие неуязвимость в самой группе 9 после тикера (удар в `ApplyDamageSystem`), это не касается: их первый списанный тик — следующий. Сегодня правило применяет `StartDashSystem`. На него же обязан опереться артефакт. Регрессионный тест — `DashInvulnerabilityTests`.

**Композиция эффектов сегодня хардкод, а не данные.** Рывок берсерка — это `Dash(Forward)` + `Invulnerable` + `PushAway`, и все три эффекта уже существуют компонентами и системами, но связывает их код, а не `AbilityDefinition`. Прежняя формулировка «исполняющие системы не изменятся» **неверна по коду** (разведка 035): неуязвимость рывка зашита внутри `StartDashSystem` — выдаётся всегда, а толчок срабатывает у любого `Player` с `Dashing` (фильтр `SweepDashPushSystem`). Вынести их в данные, не тронув эти две системы, нельзя.

**Решение шага 6 — общего `AbilityDefinition` нет** (2026-09-28, отменяет прежнее «каркас минимальный: слот, условие, вид эффекта»). У рывка и ульты общие только слот и условие, а исполняют их разные системы; обёртка, которую никто не читает, — абстракция без читателей (журнал 2026-09-06: генерический `AbilityDefinition` сознательно не строился по одному примеру). Каждая способность — свой конфиг (`DashAbilityConfig`, `BerserkAbilityConfig`) и свои системы. Каркас общего `AbilityDefinition` и язык эффектов («список компонентов-эффектов» из таблицы выше) — **вместе с артефактом или вторым персонажем**; таблица остаётся намерением. Параметры неуязвимости рывка живут в `DashAbilityConfig` (секунды — `_invulnerabilitySeconds`, там с шага 4); сам факт выдачи остаётся в `StartDashSystem`, флага «даёт неуязвимость» нет — нет второго потребителя (журнал 2026-09-28); толчок остаётся привязан к рывку.

**Ресурсы ульты** — общий компонент `UltimateCharge` и разные системы-накопители на персонажа. **Ярость — это ресурс, а не модификатор**: она лежит в `UltimateCharge { Value, Max }`, и её читают двое — перки шага 7 (по уровню: низкая / высокая ярость) и ульта (по порогу: включение только при `Value == Max`). Эффекты режима ульты — **временные модификаторы через пайплайн** (§5) с `SourceId` `ult.berserk`, снимаются `RemoveBySource` по окончании; правило «временные эффекты не таргетят `MaxHealth`» действует и для них. Во время режима ярость заморожена на максимуме. Цена режима — `DamageTaken` (§5): стат героя, множитель получаемого урона.

| Персонаж | Ресурс | Накопление | Поощряет |
|---|---|---|---|
| Берсерк | Ярость | Нанесённый (плоско за попадание) и полученный (долей `MaxHealth`) урон; спад после паузы без урона, на максимуме не спадает | Не выходить из боя |
| Рейнджер | Сосредоточенность | Время без получения урона | Чистую игру |
| Маг | Заряд с элиток | Подбор дропа с элитных врагов | Приоритет целей |

**Зависимость:** ресурс мага завязан на спавн элиток — спавнер обязан гарантировать их появление по таймеру, иначе персонаж остаётся без ульты не по своей вине. Это требование к системе спавна.

**Артефакт** — предмет, дающий способность. То есть предмет обязан уметь предоставлять поведение, а не только модификаторы статов.

## 8. Атаки: наведение и жизненный цикл

**Наведение** — параметр оружия/способности: по взгляду · ближайший враг · вокруг себя · установка в точке.

**Жизненный цикл** различается принципиально и не сводится к «нанести урон»:

| Тип | Пример | Живёт | Ключевые компоненты |
|---|---|---|---|
| Взмах | меч берсерка | замах + окно по запечённому клинку, в тиках клипа | `Swing`, `SwingBake` |
| Снаряд | болт арбалетчика | до попадания или дальности, в тиках | `Projectile` |
| Аура | выжигающее поле | пока активна, следует за владельцем | `AttachedTo`, `TickInterval` |
| Установленный | ловушка, кольцо льда | сам по себе | `Placed`, `TriggerCondition`, `Lifetime` |

Установленные объекты — **самостоятельные сущности**: своя позиция, своё владение. Отдельной регистрации в spatial hash нет: индекс берёт любую сущность с `Position`, кроме помеченных тегом `NotIndexed` (`RebuildSpatialGridSystem`, `Exc<NotIndexed>`, с 2026-10-10), а потребители отсекают чужие по своим компонентам. Обязательно решить, что с ними происходит при смерти владельца и при завершении забега. **Первый реализованный установленный объект — сегмент огненного шлейфа** (с 2026-10-04, шаг 7 блок 6): `FireSegment { Owner, RemainingTicks, DamageScale }` + `Position` + `View`, **исключён из индекса** (тег `NotIndexed`) — он сам ищет врагов запросом к индексу раз в импульс, а в индексе его никто не ищет, и 78+ сегментов только удлиняли бы перестроение; смерть владельца — сегменты доживают срок; конец забега — `ViewPool.Dispose` уничтожает вьюхи вместе с миром.

**Первый снаряд — болт арбалетчика** (с 2026-10-10, шаг 7, внеплановый блок; отчёт 047). Дальняя атака врага — `RangedAttackConfig` (`ContentConfig`, ссылка из `EnemyConfig._rangedAttack`), на враге `RangedAttack { Config, CooldownTicks, WindupTicks, PlaybackSpeed, IsHolding }`. Враг стоит (намерение 0), пока идёт замах или живой герой в радиусе; замах — коммит: уход героя из радиуса и толчок его не отменяют, смерть врага отменяет (сущность удаляется в тике смерти). Выстрел — на тике конца замаха, в позицию героя этого тика, без упреждения; кулдаун от выстрела. Болт — `Projectile { Source, LastPosition, Damage, Radius, RemainingTicks }` + `Position`, `Velocity`, `Facing`, `View`, `NotIndexed`; летит через `MoveSystem`, дальность в тиках. **Попадание — только по герою** и по ближайшему сближению двух равномерных движений за тик (болт `LastPosition → Position`, герой `PreviousPosition → Position`), поэтому рывок (до 1.141 м за тик) сквозь болт не проскакивает. Сквозь врагов и труп героя болт летит. Событие — `DamageKind.Projectile`, `Source` — стрелок, `SourcePosition` — болт; ярость копит как полученный урон. Скорость проигрывания замаха — `ReleaseClipSeconds / (тики замаха × dt)`: спуск в клипе совпадает с тиком выстрела (замерено, 0 тиков).

Заложить только «мгновенный + снаряд» нельзя — ауры и ловушки заявлены в дизайне и приедут костылями.

**Взмах по запечённому клинку** (с 2026-09-27, шаг 5 блок 3). Оружие — сущность, подчинённая герою (`OwnerLink`), со статами `WeaponDamage` и `WeaponCooldown`. Инструмент `Game/Bake Weapon Swings` (сборка `Game.Configs.Editor`) сэмплирует клип удара на риге героя с частотой 240 Гц по времени клипа и кладёт отрезок «кисть → острие» в координатах корня в `SwingBake`; окно удара, половина углового диапазона и скорость проигрывания — данные варианта в `WeaponConfig`. Удар стартует (`StartSwingSystem`, группа 6), когда кулдаун готов, герой не мёртв и не в рывке, а враг стоит в секторе срабатывания — пересечении покрытий всех вариантов, которое пишет инструмент; вариант тянется из собственного потока случайности оружия (`SimulationRandom.StreamState` от сида забега и стабильного хеша ID оружия). `AdvanceSwingSystem` (группа 7) каждый тик заметает клинок от прошлого тика к текущему подшагами запекания, обрезает его по `BodyHeight` врага и передней полусферой (`±90°`), и даёт одно попадание на врага за взмах; `Source` — герой. Кулдаун идёт от начала удара, и новый удар не стартует, пока жив прежний: период — `max(кулдаун ÷ AttackSpeed, длительность удара)`. **Скорость атаки** (с 2026-09-28, блок 2 шага 6): на старте удара `StartSwingSystem` пишет в `Swing` снимок — длительность `round(длина клипа ÷ (скорость варианта × AttackSpeed) ÷ dt)` тиков, не меньше одного, и скорость проигрывания, выведенную из этих тиков (`длина ÷ (тики × dt)`), по правилу §7; `AdvanceSwingSystem` и аниматор (`PlayAttack`) берут скорость из снимка, поэтому модификатор посреди удара действует со следующего. Потолок: буфер подшагов `AdvanceSwingSystem` — 64 отрезка за тик, то есть `4 × скорость варианта × AttackSpeed ≤ 63`; сверх — громкое исключение `SwingSweep`. **Стоящий герой наводится сам** (с 2026-09-27, блок 4): `FaceNearestEnemySystem` доворачивает `Facing` героя без ввода и без скорости к ближайшему врагу в пределах дальности сектора срабатывания, кроме рывка, смерти и взмаха; движущимся героем взгляд по-прежнему владеет движение. Вариантов в пуле два — `LeftSlash` и `RightSlash` (`Spin` удалён 2026-09-27). Рывок и смерть обрывают взмах. **Взмах несёт свои данные** (с 2026-10-04, шаг 7 блок 3): `Swing` хранит сам `SwingVariant`, долю урона `DamageScale` и вид урона `Kind`; `Weapon` — источник `WeaponDamage`, который читается вживую. **Особая атака** — маркер `SpecialAttack { Attack, LocksMovement }` на герое: пока он есть, оружие не стартует, его взмах обрывается (взмах с тегом `SpecialSwing` — нет), `Facing` не трогают ни `FaceVelocitySystem`, ни `FaceNearestEnemySystem`, ходьба обнуляется только при `LocksMovement`; маркер снимает `ExpireSpecialAttackSystem`, когда сущности атаки больше нет (конец, рывок, смерть). Второй потребитель — героический прыжок (с 2026-10-04): своя сущность `HeroicLeap` (не `Swing`), приземление на тике, запечённом из клипа (`LeapBaker`: носки ниже 0.05 м после отрыва), урон по сектору от `Facing` и толчок от точки (`PushFromPoint`, перезаписывает `Pushed`); запас запроса индекса по толчку — максимум источников в `EnemyMotionBounds.From`. Поведение перка — наследник `PerkBehaviourConfig` (`LevelCount`, `Validate`) в поле `PerkConfig._behaviour`, поиск — `TakenBehaviourLookup.TryFind<T>`. Первый потребитель — контрудар: `Spin` из `CounterStrikeConfig` (ссылка из `PerkConfig`), слой аниматора `Spin` над `Attack` (полная маска, `Override`), параметр `IsSpecial` уводит `Attack` в `Empty`. **Вид урона** — `DamageEvent.Kind` (`Unmarked` = 0 по умолчанию, `Weapon`, `Contact`, `Perk`); ярость копит только `Weapon` и `Contact`. **Урон по врагу** применяется каждым событием тика (`KillingBlow` — от добившего, события после него пропускаются); правило «сильнейшее событие за тик» осталось только для героя. **Дальность ближнего оружия — геометрия запечённого клинка, а не стат**; будущее «+дальность» для меча — отдельное решение, растягивание запечённой геометрии разойдётся с картинкой. Вьюха: слой `Attack` в `Berserk.controller` с маской «верх тела + `Hips`» играет удар поверх бега. Клинок на экране совпадает с **клипом** до 0.0000 м на скоростях ×1, ×1.5, ×2; **запечённый** клинок отличается от него не больше чем на 0.0027 м на отсчёте 240 Гц и до 0.0255 м между отсчётами — это линейная интерполяция `SwingBake.SampleAt` на быстрой части дуги, меньше шага сетки покрытия (замер, отчёт 037 §4.1; прежнее «с запечённым до 0.0000 м» из отчёта 033 этим методом не воспроизвелось).

## 9. Персонажи, режимы, время жизни забега

**`CharacterConfig`:** ID, базовые статы, стартовое оружие, три способности, одно правило-модификатор, слоты предметов.

**`RunContext`** — параметры забега: режим, персонаж, источник уровня, условие победы, правила меты. Создаётся до запуска симуляции; системы читают его, а не глобальное состояние. Ссылки на контент внутри — **только стабильные строковые ID** (§4), не прямые ссылки на конфиги: иначе `RunContext` нельзя объявить в нейтральном `Game.Core`.

Стори-мод и бесконечный режим — два `RunContext`, а не две ветки кода.

**Два уровня корня композиции.** Проектный корень живёт всё приложение: сервисы, `ContentRegistry`, мета и сейвы (§16), настройки — регистрации `Lifetime.Singleton`. Корень забега живёт ровно один забег: `RunContext`, `EcsWorld` и `EcsSystems`, сервисы симуляции (§12), вьюхи, пулы, HUD — регистрации `Lifetime.Scoped`. Рестарт забега — это разбор корня забега и создание нового; проектный корень при этом не трогается и о рестарте не знает, поэтому валюта и мета переживают смерть игрока сами собой, без кода сохранения состояния.

**Ссылка допустима только вниз**, от забега к проекту. Проектный объект не имеет права держать ссылку на объект уровня забега — итог забега уходит в мету копией данных, а не ссылкой на живой объект. Нарушение этого правила даёт ссылку на разобранный мир и проявляется на втором забеге, а не на первом.

## 10. Порядок систем

Новая система добавляется в существующую группу, а не в конец списка.

```
1.  Input          — ввод → намерения (MoveIntent, запросы действий)
2.  Abilities      — кулдауны, заряды, активация способностей
3.  Spawn          — таймлайн волн, гарантия элиток, мини-босс; последним — пересчёт статов
4.  AI             — выбор цели, желаемое направление
5.  Movement       — скорости, Facing, интегрирование позиции
6.  Weapons        — кулдауны автоатак, создание атак
7.  AttackLifetime — снаряды, ауры, установленные объекты
8.  Collision      — пересечения через spatial hash
9.  Damage         — неуязвимость, применение урона
10. Death          — смерти, дроп, валюта, удаление погибших
11. Progression    — опыт, уровни, выбор апгрейда, заряд ульты
12. ViewSync       — перенос состояния во вьюхи
13. Cleanup        — удаление one-frame компонентов, уборка осиротевших модификаторов, перестроение spatial hash
```

`AI` пишет `MoveIntent`, и порядок внутри группы — цепочка: выбор цели (`AcquireChaseTargetSystem`) → намерение к цели (`ChaseTargetSystem`) → остановка дальнего врага (`HoldForRangedAttackSystem`, с 2026-10-10: обнуляет намерение, пока замах или герой в радиусе) → подмешивание разделения толпы (`SeparateNeighborsSystem`; нулевое намерение оно не сдвигает). Разделение стоит **последним**: оно правит уже готовое намерение, и любой писатель `MoveIntent` после него затёр бы результат.

`Abilities` до `Movement` — рывок должен успеть изменить скорость в том же кадре.

Внутри `Movement` порядок тоже цепочка: запоминание позиции до шага (`StorePreviousPositionSystem`) → скорость рывка и скорость ходьбы (`ApplyDashVelocitySystem`, `ApplyMoveSpeedSystem`, взаимно исключающие по `Dashing`, а с 2026-09-24 ещё и по `Pushed`) → `Facing` (`FaceVelocitySystem`, затем `FaceNearestEnemySystem` — только для стоящего героя без ввода, §8, затем `FaceRangedTargetSystem` — стоящий дальний враг к герою, кроме `Pushed`) → отбрасывание (`ApplyPushSystem`, **ставит** скорость, а не прибавляет) → контактная коррекция скорости (`ResolveBodyOverlapSystem`, отброшенных пропускает) → интегрирование позиции (`MoveSystem`). Правило, которое держит эту цепочку без выстрелов: **движением сущности в каждый момент владеет ровно один источник** — ходьба, рывок или толчок, и остальные два в это время её не трогают. **Перестроение индекса из группы 5 ушло в конец группы 13** (2026-09-24, §12): индекс обязан строиться после всех, кто рождает и удаляет сущности, иначе удалённое в группах 6–13 доживает в снимке до следующего тика. **`Position` в тике пишет ровно одна система — `MoveSystem`.** Всё, что должно сдвинуть сущность, выражается через `Velocity` и встаёт до него; следствие для коррекции — `Facing` считается по неисправленной скорости, то есть враг смотрит на игрока даже когда его выталкивает.

**Группа 3 заканчивается `RecomputeStatsSystem`** (§5): после рождения, чтобы рождённый в этом тике шёл дальше с итоговыми статами, и до всех читателей статов (группы 5–12). Источники из групп 6–11 попадают в итог со следующего тика. **В группе 13 `SweepOrphanModifiersSystem` стоит после `CleanupEventsSystem` и перед `RebuildSpatialGridSystem`.** **Оружие** (с 2026-09-27): в группе 3 `EquipStartingWeaponSystem` (только `Init`) рождает оружие героя; в группе 6 — `SpawnFireTrailSystem` (с 2026-10-04: сегменты шлейфа по отрезку `PreviousPosition → Position` тика рывка, после движения группы 5) → `TickWeaponCooldownSystem` → `StartHeroicLeapSystem` (с 2026-10-04: кулдаун прыжка и старт до обрыва, чтобы удар меча оборвался в том же тике) → `InterruptSwingSystem` → `ExpireSpecialAttackSystem` (после обрыва: рывок снимает маркер в том же тике) → `StartSwingSystem` → `ReleaseRangedAttackSystem` (с 2026-10-10: кулдаун и замах дальней атаки, выстрел на нуле замаха) → `StartRangedAttackSystem` (старт замаха; в `Init` — проверка `RangedAttackConfig` всех врагов базы и таймлайна с адресом); в группе 7 — `AdvanceSwingSystem`, затем `AdvanceHeroicLeapSystem` (приземление: урон по сектору и толчок; обрыв смертью и рывком), `PulseFireSegmentsSystem` (импульс шлейфа раз в 0.5 с, один удар на врага за импульс) и `TickFireSegmentsSystem` (срок жизни, возврат вьюхи), затем `AdvanceProjectilesSystem` (попадание болта в героя и дальность; событие болта рождается раньше контактного группы 8, поэтому при равном уроне правило «сильнейшее за тик» оставляет болт) — после движения группы 5, до урона группы 9; в группе 11 первой — `TriggerCounterStrikeSystem` (с 2026-10-04: читает `DamageApplied` по герою этого тика — события живут с группы 9 до группы 13 — и после `MarkDeadSystem`, поэтому погибший не контратакует; рождённый `Spin` метёт с группы 7 следующего тика); в группе 12 — `PlaySwingFeedbackSystem`, `PlayLeapFeedbackSystem`, `PlayRangedAttackFeedbackSystem` и `SyncSpecialAttackViewSystem`; в группе 13 `SweepOrphanOwnedSystem` убирает подчинённых без владельца.

Внутри `Death` порядок: `MarkDeadSystem` (вешает `Dead` и одноразовый `DiedEvent`; игроку ещё обнуляет `MoveIntent`, снимает `DashRequest` и вешает `PendingFinish`) → `TickPendingFinishSystem` → `FinishRunOnPlayerDeathSystem` (зовёт `RunOutcome.Finish`, когда `RemainingTicks <= 0`) → `ReapDeadEnemiesSystem`. Та же идиома «тикер перед потребителем», что у `Invulnerable`, `Pushed`, `DashCooldown`. С шага 7 сразу после `MarkDeadSystem` стоит `DropGemsSystem`: враг с `GemDrop` в тик смерти рождает сферу в своей позиции, до того как `ReapDeadEnemiesSystem` его удалит.

**Сферы опыта** (с 2026-10-03, шаг 7 блок 2) проходят пять групп: 10 — рождение (`DropGemsSystem`); 8 — старт полёта по стату `PickupRadius` героя (`StartGemFlightSystem`, `Exc<GemFlight>`: начатый полёт не перезапускается); 5 — `ApplyGemFlightSystem` после `ApplyPushSystem`, единственный владелец скорости сферы: позиция тика `lerp(старт, герой, (t/T)^k)` через `Velocity` и `MoveSystem`, герой — его позиция на конец прошлого тика; 11 — `CollectGemsSystem` начисляет опыт в тик окончания полёта, `AdvanceLevelSystem` переносит остаток и поднимает `LevelUpEvent.Count` перед `OfferUpgradesSystem`; 12 — `SyncGemViewSystem` (без `Facing`) и `PublishExperienceSystem`. В индекс сферы не попадают (тег `NotIndexed`). Мёртвый игрок стоит, потому что системы ввода исключают `Dead`, а обнулённое намерение больше никто не пишет; `FaceVelocity`, рывок и контактная коррекция `Exc<Dead>` не получали сознательно — труп остаётся препятствием.

**Одноразовые события** — компоненты, создаваемые в кадре и удаляемые в `Cleanup`. Никаких C#-событий и `Action` внутри симуляции.

**Набор выбора апгрейда** (с 2026-10-03, шаг 7) — второй `EcsSystems` на том же мире (`RunSystems.BuildChoice`), вне 13 групп. Пока `UpgradeChoiceGate` закрыт (его закрывает `OfferUpgradesSystem`, группа 11), `RunEntryPoint` не тикает основной набор, держит `Time.timeScale` = 0 и каждый кадр крутит только набор выбора; применённый выбор открывает ворота. Модификаторы, добавленные там, пересчитываются в конце группы 3 следующего тика — то же отставание, что у источников из групп 6–11.

## 11. Модель апгрейдов — компонентная

**Решение принято.** Апгрейд не правит числа, а **добавляет компоненты и включает системы**.

Причина: заявлены апгрейды вроде «второй заряд рывка», «ульта оставляет след», «ловушка срабатывает дважды». Числовая модель их не выражает — потребовались бы флаги-костыли. Плюс пострелизные обновления обязаны добавлять поведение, а не только множители.

Требования к каждому апгрейду:
- **идемпотентность** — взят дважды, поведение предсказуемо;
- **независимость от порядка** взятия;
- **стабильный ID** (см. §4).

**Реализация (с 2026-10-03, шаг 7 блок 1).** Перк — `PerkConfig` с таблицей уровней; взятый перк — сущность `TakenPerk { Owner, PerkId, Level }`. Числовой перк вешает модификаторы через `StatModifiers` с источником = ID перка; смена уровня снимает их по источнику и вешает уровень целиком, поэтому повторное взятие идемпотентно по ключу, а порядок взятия не важен (§5). Поведенческие перки добавят свои компоненты рядом с `TakenPerk`.

## 12. Пространственный индекс

Физика Unity не тянет 500+ агентов с покадровыми запросами. Реализация — `Game.Simulation.Services.SpatialGrid`, перестроение — `RebuildSpatialGridSystem`.

- **Плотный массив, не словарь.** Арена ограничена (`LevelConfig.ArenaRadius`), поэтому индекс — квадрат `[-(R + 2·cell), +(R + 2·cell)]` по обеим осям, нарезанный на ячейки, и одномерный массив длиной `columns × rows` с адресом `row × columns + column`. Упакованный ключ и хеш-таблица нужны миру без границ; здесь границы есть, и словарь платил бы за то, чего нет.
- **Размер ячейки — сериализованное поле `LevelConfig.SpatialCellSize`**, не константа в коде. Сегодня `1.0` — по замеру, не по ориентиру (§18).
- **Индекс перестраивается целиком каждый тик**, **последней системой тика** (конец группы 13) — после всех, кто пишет `Position`, и после всех, кто рождает и удаляет сущности. Инкрементального обновления нет: протухшая запись становится невозможной *по построению*, а не по дисциплине вызывающих. До 2026-09-24 перестроение стояло последним в группе 5, и это оставляло окно: удалённое в группах 6–13 доживало в снимке до следующего перестроения. Цена перестроения измерена отдельной строкой и от переезда не изменилась — 0.1310 мс при 60 живых.
- **В ячейке лежит сырой `int` сущности.** Это безопасно ровно потому, что запись не переживает тик, — и только поэтому. Id удалённой сущности ecslite отдаёт **следующей созданной**, а не переиспользует мгновенно, поэтому у протухшей записи два режима отказа, и оба проверены замером 2026-09-24: **громкий**, когда между удалением и запросом никто не родился (`EcsPool.Get` бросает `Cant touch destroyed entity`, но только в редакторе — проверка под `#if DEBUG`, в билде читается мусор молча), и **тихий**, когда родился: id уже принадлежит чужой живой сущности, и она числится в ячейке покойника. Замерено: новый враг в 0.50 м от игрока при радиусе запроса 0.9 не вернулся запросом вовсе — ни исключения, ни симптома. Позиции в индексе не дублируются — запрос читает пул `Position`.
- **Контракт запроса: `Query(center, radius, candidateSlack, result)`** (с 2026-09-26, шаг 5 блок 1). Обходятся ячейки в квадрате `±rings` вокруг ячейки центра, где `rings = max(1, ceil((radius + candidateSlack) / cellSize))`. Потолка радиуса нет: радиус больше ячейки просто обходит больше колец, а радиус шире сетки обходит её целиком. Точная проверка расстояния — **только по `radius`**, запас влияет лишь на число колец, поэтому урон никогда не пройдёт по тому, до кого не достали. Отрицательные или `NaN` радиус и запас — `ArgumentOutOfRangeException`. Цена растёт квадратично по числу колец: при ячейке 1.0 контактный урон (0.9 + 0.94) обходит 5×5, разделение и коррекция (1.0 и 0.9, запас 0) — 3×3, как раньше. Сверка с перебором, проверка запаса сдвигом кандидатов и мутационная проверка тестов — `Game.Simulation.Tests`, отчёт 031.
- **Координаты вне сетки прижимаются к краевой ячейке, а диапазон обхода — к границам сетки целиком**, не каждая ячейка по отдельности: иначе при нескольких кольцах у края одна краевая ячейка обходилась бы несколько раз и давала дубли (воспроизведено мутацией, отчёт 031). Прижатие безопасно только вместе с точной проверкой расстояния: у границы появляются лишние кандидаты, их отсеивает проверка.
- **Точную проверку расстояния делает индекс, а не потребитель.** Ячейки — грубая фаза; без финальной проверки результат не совпал бы с честным перебором. Сравнение в квадратах, без `Sqrt`.
- **Буфером результата владеет вызывающий**, индекс его только чистит. Списки ячеек создаются один раз при построении и дальше только `Clear()`. Аллокаций в перестроении и в запросе нет.
- **Контракт: индекс описывает мир на конец прошлого тика.** Одно правило на всех потребителей, без исключений по группам — прямое следствие того, что перестроение стоит последним в тике. Следствия, которые обязан учитывать потребитель:
  - **устаревает состав кандидатов, а не их координаты.** В ячейке лежит только `int`, позиции потребитель читает из пула `Position`, то есть актуальные. Ошибка ограничена смещением за один тик: при `MoveSpeed = 2.5` это 4 см;
  - **сущность, рождённая в этом тике, в индексе появится только в его конце.** Первый тик жизни она соседей не видит и соседям не видна, поэтому пачка гарантированного спавна рождается внахлёст и начинает расходиться со второго тика;
  - **потребитель до `MoveSystem` отставания не чувствует вовсе:** `Position` с момента перестроения никто не писал (пишут её только `MoveSystem` и рождение), поэтому состав ячеек точно соответствует позициям, которые он читает. Здесь стоят `SeparateNeighborsSystem` (группа 4) и `ResolveBodyOverlapSystem` (группа 5, до `MoveSystem`) — оба передают запас 0.
- **Запас — свойство вызова, а не ограничение ячейки.** Запрос корректен, пока `candidateSlack` не меньше максимального смещения **кандидата** с момента перестроения. Смещение центра значения не имеет: центр передаётся живой позицией. Потребитель **выводит запас из данных** в `Init` и на каждом тике, констант не ставит. Нарушается молча — потерей кандидата, поэтому формула запаса каждого потребителя записана: `DetectContactDamageSystem` (группа 8) — `max(maxEnemyMoveSpeed·dt + (playerRadius + maxEnemyRadius), pushSpeed·dt)`: ход врага, плюс контактная коррекция `ResolveBodyOverlapSystem`, которая при совпадении позиций сдвигает врага на всю сумму радиусов за тик, либо толчок (отброшенных коррекция пропускает). Сегодня `max(2.5/60 + 0.9, 5/60) = 0.9417`. Прежнее условие `0.9 + 0.042 ≤ 1.0` не учитывало коррекцию и **формально нарушалось** — замерено смещение врага 0.8772 м за тик, — но потерь на живом забеге с 117 рывками не дало ни одной (отчёт 031). Новый потребитель, у которого кандидатом может оказаться **игрок**, обязан учесть рывок: сегодня до 1.141 м за тик — последний тик разгоночного рывка 8 м за 20 тиков (`Dash_Berserk`, сверено с кодом 2026-09-26). Вывод запаса с 2026-09-27 живёт в одном месте — `EnemyMotionBounds` (строится в `RunEntryPoint` рядом с индексом, инжектится в контактный урон, сторож скорости и оружие). Оружие (группа 7, после `MoveSystem`, кандидаты — враги) передаёт тот же запас, а радиус запроса берёт из фактических точек клинка этого тика плюс самый широкий враг.

- **Не в индексе — тег `NotIndexed`** (с 2026-10-10), а не перечень типов в фильтре перестроения: сферы опыта, сегменты шлейфа, болты. Тег ставит рождающая система. Замена `Exc<Gem, FireSegment>` доказана эталоном 045 (отчёт 047).
- **Болт индекс не использует.** Его единственная цель — герой, и `AdvanceProjectilesSystem` перебирает живых героев напрямую (отрезок против отрезка, §8). Запаса запроса здесь нет и не нужно.

Игра логически 2D (движение по плоскости), 3D — только визуал. Сетка двумерная.

**Что придётся решать заново на шаге 5.** Прежняя редакция раздела требовала, чтобы «установленные объекты регистрировались один раз» — это инкрементальное допущение, и оно несовместимо с полным перестроением. Пока установленных объектов не существует, конфликта нет; когда они появятся, выбор между «перестраивать всё» и «держать статический слой отдельно» делается заново.

## 13. Рендер толпы

1. **Этап 1 (сейчас):** префабы + пул. Пул есть с 2026-09-24 (`ViewPool`, блок 4 шага 4) — он же единственный владелец времени жизни вьюх. Хватает до ~150 врагов, и это тот же порог, при котором покадровые `Update` интерполяторов пора менять на менеджер (`CLAUDE.md` §8).

Значит следующий шаг этапа 1 — не код, а облегчение префаба при импорте; этап 2 (отказ от `Animator`) отодвигается за него.

`Game.Simulation` не зависит от `Game.View` и `Game.UI`.

Связать объект, положенный в сцену руками, со скоупом забега нечем: `CreateChild` вешает скоуп забега под проектный корень в `DontDestroyOnLoad`, а `RegisterComponentInHierarchy` ищет в сцене своего скоупа. Это же и шов под пул вьюх шага 4.

**`Game.Editor` — девятая сборка, только для редактора.** `includePlatforms: ["Editor"]`, ноль ссылок на проектные сборки: инструменты редактора не имеют права стать зависимостью рантайма, а рантайм не имеет права о них знать. Отдельная сборка, а не скрипт в `Assembly-CSharp-Editor`, по тому же правилу, что и остальные восемь: забытый вне asmdef скрипт должен падать, а не молча компилироваться.

**`Game.View` дополнительно ссылается на `Unity.Cinemachine`.** Камера — часть слоя вьюх, и Cinemachine не имеет права протечь ни в `Game.Simulation` (там `overrideReferences`), ни в `Game.Core`: наружу торчит только `ICameraService` с `Transform` в сигнатуре.

**Соседи по слою не ссылаются друг на друга.** `Game.UI` не видит `Game.Meta`, `Game.View` не видит `Game.Services`. Связь — через интерфейс, объявленный в `Game.Core`.

**`Game.Simulation` не ссылается на `VContainer`.** Это то, чем граница двух DI держится физически: без ссылки система не может достать контейнер, и единственный оставшийся путь передать в неё сервис — `EcsSystems.Inject()` через LeoECS Lite DI.

**`Game.Simulation` компилируется с `overrideReferences: true` и пустым `precompiledReferences`.** Список ссылок asmdef не управляет precompiled-библиотеками: dll вне asmdef (пакеты NuGet в `Assets/Packages`) автоматически видны всем сборкам проекта. Без этого флага `using R3;` внутри ECS-системы компилируется, и запрет из `CLAUDE.md` §7 держится дисциплиной, а не компилятором.

**Объекты на сцене инжектятся сценовым `LifetimeScope`.** Проектный корень живёт префабом в `DontDestroyOnLoad` и объекты загружаемых сцен не видит. Сцена, которой нужны сервисы, кладёт собственный `LifetimeScope`: родителя ему не указывают — VContainer сам находит корневой скоуп, — а её `MonoBehaviour` регистрируются `RegisterComponentInHierarchy<T>()`, который ищет только в сцене своего скоупа и форсирует резолв при построении контейнера. Значит инъекция происходит до первого кадра, а отсутствующий компонент падает сразу, а не `null`-ом по первому обращению.

**`Game.Configs.Editor` — одиннадцатая сборка, инструмент запекания взмахов** (2026-09-27, шаг 5 блок 3). Editor-only, лежит в `Configs/Editor/`, ссылается на `Game.Configs`, `Game.Core` и `Game.Simulation` (покрытие ударов считается тем же `SwingSweep`, что и попадания). Отдельная сборка, а не `Game.Editor`, чтобы у `Game.Editor` осталось правило «ноль ссылок на проектные сборки». В player-билд не попадает — проверено пробным билдом.

**`Game.Simulation.Tests` — десятая сборка, EditMode-тесты симуляции** (2026-09-26, шаг 5 блок 1). Лежит в `Tests/Simulation/`, а не внутри `Simulation/`: вложенный asmdef забрал бы соседние папки из-под `Game.Simulation` незаметно. `includePlatforms: ["Editor"]` и `defineConstraints: ["UNITY_INCLUDE_TESTS"]` — форма шаблона Test Framework 1.6.0 (его же образцы в `Samples~`). NUnit приходит как precompiled `nunit.framework.dll` из `com.unity.ext.nunit` 2.0.3 с `isExplicitlyReferenced: 0`, то есть без флага он виден всем сборкам без `overrideReferences`; тестовая сборка ставит `overrideReferences: true` и называет его явно. **Граница `Game.Simulation` от этого не меняется:** проверено компиляцией, `using R3;` и `using NUnit.Framework;` внутри неё оба дают `CS0246`. В player-билд сборка не попадает — проверено пробным билдом: в `Managed` семь `Game.*` и ни одной тестовой dll.

**`Game.View.Tests` — EditMode-тесты вьюхи** (2026-10-03, шаг 6 блок 4). Лежит в `Tests/View/`, форма — как у `Game.Simulation.Tests` (`overrideReferences: true`, NUnit явно, `includePlatforms: ["Editor"]`, `UNITY_INCLUDE_TESTS`). Ссылается только на `Game.View` и `Game.Core`; тестовые сборки разделены, чтобы тесты симуляции не видели вьюху. `Game.View` открывает ей `internal` (`Configure`, `ResetFeedback`) через `InternalsVisibleTo` в `View/AssemblyInfo.cs`. Пробным билдом её отсутствие в `Managed` **не проверялось**.

`autoReferenced: false` у всех сборок проекта: `Assembly-CSharp` в проекте не используется, и забытый вне asmdef скрипт должен падать с ошибкой, а не молча компилироваться.

## 17. Выстраданные правила

Правила, полученные не из теории, а из уже сломанного в этом проекте. Баг искался дольше часа и причина оказалась архитектурной — сюда добавляется строка. Самый ценный раздел в долгой перспективе.

Формат: **правило — что происходит при нарушении.**

- **Одно время — один накопитель.** Один и тот же поток времени, накопленный в двух местах, расходится молча, если сбрасывает его только одно из них: `RunEntryPoint.Tick` при переполнении `MaxStepsPerFrame` выбрасывает остаток, а накопитель `ViewInterpolator` об этом не узнаёт и растёт навсегда. **Что происходит при нарушении:** фаза интерполяции залипает на `1.000`, картинка переставляется скачком раз в тик вместо сглаживания — то есть симптом выглядит как «интерполяция не написана», ошибки нет, консоль чиста. Найдено отчётом 017 §9.1, устранено 2026-09-14 (отчёт 022, задача 1): вьюха больше не копит ничего, а берёт фазу от отметки времени последнего `SetPosition` — накопитель этого времени остался один, и расходиться теперь нечему. **Как проверять, что правило соблюдено:** замер фазы обязан показывать разброс, а не одно значение; сверка вьюхи с `Lerp` при фазе `1.000` вырождена и не доказывает ничего.

Как это выглядит в зрелом проекте (для ориентира, из соседнего проекта):
- *Один реактивный флаг — один писатель.* Два писателя дают тихий orphaning: состояние рассинхронизировано, ошибки нет.
- *`Dispose()` стейт-машины обязан звать `Exit()`.* Иначе при жёстком teardown сцены глобальные сервисы остаются грязными.
