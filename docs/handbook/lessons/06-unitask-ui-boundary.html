06 · UniTask на границе UI: ошибка, отмена, повторное нажатие

шаг 2 роадмапа (игрок) · блок 0 · 2026-08-28
Доки проекта: CLAUDE.md §7 (красные линии), §8 (техдолг) · ARCHITECTURE.md §2, §3, §15 · журнал решений PROGRESS.md от 2026-08-21 (кто запускает забег)
Опирается на урок 03 · VContainer и 05 · Fail fast; закрывает риск Р-2 отчёта docs/recons/008
Версии: Unity 6000.4.11f1, UniTask 2.5.11 (коммит e5acc10), VContainer 5103bfc. Всё, помеченное как проверенное, проверялось на этом проекте запуском, вывод консоли приведён дословно.

К концу шага 1 забег умеет стартовать, но запускать его некому: IRunLauncher зовут руками из Play Mode. Этот блок ставит на сцену MainMenu первую кнопку, которая действительно начинает игру, — и на ней вылезает вся асинхронная механика разом. Главная мысль блока: async-метод не бросает исключение в точке вызова. Он кладёт его в возвращённый таск, и если таск никто не ждёт, ошибка перестаёт существовать для того, кто её вызвал. Всё остальное в уроке — следствия.

Теория

1.1 Машина состояний: куда уезжает исключение

Метод, помеченный async, компилятором не компилируется как метод. Компилятор строит из его тела машину состояний: структуру с полем «на каком я шаге», методом MoveNext() и билдером (AsyncUniTaskMethodBuilder), который отвечает за возвращаемый объект. Тело метода превращается в ветки внутри MoveNext(), и всё это целиком обёрнуто в try/catch. Когда изнутри вылетает исключение, билдер вызывает SetException — то есть записывает исключение в возвращённый таск и возвращает управление вызывающему нормально, без броска.

Отсюда неинтуитивное следствие: перед первым await кода тоже нет. Строка, стоящая до всякого ожидания, всё равно живёт внутри машины состояний, а значит её исключение уезжает туда же, в таск. 

// Домен: панель погоды. К проекту отношения не имеет.
private static async UniTask<string> LoadForecastAsync(string cityId)
{
    // Эта проверка — ПЕРВАЯ строка метода, до всякого await.
    // Её исключение всё равно уедет в возвращённый UniTask, а не в место вызова.
    if (string.IsNullOrEmpty(cityId))
        throw new ArgumentException("cityId is empty");

    using (UnityWebRequest request = UnityWebRequest.Get("https://example.invalid/forecast/" + cityId))
    {
        await request.SendWebRequest();
        return request.downloadHandler.text;
    }
}

Проверено на проекте. Две одинаковые по смыслу ошибки — одна брошенная до первого await, вторая после — вели себя одинаково: ни одна не долетела до следующей строки вызывающего. Дословный вывод: 

[SBX] E1a: call FailAfterAwaitAsync and DROP the returned UniTask
[SBX] E1a: the line after the call was reached. No exception at the call site.
[SBX] E1b: call FailBeforeAwaitAsync (throws BEFORE the first await) and DROP it
[SBX] E1b: the line after the call was reached. Still no exception at the call site.
Что это значит для RunLauncher.StartAsync

Первая содержательная строка запуска забега — _content.Get<LevelConfig>(request.LevelId), и она стоит до await _sceneLoader.LoadAsync(...). Урок 05 специально добивался того, чтобы промах по ID падал громко и сразу (05, 1.4). На границе async эта громкость теряется: ContentNotFoundException уезжает в возвращённый UniTask, а вызывающий, если он не пишет await, спокойно идёт дальше. Это риск Р-2 отчёта 008 и единственная причина, по которой урок вообще существует.

1.2 Три способа не дождаться, и все они разные

«Не дождались» — это не одно поведение, а три, и различаются они не стилем, а тем, когда и увидит ли кто-нибудь ошибку. Всё в таблице проверено запуском на UniTask 2.5.11.

Форма вызоваГде всплывает ошибкаКогда
DoAsync(); — таск выброшен в консоли, через финализатор ExceptionHolder либо ExceptionResultSource в неопределимый момент: когда сборщик мусора доберётся до объекта
DoAsync().Forget(); в консоли, через UniTaskScheduler.PublishUnobservedTaskException сразу, в кадре сбоя
await DoAsync(); в try/catch в catch вызывающего сразу, в кадре сбоя

Разница между первой и второй строкой — не косметическая. Forget() это не «намеренно не жду»: это подписка на результат ради того, чтобы ошибку заметить. Внутри он берёт awaiter и вызывает GetResult(), ловит исключение и отдаёт его планировщику. Выброшенный таск не наблюдает никто, и исключение доживает до финализатора.

Насколько «в неопределимый момент» — цифра с этого проекта. Исключение бросалось на 100-й миллисекунде; в консоли оно появилось примерно через четыре секунды, в момент загрузки сцены, потому что загрузка сцены запускает сборку мусора. Стек при этом такой: 

InvalidOperationException: boom-after-await:E1a-dropped-after-await
  Sandbox.SandboxRunner.FailAfterAwaitAsync (System.String label)
  UnityEngine.Debug:LogException(Exception)
  Cysharp.Threading.Tasks.UniTaskScheduler:PublishUnobservedTaskException(Exception)
  Cysharp.Threading.Tasks.ExceptionHolder:Finalize()

Последняя строка — приговор. В стеке нет вызывающего: нет кнопки, нет метода, который начал операцию, нет кадра, в котором это случилось. Есть только Finalize(). Отладка по такому сообщению начинается с нуля.

Почему это хуже, чем «ошибка потерялась совсем»

Совсем потерянная ошибка воспроизводится: сделал то же самое — снова ничего. Ошибка, привязанная к сборке мусора, воспроизводится иногда и всплывает не там. Типичный результат — час, потраченный на поиск причины в загрузке сцены, потому что именно там она напечаталась.

Так не надо — и почему.

// ← НЕТ. Ошибка загрузки прогноза уедет в финализатор.
//   Сломается: пользователь жмёт «обновить», ничего не происходит, консоль молчит.
//   Заметят: через несколько дней, по случайной строке в логе без стека вызова.
private void OnRefreshClicked()
{
    RefreshPanelAsync();
}

// ← НЕТ. async void: исключение уходит в обработчик необработанных исключений
//   среды, мимо UniTask и мимо любого твоего catch.
//   Сломается: ошибка не ловится нигде в твоём коде, отменa неотличима от сбоя.
//   Заметят: когда попытаются написать catch и он не сработает.
private async void OnRefreshClicked()
{
    await RefreshPanelAsync();
}

Так надо.

// Обработчик кнопки синхронный: он только запускает.
// Вся асинхронность — в UniTaskVoid-методе, и Forget() здесь честный:
// внутри метода стоит try/catch, наружу выйти нечему.
private void OnRefreshClicked()
{
    RefreshPanelAsync().Forget();
}

private async UniTaskVoid RefreshPanelAsync()
{
    try
    {
        string json = await LoadForecastAsync(_cityId);
        _label.text = json;
    }
    catch (UnityWebRequestException e)
    {
        _label.text = "Прогноз недоступен";
        Debug.LogWarning("forecast request failed: " + e.Message);
    }
}
UniTaskVoid, а не UniTask

UniTaskVoid — тип «этот таск не предназначен для ожидания». Он не создаёт промис под результат и приучает читателя: раз вернули UniTaskVoid, значит обработка ошибок внутри. Метод, который кто-то обязан дождаться, возвращает UniTask — именно так объявлен IRunLauncher.StartAsync.

1.3 Две разные беды: баг данных и отмена

try/catch вокруг запуска — это не одна ветка, а минимум две, и путать их нельзя. Они отличаются тем, кто виноват и кто чинит.

Баг данных или кодаОтмена
Типичный представитель ContentNotFoundException: в поле levelId опечатка, в базе нет такого ID OperationCanceledException: игрок ушёл из меню, объект уничтожен, токен отменён
Что произошло программу попросили о несуществующем программа сделала ровно то, о чём её попросили
Кто чинит разработчик, правкой ассета или кода никто, это штатный ход
Реакция в редакторе Debug.LogException — красным, со стеком ничего; максимум Debug.Log на время отладки
Реакция в релизе сообщение игроку «не удалось начать» и разблокировка кнопки ничего: экрана, которому сообщать, уже нет
Чего нельзя делать глушить, подставлять уровень по умолчанию, звать TryGet красить в ошибку и показывать игроку

Порядок catch-блоков определяется правилом C#: сначала более конкретный тип. OperationCanceledException ловится первым, иначе его съест общий блок. 

// Домен: отправка формы обращения в поддержку.
private async UniTaskVoid SubmitTicketAsync()
{
    try
    {
        await _tickets.SendAsync(_subjectField.text, _bodyField.text, _lifetime);
        _status.text = "Отправлено";
    }
    catch (OperationCanceledException)
    {
        // Штатный выход: форму закрыли, пока письмо уходило.
        // Не логируем, не показываем, ничего не трогаем — трогать уже нечего.
    }
    catch (ArgumentException e)
    {
        // Баг: форма пропустила пустую тему. Чинит разработчик, поэтому громко.
        Debug.LogException(e);
        _status.text = "Не удалось отправить";
    }
}

Так не надо.

// ← НЕТ. Один catch на всё: отмена станет ошибкой в логе, а настоящая ошибка
//   станет строчкой того же цвета.
//   Сломается: каждый выход из формы во время отправки печатает красное.
//   Заметят: сразу — и привыкнут, а потом пропустят реальную ошибку рядом.
catch (Exception e)
{
    Debug.LogError(e);
}

// ← НЕТ. Пустой catch на всё. Ошибка данных исчезает вместе с отменой.
//   Сломается: опечатка в levelId даёт кнопку, которая просто ничего не делает.
//   Заметят: когда кто-то скажет «кнопка не работает».
catch (Exception)
{
    // молча
}

// ← НЕТ. «Починка» промаха по ID подстановкой значения по умолчанию.
//   Сломается: битые данные доезжают до релиза, потому что игра их прощает.
//   Заметят: никогда — оно же «работает».
if (_content.TryGet<LevelConfig>(id, out LevelConfig level) == false)
    level = _content.All<LevelConfig>()[0];
Отмена — не откат

Отменённый await прекращает ожидание, а не работу. Проверено на проекте: SceneManager.LoadSceneAsync("Gameplay") с отменённым токеном дал OperationCanceledException — и сцена всё равно загрузилась: 

[SBX] E3: active scene before = MainMenu
[SBX] E3: OperationCanceledException — we stopped waiting
[SBX] E3: active scene 2 s later = Gameplay

Значит catch (OperationCanceledException) не имеет права считать, что мир остался прежним. Если после отмены надо что-то разобрать — разбирать придётся руками, и это отдельная ответственность владельца операции.

1.4 Кнопка нажата дважды

Загрузка сцены занимает не кадр, а сотни миллисекунд. Всё это время кнопка на экране жива и кликабельна. Второе нажатие — не экзотика, а норма: игрок не увидел реакции и нажал ещё раз.

RunLauncher.StartAsync первой строкой зовёт Stop() — по отчёту 008 (К-1) это означает «повторный старт молча перезапускает забег». Для последовательного второго запуска это верно. Для второго нажатия во время загрузки — нет, и вот почему: обе копии метода успевают выполнить Stop() до того, как первая дошла до присваивания _runScope. Первой копии нечего останавливать, второй — тоже.

Проверено на проекте на модели той же формы (домен: открытие документа, поле «что сейчас открыто», закрытие перед открытием, ожидание между ними): 

[SBX] E4: OpenDocumentAsync(doc-A) entered, closing whatever is open
[SBX] E4:   nothing to close
[SBX] E4: OpenDocumentAsync(doc-B) entered, closing whatever is open
[SBX] E4:   nothing to close
[SBX] E4: opened doc-A
[SBX] E4: LEAK — 'doc-A' is still open and nobody will ever close it
[SBX] E4: opened doc-B
[SBX] E4: _openDocument is now 'doc-B'

Обе «закрывашки» отработали вхолостую, потом первая копия открыла A, вторая затёрла поле значением B, и A остался открытым навсегда. Переведи на проект: первый RunLifetimeScope создан, ссылка на него потеряна, Dispose не будет вызван никогда. Это ровно та утечка, которую К-1 считал закрытой, — с живым EcsWorld, тикающим параллельно второму.

Почему блокировать надо в UI, а не в лаунчере

Соблазн — поставить флаг «уже стартую» внутрь RunLauncher и игнорировать повторный вызов. Три довода против.

Первый: семантика лаунчера уже выбрана, и она другая. Журнал решений от 2026-08-21 и К-1 отчёта 008 фиксируют «повторный старт перезапускает забег» — это нужно рестарту с экрана смерти. Флаг превратит рестарт в тихий отказ.

Второй: лаунчер не умеет отвечать «нет». Его метод возвращает UniTask. Игнорирование вызова — это возврат уже завершённого таска, то есть ложь вызывающему: «готово», хотя ничего не сделано. Чтобы не соврать, пришлось бы завести код ошибки — и появился бы второй способ сообщать о проблеме рядом с исключениями.

Третий и главный: проблема не в лаунчере, а в кнопке. Кнопка, нажимаемая во время начатой ею операции, — дефект UI, и лечится он там, где находится: кнопка гасится на время запуска. Заодно игрок видит, что нажатие принято. Флаг в сервисе этой обратной связи не даёт вообще.

Правильная форма — флаг плюс finally. Ключевое слово здесь finally: без него первое же исключение оставит кнопку выключенной навсегда. 

// Домен: скачивание файла патчноутов по кнопке.
private bool _isDownloading;

private void OnDownloadClicked()
{
    if (_isDownloading)
        return;

    DownloadAsync().Forget();
}

private async UniTaskVoid DownloadAsync()
{
    _isDownloading = true;
    _downloadButton.interactable = false;

    try
    {
        await _patchNotes.DownloadAsync(_lifetime);
        _status.text = "Готово";
    }
    catch (OperationCanceledException)
    {
        // Панель закрыта — восстанавливать нечего, finally отработает вхолостую.
    }
    catch (UnityWebRequestException e)
    {
        Debug.LogException(e);
        _status.text = "Не удалось скачать";
    }
    finally
    {
        // Единственное место, где флаг и кнопка возвращаются в исходное.
        _isDownloading = false;
        _downloadButton.interactable = true;
    }
}

Так не надо.

// ← НЕТ. Восстановление после try, а не в finally.
//   Сломается: первая же ошибка оставляет кнопку серой до перезапуска игры.
//   Заметят: при отладке битого ID — «нажал, ничего, теперь вообще не нажимается».
try { await _patchNotes.DownloadAsync(_lifetime); }
catch (Exception e) { Debug.LogException(e); }
_isDownloading = false;

// ← НЕТ. Кнопка не гасится, а прячется.
//   Сломается: SetActive(false) на объекте с кнопкой прекращает его собственные
//   корутины и двигает вёрстку соседей; вернуть объект обязан тот же код,
//   который скрыл, — а он может до этого не дожить.
//   Заметят: когда после ошибки кнопка исчезнет с экрана насовсем.
_downloadButton.gameObject.SetActive(false);

1.5 Токен отмены и жизнь объекта UI

Загрузка сцены выгружает предыдущую сцену со всеми её объектами. Таск при этом не знает о смерти объекта и продолжается: он живёт в PlayerLoop, а не в объекте. Продолжение выполнится и обратится к полям уничтоженного компонента.

Проверено на проекте, дословный вывод:

[SBX] E2a: started, NO cancellation token
[SBX] E2b: started WITH GetCancellationTokenOnDestroy, CanBeCanceled=True
[SBX] E2: loading MainMenu — this unloads the scene the victim lives in
[SBX] E2b: OperationCanceledException — the task stopped when the object died
[SBX] E2a: CONTINUATION RAN after the scene unload
[SBX] E2a: this == null (Unity fake null) -> True
[SBX] E2a: touching transform threw MissingReferenceException /
          The object of type 'SandboxVictim' has been destroyed
          but you are still trying to access it.

Три факта отсюда, и все три неочевидны:

  • Продолжение выполняется. Не «иногда», не «только в редакторе» — всегда. Уничтожение объекта на таск не влияет никак.
  • this == null даёт true (подменённое сравнение Unity), но this при этом живой управляемый объект: поля читаются, методы зовутся. Ловушкой это становится на первом обращении к transform, gameObject или любому другому Component — там MissingReferenceException.
  • Версия с токеном остановилась раньше версии без токена: отмена пришла в момент уничтожения, а не по истечении задержки.

GetCancellationTokenOnDestroy() — токен, который отменяется при уничтожении объекта. На Unity 2022.2+ (то есть и на нашей 6000.4) для MonoBehaviour он просто возвращает встроенный destroyCancellationToken; для GameObject и не-MonoBehaviour-компонентов UniTask подвешивает собственный AsyncDestroyTrigger.

Токен нельзя взять задним числом

Проверено: обращение к GetCancellationTokenOnDestroy() уже после уничтожения даёт MissingReferenceException. Токен берётся до первого await, в живом объекте, и хранится в поле или локальной переменной.

Когда токен обязателен. Правило простое: если после await код трогает this, transform или поля со ссылками на объекты сцены и UI — токен обязателен. Если после последнего await ничего такого нет, можно без токена; но это свойство легко потерять при следующей правке, поэтому в UI дешевле всегда передавать токен. 

// Домен: панель погоды на экране настроек.
public sealed class WeatherPanel : MonoBehaviour
{
    [SerializeField] private TMP_Text _label;
    [SerializeField] private string _cityId;

    private CancellationToken _lifetime;

    private void Awake()
    {
        // Берём один раз, пока объект точно жив.
        _lifetime = this.GetCancellationTokenOnDestroy();
    }

    private async UniTaskVoid RefreshAsync()
    {
        try
        {
            await UniTask.Delay(200, cancellationToken: _lifetime);

            // Сюда мы не попадём, если панель уничтожили за эти 200 мс.
            _label.text = "обновляю…";
        }
        catch (OperationCanceledException)
        {
        }
    }
}

Так не надо.

// ← НЕТ. Без токена. После выгрузки сцены продолжение выполнится и упадёт.
//   Сломается: MissingReferenceException в консоли на каждом переходе из меню.
//   Заметят: сразу — но «поправят» проверкой на null, а не токеном (см. ниже).
await UniTask.Delay(200);
_label.text = "обновляю…";

// ← НЕТ. Проверка на null вместо токена.
//   Формально не падает, но цепочка await продолжает выполняться до конца:
//   держит ссылки, качает данные никому не нужной панели, — и каждую новую
//   строку после каждого await надо не забыть накрыть такой же проверкой.
//   Заметят: не заметят. Это тихий расход и мина под будущие правки.
await UniTask.Delay(200);
if (this == null)
    return;

// ← НЕТ. Токен берётся внутри, после await.
//   Сломается: MissingReferenceException прямо на этой строке, если объект уже мёртв.
//   Заметят: сразу, но причину — «нельзя спросить у покойника» — не сразу.
await UniTask.Delay(200);
CancellationToken ct = this.GetCancellationTokenOnDestroy();

Привязка к стеку

2.1 Что уже готово, и чего не хватает ровно одного

Со стороны кода забег полностью собран. Не хватает единственного вызывающего.

ЧтоГдеСостояние
IRunLauncher.StartAsync(RunRequest, CancellationToken) Game.Core / Game.Bootstrap работает, зарегистрирован Lifetime.Singleton
RunRequest(levelId, characterId, mode) Game.Core readonly struct, три поля
ContentRegistry, LevelConfig Game.Core / Game.Configs в базе одна запись: level.gameplay → сцена Gameplay
Сцена Gameplay Assets/_Project/Scenes арена, свет, камера, болван; в Build Settings, включена
Кнопка NewGameButton сцена MainMenu есть, interactable, обработчиков ноль
Компонент, который свяжет кнопку и лаунчер Game.UI его и надо написать
Ловушка на первой минуте: Game.UI не видит Button

Ссылки Game.UI сегодня — это Game.Core, Game.Configs, VContainer, UniTask и R3.Unity. Сборок UnityEngine.UI и Unity.TextMeshPro среди них нет, а asmdef-ссылки автоматически не добавляются. Значит using UnityEngine.UI; внутри Game.UI сегодня даёт CS0234, и то же самое с TMPro.

Чинится добавлением двух ссылок в Game.UI.asmdef. Это осмысленная правка, а не обход: сборка экранов обязана видеть библиотеку экранов. Сделать её надо осознанно и отдельной строкой в отчёте, а не по подсказке IDE — см. историю с автоимпортами в CLAUDE.md §8.

2.2 Кто проинжектит компонент в сцене

Проектный корень живёт префабом в DontDestroyOnLoad и о содержимом сцены MainMenu не знает ничего. Просто написать [Inject] в компоненте недостаточно: инъекцию должен кто-то выполнить.

СпособОценка
Сценовый LifetimeScope в MainMenu + RegisterComponentInHierarchy<T>() берём. Ровно тот механизм, который проверен в блоке 2: сценовый скоуп сам находит проектный корень родителем и резолвит его регистрации. Регистрация форсирует инъекцию при построении контейнера — компонент получает зависимости даже если его никто не спрашивает
FindObjectOfType из точки входа нет: красная линия CLAUDE.md §7
Статическая ссылка на контейнер, Resolve в Awake нет: это Service Locator, отвергнут в блоке 1 (урок 02)
Регистрация префаба меню в проектном скоупе нет: проектный скоуп начнёт знать про конкретные экраны, а меню перестанет быть частью своей сцены

Два свойства RegisterComponentInHierarchy<T>(), о которых стоит знать заранее, потому что оба дают неочевидные симптомы:

  • Он ищет компонент в сцене самого скоупа, а не во всех загруженных сценах. Скоуп и компонент обязаны лежать в одной сцене.
  • Он форсирует резолв при построении контейнера. Компонента нет в сцене — падение произойдёт на старте сцены, а не при первом обращении. Это хорошо: то же «fail fast», что и у реестра контента.

2.3 Откуда берётся токен и что уедет в StartAsync

Токен здесь — жизнь компонента меню, потому что сцена MainMenu выгружается ровно в середине операции, которую этот компонент начал. Последовательность: 

нажатие → StartAsync → сборка RunContext
                    → await LoadAsync(Gameplay)   ← ЗДЕСЬ MainMenu выгружается
                    → CreateChild(RunLifetimeScope)
                    ↩ возврат в наш try/catch     ← компонента уже нет в живых

То есть код после await в компоненте меню выполняется всегда на уничтоженном объекте — не в редком случае, а в основном сценарии. Отсюда два следствия:

  • Токен destroyCancellationToken обязателен: он превращает основной сценарий в штатную отмену, а не в MissingReferenceException.
  • Блок finally, возвращающий кнопку, обязан быть готов к тому, что кнопки уже нет. При отмене восстанавливать нечего, и это нормально; проверка выполняется по флагу отмены, а не по null.
Почему успешный запуск выглядит как отмена

Непривычная, но правильная картина: при удачном старте забега компонент меню получит OperationCanceledException, потому что его сцену выгрузили. Это не ошибка — это признак того, что всё сработало. Обратная ситуация (метод дошёл до конца и спокойно трогает _button) означала бы, что сцена не сменилась.

2.4 Компонент временный, и это надо записать

По GDD.md §12 меню делается на шаге 9, и делается целиком: «UI, написанный до понимания того, что он запускает, переписывается целиком». Значит компонент этого блока — не первая версия меню, а отладочный запускатель, и его имя обязано об этом говорить.

Требование блока: пункт в CLAUDE.md §8 с явным условием снятия — «удаляется при появлении настоящего UI меню на шаге 9». Без этой строки временный компонент через два месяца станет постоянным просто потому, что работает.

// Лежит объектом на сцене MainMenu. Родителя не указываем:

3.2 Game.UI: отладочный запускатель

// Имя говорит о временности. Снимается на шаге 9 вместе с настоящим меню.
public sealed class DebugRunStarter : MonoBehaviour
{
    // Кнопка — ссылкой из инспектора, не поиском.
    [SerializeField] private Button _playButton;

    // ID — сериализованные поля, НЕ литералы в коде (CLAUDE.md §7).
    // Сегодня в базе есть только level.gameplay; characterId реестром пока
    // не проверяется — он просто уезжает в RunContext.
    [SerializeField] private string _levelId;
    [SerializeField] private string _characterId;

    private IRunLauncher _launcher;
    private CancellationToken _lifetime;
    private bool _isStarting;

    // Инъекция методом: у MonoBehaviour конструктора нет.
    [Inject]
    public void Construct(IRunLauncher launcher);

    // Берёт токен, подписывается на кнопку.
    private void Awake();

    // Отписывается: подписка переживёт объект, если её не снять.
    private void OnDestroy();

    // Синхронный. Проверяет флаг и запускает StartRunAsync().Forget().
    private void OnPlayClicked();

    // Здесь живут: флаг, гашение кнопки, await, три catch и finally.
    // UniTaskVoid, потому что ждать этот метод некому и незачем.
    private async UniTaskVoid StartRunAsync();
}

Что должно оказаться внутри StartRunAsync, по пунктам и без кода:

  1. поднять _isStarting и погасить _playButton.interactable;
  2. try: собрать RunRequest из сериализованных полей и RunMode.Story, затем await _launcher.StartAsync(request, _lifetime);
  3. catch (OperationCanceledException) — тихо: это основной сценарий удачного старта (2.3);
  4. catch (ContentNotFoundException e) — Debug.LogException: битый _levelId чинит разработчик;
  5. finally — вернуть флаг и кнопку, если кнопка ещё жива.

private async void OnPlayClicked()            // ← нет: catch не поймает (1.2)

_launcher.StartAsync(request, _lifetime);       // ← нет: ошибка уедет в финализатор

await _launcher.StartAsync(request, default); // ← нет: токена нет, отмены нет (1.5)

new RunRequest("level.gameplay", …);        // ← нет: литерал ID в коде

catch (Exception) { }                      // ← нет: съедает баг данных (1.3)

    .GetComponent<Button>();

Подводные камни

Вызов без await и без Forget

Симптом: кнопка нажата, ничего не произошло, консоль чистая. Через несколько секунд — а иногда через минуту, а иногда никогда — в логе всплывает InvalidOperationException со стеком, в котором последняя строка ExceptionHolder:Finalize() и нет ни одного твоего метода. Самая дорогая ошибка блока: она разводит момент сбоя и момент сообщения о нём, а без этой связи отладка превращается в гадание.

Обработчик кнопки объявлен async void

Симптом: компилируется, подписывается, работает — пока всё хорошо. При первой ошибке исключение уходит мимо UniTask и мимо любого catch в твоём коде. async void в Unity допустим ровно в одном месте — в обработчиках, где ты сознательно принял это поведение, — а в этом проекте таких мест нет. Правильная форма: синхронный обработчик, который зовёт UniTaskVoid-метод через Forget().

Один catch (Exception) на всё

Симптом: лог краснеет на каждом успешном запуске забега, потому что штатная отмена печатается как ошибка. Дальше по сценарию: к красному привыкают, и настоящая ошибка данных тонет между ними. Обратный вариант — пустой catch (Exception) — даёт кнопку, которая молча ничего не делает при опечатке в ID.

Кнопка возвращается не в finally

Симптом: первая же ошибка запуска оставляет кнопку серой до перезапуска игры. Обнаруживается именно тогда, когда мешает больше всего: при отладке битого levelId, то есть после каждой попытки надо перезапускать Play Mode.

Токен берётся после await

Симптом: MissingReferenceException на самой строке GetCancellationTokenOnDestroy(). Проверено: у уничтоженного компонента токен спросить нельзя. Токен берётся в Awake и хранится полем.

Токен взят у не того объекта

Симптом: отмена не срабатывает никогда, и всё выглядит как в примере «без токена». Причина обычно одна: токен взят у объекта, который переживает сцену, — у проектного корня, у объекта в DontDestroyOnLoad, у родителя, который не уничтожается. Токен обязан принадлежать тому самому компоненту, чьи поля трогает код после await.

Подписка на кнопку не снимается

Симптом: в этом блоке — никакого: кнопка умирает вместе с компонентом. Станет симптомом на шаге 9, когда экраны начнут переиспользоваться: один и тот же клик обработается дважды, потом трижды. Дешевле завести привычку сейчас: подписался в Awake — отписался в OnDestroy.

Защита от двойного клика уехала в лаунчер

Симптом: сначала всё хорошо, а на шаге 8 перестаёт работать рестарт с экрана итогов — лаунчер «защищается» от него как от повторного нажатия. Флаг живёт в UI, потому что защищаться надо от кнопки, а не от вызова (1.4).

ID уровня — литерал в коде

Симптом: компилируется, работает, и техдолг про имена сцен, закрытый блоком 4 шага 1, тихо возвращается — только теперь не именем сцены, а ID контента. Оба поля обязаны быть [SerializeField]: ID видно в инспекторе, менять можно без пересборки.

Ссылка на UnityEngine.UI добавлена «чтобы собралось»

Симптом: отсутствующий на первый взгляд. Опасность не в самой ссылке — она законна, — а в привычке добавлять ссылки по подсказке IDE. Ровно так в проект уже дважды заезжали редакторные сборки, которые компилировались в редакторе и упали бы на билде (CLAUDE.md §8). Правило: каждая новая строка в references — осознанное решение, попадающее в отчёт.

«Отменил — значит откатил»

Симптом: в этом блоке — сцена, которая всё-таки загрузилась после отмены. Дальше по проекту хуже: отменённый запуск, успевший создать дочерний скоуп, оставит его висеть. Проверено, что отмена ToUniTask не прекращает загрузку сцены. Любая уборка после отмены — явный код в catch, а не надежда на семантику токена.

Чек-лист приёмки

Форма кода

  • Обработчик клика синхронный; асинхронная часть вынесена в UniTaskVoid-метод, запускаемый через Forget().
  • Вызов _launcher.StartAsync(...) стоит под await, а не сам по себе.
  • В коде нет async void.
  • catch (OperationCanceledException) идёт раньше остальных и ничего не логирует.
  • Ошибка данных логируется через Debug.LogException, а не LogError(e.Message): нужен стек.
  • Возврат флага и кнопки — только в finally.
  • _levelId и _characterId — [SerializeField], литералов ID в коде нет.
  • Кнопка гасится через interactable, а не SetActive(false).
  • Подписка на onClick снимается в OnDestroy.

Токен и время жизни

  • Токен взят у этого компонента и до первого await.
  • Токен передан в StartAsync; default там не встречается.
  • finally не падает, когда кнопка уже уничтожена.

Проверяется руками — сценарии

  • Запуск с Bootstrap, нажатие «Играть» → грузится Gameplay, на арене стоит болван, консоль чистая.
  • В _levelId вписан несуществующий ID → в консоли сразу красное ContentNotFoundException с этим ID в тексте, сцена не сменилась, кнопка снова нажимается.
  • Двойное быстрое нажатие → забег стартует ровно один раз; в иерархии DontDestroyOnLoad ровно один объект RunLifetimeScope.
  • _levelId оставлен пустым → тоже ContentNotFoundException, а не NullReference где-то дальше.
  • Успешный запуск не печатает в консоль ничего — в том числе про отмену.
  • Выход из Play Mode во время загрузки не оставляет ошибок в консоли.

Понимание

  • Понятно, почему исключение из async-метода не появляется в точке вызова, даже если брошено до первого await (1.1).
  • Понятно, чем Forget() отличается от «просто не дождались» и почему разница — в моменте, а не в наличии сообщения (1.2).
  • Понятно, почему отмена и ошибка данных обрабатываются по-разному и кто чинит каждую (1.3).
  • Понятно, почему блокировка кнопки не переносится в лаунчер (1.4).
  • Понятно, почему при успешном старте забега компонент меню получает OperationCanceledException (2.3).
  • Понятно, почему отмена не откатывает уже начатую работу (1.3).
