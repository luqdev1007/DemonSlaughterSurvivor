1. ApplyDamageSystem
==========================================================================
В: Как выбирается сильнейшее событие за тик?
О: Первый проход по всем DamageEvent: пропуск Amount <= 0, цели без Health,
   цели с Invulnerable; на цель остаётся событие с наибольшим Amount, при
   равенстве — первое встреченное (строгое «>»). Второй проход применяет.
   Сравнивается сырой Amount события — никакой стат цели в выборе не участвует.
   → Simulation/Systems/ApplyDamageSystem.cs:44-69 (Invulnerable :57, сравнение :64)

В: Где известен фактически применённый урон?
О: Во втором проходе: health.Current -= damageEvent.Amount, и на СУЩНОСТЬ
   СОБЫТИЯ вешается тег DamageApplied. «Применённый» = Amount выбранного события
   целиком: оверкилл не вычитается (Health уходит в минус), HP до удара нигде
   не сохраняется.
   → ApplyDamageSystem.cs:73-91 (запись :80, DamageApplied :82, KillingBlow :84-88)
   → Simulation/Components/CombatComponents.cs:23-33

В: Можно ли отдать его наружу без правки читателей?
О: Да, путь уже существует. Выбранные события помечены DamageApplied и живут до
   CleanupEventsSystem в группе 13 (удаляет сущности событий целиком). Готовый
   прецедент читателя — PlayHitFeedbackSystem с фильтром Inc<DamageEvent,
   DamageApplied>. Новый читатель в группах 10–12 видит ровно применённые события
   без правки ApplyDamageSystem. Ограничение: только Amount события; для урона
   «до обрезки по HP» нужна правка ApplyDamageSystem.
   → PlayHitFeedbackSystem.cs:11; CleanupEventsSystem.cs:22-23

В: Кто пишет Health?
О: Четыре места:
   - ApplyDamageSystem (урон) → ApplyDamageSystem.cs:80
   - RecomputeStatsSystem (MaxHealth растёт дельтой, падает обрезкой; не у Dead)
     → RecomputeStatsSystem.cs:216-242
   - SpawnPlayerSystem (рождение героя) → SpawnPlayerSystem.cs:76-77
   - EnemyFactory (рождение врага) → Simulation/Services/EnemyFactory.cs:87
   Больше писателей нет (grep по Assets/_Project/**/*.cs).

В: Порядок групп вокруг?
О: 7 AdvanceSwingSystem (урон оружия) → 8 SweepDashPushSystem, DetectContactDamage
   (урон по герою) → 9 TickInvulnerabilitySystem, ApplyDamageSystem → 10 MarkDead,
   TickPendingFinish, FinishRunOnPlayerDeath, ReapDeadEnemies → 11 Progression
   (пусто; по ARCHITECTURE §10 «заряд ульты» живёт здесь) → 12 ViewSync
   (PlayHitFeedback, PublishPlayerVitals…) → 13 CleanupEvents …
   → Simulation/Systems/RunSystems.cs:42-70
   Следствие: ReapDeadEnemiesSystem (группа 10) удаляет сущность врага до группы 11,
   поэтому Source события контактного урона от врага, умершего в этом тике, в группе

2. Source у DamageEvent и два потока для ярости
==========================================================================
В: Всегда ли Source — герой для урона оружия?
О: Да. AdvanceSwingSystem кладёт Source = владелец взмаха (swing.Owner), не оружие
   (решение (г) журнала 2026-09-27). Единственный рождатель урона оружия.
   → AdvanceSwingSystem.cs:143-149

В: Что лежит для контактного урона по герою?
О: Source = сущность врага, Target = игрок, SourcePosition = позиция врага.
   Детектор ищет только цели с тегом Player — урон «враг → враг» и «герой → враг
   контактом» не рождается.
   → DetectContactDamageSystem.cs:17 (фильтр целей), :92-98

В: Рождателей DamageEvent всего?
О: Два: AdvanceSwingSystem и DetectContactDamageSystem. Отладочный K удалён (bed7532).

В: Как получить «нанесено героем» и «получено героем»?
О: По коду — одним читателем Inc<DamageEvent, DamageApplied> в группе 10–12:
   - нанесено: Source распаковывается в сущность с тегом Player;
   - получено: Target распаковывается в сущность с тегом Player.
   Оба потока — только применённые события (после i-frames и выбора сильнейшего).
   Урон по неуязвимому герою в «получено» не попадёт (события без DamageApplied).
   Урон по врагам всегда применяется: у врагов нет HitInvulnerability и Invulnerable
   (грепом: выдают только StartDashSystem и ApplyDamageSystem через HitInvulnerability,
   которая есть только у героя — SpawnPlayerSystem.cs:79-80).

3. Скорость атаки
==========================================================================
В: Откуда берётся скорость проигрывания?
О: Поле варианта WeaponConfig.SwingVariant._playbackSpeed (данные, не стат).
   Сейчас: LeftSlash 1.5, RightSlash 1.
   → Configs/WeaponConfig.cs:107, :117; Configs/Weapons/Weapon_BerserkSword.asset:20, :29

В: Кто её читает?
О: Четыре места, каждое читает из конфига на каждом обращении, снимка нет:
   - AdvanceSwingSystem: to = min(from + delta × PlaybackSpeed, ClipLength) каждый тик
     → AdvanceSwingSystem.cs:65-72
   - StartSwingSystem.ResolveShortestWindup: упреждение = min(WindowStart / PlaybackSpeed)
     → StartSwingSystem.cs:128-140 (используется в :88-90 для радиуса и :111)
   - PlaySwingFeedbackSystem → IView.PlayAttack(trigger, PlaybackSpeed)
     → PlaySwingFeedbackSystem.cs:37-39
   - SwingBaker при запекании покрытия (шаг сэмпла = speed/60 по времени клипа)
     → Configs/Editor/SwingBaker.cs:147, :285, :300

В: Как считается период и длительность в тиках?
О: Длительность взмаха не переводится в тики заранее: время клипа копится float
   (to = from + delta × speed), взмах удаляется в тике, где to >= ClipLength, то есть
   живёт ceil(ClipLength / (speed × delta)) тиков. Кулдаун: WeaponReady.Remaining =
   WeaponCooldown.Value на старте, тикает в группе 6; StartSwingSystem исключает
   Swinging. Период = max(кулдаун, длина взмаха в тиках). Сегодня кулдаун 0.25 с
   короче обоих клипов → период задаёт клип: LeftSlash 36 тиков, RightSlash 26
   (по коду, не замерено).
   → AdvanceSwingSystem.cs:71-91; StartSwingSystem.cs:17 (Exc<Swinging>), :53-56, :81;
     TickWeaponCooldownSystem.cs:20-31
   Замечание: ARCHITECTURE §7 требует «длительность способности в тиках, округление на
   старте» — взмах этому правилу не следует (float-накопление). Для ульты правило
   действует.

В: Как аниматор получает скорость?
О: IView.PlayAttack → ViewInterpolator: SetFloat("AttackSpeed", speed), затем
   SetTrigger(trigger). Состояния AttackLeftSlash/RightSlash/Spin в слое Attack
   имеют speed = 1 и speedParameter = AttackSpeed. Вход из Any State — длительность
   перехода 0, выход — exit time 1.0, фиксированные 0.1 с в Empty.
   → View/ViewInterpolator.cs:163-170
   → Art/Animations/Berserk/Berserk.controller: состояния :246/:262, :863/:879,
     :125/:141; входы :908 (LeftSlash), :424 (RightSlash); выходы :772, :170
   Параметр AttackSpeed по умолчанию 1 (:528-530).

В: Что менять, чтобы скорость стала статом героя со снимком на старте взмаха?
О: Факты, без выбора варианта:
   - StatId: новый член с номером 7 (StatId.cs:10) + строка в StatIdTableTests.cs:13-21.
   - Компонент со значением (Value/Base, как у WeaponCooldown — WeaponComponents.cs:11)
     и ветки в RecomputeStatsSystem.Apply (:180-214) и Carries (:244-263).
   - Наследование: если компонент будет на оружии, модификаторы героя дойдут до него
     сами — Gather берёт модификатор владельца, когда цель несёт этот стат
     (RecomputeStatsSystem.cs:94-108, Carries), а грязный владелец делает грязным
     подчинённого (:56-67). Если на герое — оружию придётся читать владельца.
   - Снимок: в Swing полей скорости нет (WeaponComponents.cs:21-47) — нужно поле,
     заполняемое в StartSwingSystem.StartSwing (:154-171) и читаемое в
     AdvanceSwingSystem.cs:72 и PlaySwingFeedbackSystem.cs:39 вместо variant.PlaybackSpeed.
   - Упреждение StartSwingSystem.ResolveShortestWindup (:136) тоже делит на скорость.
   - Итог пайплайна в секундах/множителях; перевод — у потребителя (журнал 2026-09-26 (ж)).

В: Где граница риска для совпадения клинка 0.0000 м?
О: Совпадение держится на трёх условиях, все проверяются тестом SwingBakeFreshnessTests
   (SwingBakeFreshnessTests.cs:70-104): состояние в слое Attack, его speed = 1, его
   скорость — параметр AttackSpeed. Плюс вход без перехода (длительность 0).
   - Безопасно: менять значение AttackSpeed на старте взмаха — аниматор и симуляция
     получают одно число (PlayAttack вызывается один раз на взмах, наложения взмахов нет).
   - Риск 1: скорость, прочитанная в разные моменты в симуляции и во вьюхе. Сегодня
     симуляция читает её каждый тик (AdvanceSwingSystem.cs:72), вьюха — один раз.
     Пока значение — константа конфига, разницы нет; как только оно станет статом,
     меняющимся посреди взмаха (ярость), без снимка симуляция и аниматор разойдутся.
   - Риск 2: покрытие и сектор срабатывания запечены при скорости конфига
     (SwingBaker.cs:147, :300). Сама проверка попадания (SwingSweep по подшагам
     запекания) от скорости не зависит, а сетка покрытия — дискретизация по тикам
     при данной скорости; при другой скорости покрытие становится приближением.
     Величина расхождения не замерялась.
   - Риск 3: известное отставание аниматора на 1 тик (CLAUDE.md §8) от скорости
     не зависит, но в клип-времени это speed/60 — при ускорении растёт.

10. Прыжок (AttackJump)
==========================================================================
В: Клип, длительность, root motion?
О: AttackJump.anim — generic-клип (не humanoid), 0.787 с, 75 fps, без цикла. Root
   motion нет: m_HasGenericRootTransform 0, hasRootCurves False, applyRootMotion у
   героя выключен (тест SwingBakeFreshnessTests.cs:78). Перемещение запечено в
   позицию Hips: по XZ прыжок на месте (Hips.z = 0 на всех ключах, x в пределах
   ±0.1 м), по высоте Hips 0.95 → пик 1.97 м на 0.213 с клипа → присед до 0.42 м
   около 0.44–0.49 с → 0.98 м в конце. В контроллере скорость 2, то есть на экране
   ≈0.39 с, пик ≈0.11 с. События: EnableHitbox 0.213, DisableHitbox 0.56,
   OnAttackFinished 0.787. Выход — exit time 0.682 → Idle за 0.1 с.
   → AttackJump.anim:10346 (fps), :10998 (длина), :9492-9814 (Hips), :81695-81718;
     Berserk.controller:11, :192-212 (выход)
   Числа высоты — чтение кривых, не замер позы в рантайме.

В: Обрабатывает ли его Bake Weapon Swings?
О: Инструмент запекает только варианты из WeaponConfig, ища состояние по имени во
   всех слоях (SwingBaker.cs:32-37, :44-81, :123-126) — найти AttackJump он сможет.
   Но тест свежести требует, чтобы каждый вариант был в слое Attack, со speed 1 и
   параметром AttackSpeed (SwingBakeFreshnessTests.cs:70-104); AttackJump лежит в
   Base Layer со скоростью 2 без параметра — как вариант меча он тест не пройдёт.
   Кроме того, Any State базового слоя по IsDashing уводит в DashRun
   (Berserk.controller:650-673) — рывок оборвёт картинку прыжка.

В: Как поведёт себя сектор срабатывания при варианте с другой геометрией?
О: Сектор = ПЕРЕСЕЧЕНИЕ покрытий всех вариантов (SwingBaker.cs:118-121, :151-155,
   :173-175). Вариант с другой формой покрытия может только сузить сектор; если
   пересечение станет пустым, забег не стартует — EquipStartingWeaponSystem.cs:80-83
   бросает «would never swing». Запасной А3′ (объединение) описан в CLAUDE.md §8,
   не реализован.

В: Как выбирается вариант?
О: Равновероятно из всего пула, без весов и условий: roll ∈ [0,1) из собственного
   потока оружия × VariantCount. Цель на вариант не влияет — HasTarget проверяет
   только общий сектор.
   → StartSwingSystem.cs:72-79, :142-152; поток — EquipStartingWeaponSystem.cs:58-59

В: Нужен ли прыжку отдельный триггер?
О: Факт по коду: в пуле вариантов прыжок станет случайным автоударом с вероятностью
   1/(N+1), и способа запустить его по кнопке или по ульте у пула нет. Если прыжок —
   часть ульты/способности, путь через пул меча не даёт ни «по решению игрока», ни
   гарантии выбора. Решение — за планом.
