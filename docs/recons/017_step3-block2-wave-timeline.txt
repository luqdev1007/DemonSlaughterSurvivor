4.1. ЧИСЛО ЖИВЫХ БЕЗ СЧЁТЧИКА — src/filters.cs:55-57

       [MethodImpl (AggressiveInlining)]
       public int GetEntitiesCount () { return _entitiesCount; }

     Это O(1) чтение поля, а не обход. Требование задачи «число живых — всегда
     запрос к фильтру» стоит ноль тактов, и отдельный счётчик в поле системы не
     дал бы ни байта выигрыша. Единственный писатель _entitiesCount — сам мир.

4.2. ГЛАВНАЯ ЛОВУШКА БЛОКА, КОТОРУЮ ПРИШЛОСЬ ПРОВЕРИТЬ ДО НАПИСАНИЯ КОДА:
     ФИЛЬТР ПОД ИТЕРАЦИЕЙ ЗАМОРАЖИВАЕТ СВОЙ СОСТАВ — src/filters.cs:69-72,
     108-117, 138-146, 152-167

       GetEnumerator ()  { _lockCount++; return new Enumerator (this); }
       AddEntity (e)     { if (AddDelayedOp (true, e)) { return; } … }
       AddDelayedOp (…)  { if (_lockCount <= 0) { return false; } … }   // копит
       Unlock ()         { _lockCount--; if (_lockCount == 0 && …) { … } }

     То есть пока по фильтру идёт foreach, добавления В ЭТОТ фильтр
     ОТКЛАДЫВАЮТСЯ и GetEntitiesCount() их НЕ ВИДИТ до выхода из цикла.

     ПОЧЕМУ ЭТО РЕШАЕТ ФОРМУ СИСТЕМЫ: спавн обязан читать число живых ПОСЛЕ
     каждого потока (основного и дозаправки). Если бы система шла foreach'ем по
     фильтру Inc<Enemy> и внутри спавнила, потолок перестал бы работать молча:
     счётчик не рос бы, и один тик выплюнул бы врагов сверх потолка. Поэтому
     фильтр живых в системе используется ТОЛЬКО как GetEntitiesCount(), и ни
     одного foreach по нему в коде нет. Обход идёт по фильтру Inc<WaveState>,
     в состав которого спавн не добавляет ничего.

4.3. ДОБАВЛЕНИЕ КОМПОНЕНТА ОБНОВЛЯЕТ ФИЛЬТРЫ НЕМЕДЛЕННО (если не заперто) —

6. АРХИТЕКТУРА БЛОКА В ДВУХ АБЗАЦАХ
------------------------------------

SpawnWaveSystem (группа 3, после SpawnPlayerSystem) в Init валидирует весь
таймлайн, создаёт сущность забега с единственным компонентом WaveState
{ Index, Elapsed } и заводит три объекта: RingSpawnPlacement, WeightedEnemyPicker,
SimulationRandom(seed из RunContext). В Run: прибавляет Delta к Elapsed;
на границе волны зовёт TryAdvanceWave (ДЫРКА 3) и чистит флаги гарантий; берёт
центр кольца из Position игрока фильтром; отрабатывает гарантированные события;
считает основной поток через ResolveSpawnCount (ДЫРКА 1) и спавнит; ПЕРЕЧИТЫВАЕТ
число живых; если оно ниже пола — считает поток дозаправки тем же
ResolveSpawnCount с полом вместо потолка и спавнит.

Что где живёт. Индекс волны и накопленное время — в компоненте, потому что HUD
шага 9 будет их читать. Накопители дробей, флаги отработанных гарантий, ссылка
на таймлайн и генератор случайных — приватные поля системы: наружу не нужны.
Выбор врага по весам и вычисление точки — отдельные объекты без состояния в
Simulation/Services, их зовёт система. Пути публикации в UI не построено:
ни сервиса, ни R3, ни интерфейса в Game.Core.

Р1. Система переименована: SpawnEnemiesSystem удалена, появилась SpawnWaveSystem

    значило бы завести файл, имя которого врёт про содержимое.
    ЦЕНА: в git это удаление + добавление, а не переименование; заполненная
    разработчиком дырка блока 1 (ResolveSpawnPosition) уехала вместе с файлом.

Р2. Правило размещения вынесено в RingSpawnPlacement, центр кольца — Position
    ИГРОКА, взятая фильтром.
    ПОЧЕМУ: это ровно замечания 1 и 2 отчёта 016. Прежний центр — литерал
    Vector3.zero в одном файле и такой же литерал в SpawnPlayerSystem, связанные
    только совпадением значения; поле называлось «радиус спавна», но радиусом
    было лишь пока игрок стоит в origin. Теперь радиус — честный радиус от
    игрока, а «center» стал настоящим параметром, а не переменной без второго
    значения. Заодно снято замечание 3: локальная spawnRange исчезла, имя
    параметра — ringRadius.
    ПРАВИЛО ТО ЖЕ, ЧТО БЫЛО (точка на окружности, y = 0), второго правила
    размещения в проекте не появилось. Изменилось только, откуда берётся угол:
    был index/count, стал случайный от сида — потому что волны спавнят по
    одному, а не пачкой, и «номер из скольких» больше не существует.
    ОТСУТСТВИЕ ИГРОКА — законный исход: фильтр пуст, спавн пропускается, время
    волны при этом продолжает идти. Не падает.

Р3. Случайность — СОБСТВЕННЫЙ детерминированный генератор SimulationRandom,
    засеянный RunContext.Seed. НЕ ISeedSource и НЕ UnityEngine.Random.
    ПОЧЕМУ ИМЕННО ТАК, а не как сказано в задаче: см. расхождение Р-3 раздела 2.
    ISeedSource — синглтон ПРОЕКТНОГО скоупа, недетерминированный по построению
    (new Random(Guid.NewGuid().GetHashCode())), и в архитектуре он отвечает за
    один вопрос: «какой сид у этого забега». Дёргать его из системы значило бы
    получать новое случайное число на каждого врага и потерять
    воспроизводимость — то самое, что задача запрещает. Единственный
    существующий носитель «сида забега» — RunContext.Seed, и он уже инжектится
    в системы. Новой инфраструктуры при этом ровно 20 строк.
    ПОЧЕМУ НЕ System.Random(seed): его последовательность — деталь реализации
    рантайма, и обновление Unity/Mono может её изменить. Для «один сид — один
    забег» на годы вперёд это неприемлемо. SimulationRandom — xorshift32,
    десять строк, поведение задано кодом проекта, а не рантаймом.
    ЦЕНА: порядок обращений к генератору стал частью контракта. Сейчас он такой:
    на каждого врага сначала бросок для выбора по весам, потом бросок для угла.
    Вставили нового потребителя случайности выше по коду — вся расстановка
    поехала. Ровно та цена, которую отчёт 015 предъявлял в варианте В1-Б.

Р4. Состояние волн — компонент на сущности забега; накопители и флаги —
    приватные поля системы.
    ПОЧЕМУ: индекс волны и время в волне нужны HUD шага 9, то есть у них есть
    внешний потребитель, и место таким данным — в мире. Накопители дробей и
    флаги отработанных гарантий внешнего потребителя не имеют и никогда не
    получат: это внутренняя механика одного правила спавна. В компоненте они
    были бы шумом, который пришлось бы объяснять каждому, кто откроет файл.
    ПУТЬ В UI НЕ ПОСТРОЕН — ни сервиса, ни R3, ни интерфейса в Game.Core.
    Потребителя нет, а инфраструктура без потребителя протухает раньше, чем
    понадобится.

Р5. Время волны хранится в СЕКУНДАХ (float Elapsed), а не в целых тиках.
    ПОЧЕМУ: и порог гарантированного события, и длительность волны заданы в
    конфиге секундами, и оба сравниваются с этим полем — перевод в тики
    потребовал бы округления на каждой границе и хранения тиковой длительности
    рядом с секундной, то есть второго источника правды. Плюс тиковый счётчик
    зашивает в компонент допущение «тик равен 1/60», которого в компоненте
    быть не должно.
    ЦЕНА, И ОНА ИЗМЕРЕНА: граница волны попадает на тик, поэтому фактическая
    длительность квантуется шагом симуляции, а последняя дробь темпа остаётся
    в накопителе — замер 1 показал минус 0.92 спавна на волну (−1.8%).
    Это тот же класс эффекта, что квантование рывка (отчёт 013, п. 2 журнала),
    но здесь от точности не зависит ничего: волна на 30 секунд не становится
    хуже от того, что она длится 29.983.

Р6. Границы арены — число ArenaRadius в LevelConfig, а не в конфиге волн.
    ПОЧЕМУ: размер арены — свойство АРЕНЫ, ровно по той же логике, по которой
    отчёт 015 (Р4) развёл числа врага и числа старта. Тот же таймлайн волн на
    другой арене должен ужиматься по её размеру, а не тащить чужую геометрию.
    Радиус спавна при этом лежит в конфиге ВОЛН: «как далеко от игрока рождать»
    — свойство правила спавна, а не арены.
    ЗАМЕРЕННЫЙ КОНФЛИКТ, из-за которого пункт заведён в CLAUDE.md §8, а не
    просто закрыт числом: при текущей камере (pitch 50, distance 16, fov 50,
    16:9) дальние углы экрана лежат в 27.03 м от игрока, ближние — в 11.83 м.
    Значит спавн строго за экраном требует радиуса больше 27.03, а арена — 30.
    Рабочая полоса 3 метра, и она схлопывается, как только игрок отходит от
    центра: прижатие сгоняет половину кольца на одну дугу. Выбран spawnRadius
    30 — «рождать на границе арены». Это временно и честно записано.

Р7. Веса и гарантии описаны ОДНОЙ структурой каждая, не параллельными массивами.
    WeightedEnemy { EnemyConfig, float } и GuaranteedSpawn { float, EnemyConfig,
    int } — сериализуемые классы в файле конфига.
    ПОЧЕМУ: два параллельных массива рассинхронизируются при первой же правке в
    инспекторе, и ошибка будет не «упало», а «не тот враг с не тем весом».
    ЦЕНА: три сериализуемых типа в одном файле с SO. Это осознанно: они не
    ScriptableObject и отдельными файлами дали бы каталог из трёх файлов по
    десять строк.

Р8. Валидация таймлайна — в Init, целиком и один раз, с указанием номера волны
    и номера записи. Пустой список волн — ЗАКОННОЕ состояние, не ошибка.
    ПОЧЕМУ: незаполненный EnemyConfig в двадцатой записи должен падать один раз
    на старте с адресом «волна 3, weighted запись 2», а не шестьдесят раз в
    секунду из тика. А пустой таймлайн — это нормальный уровень без врагов
    (и, кстати, то, с чего начнётся любая новая арена), падать на нём нельзя.
    Проверено замером 8.

Р9. Все три дырки — в Run, ни одной в Init.
    ПОЧЕМУ: п. 4.5 и опыт блока 1. Дырка в Init отравляет весь EcsSystems, и
    сообщения остальных дырок тонут в постороннем «Cant run without
    initialization». Здесь Init отрабатывает целиком, поэтому в консоли видны
    настоящие имена методов и строки — замер 0.
    ПОБОЧНО: до заполнения дырок агентская часть Run успевает отработать
    гарантированные события, и они видны в мире. Это не костыль, а следствие
    порядка внутри Run: гарантии не зависят ни от одной из дырок.

9.1. НАЙДЕН ДЕФЕКТ ВНЕ СКОУПА БЛОКА — ИНТЕРПОЛЯЦИЯ ВЬЮХ МЁРТВАЯ.
     Это главное, что вылезло за сессию, и это НЕ дефект блока 2.

     ЧТО НАБЛЮДАЕТСЯ. ViewInterpolator._secondsSinceUpdate на живом забеге
     равен 0.274…1.306 с при длине тика 0.01667 с, то есть в 16…78 раз больше
     тика. Значит phase = Clamp01(sec / tick) равна ровно 1.000 ВСЕГДА:
     4320 замеров подряд, minPhase = maxPhase = 1.000. Картинка не
     интерполируется — она стоит в _currentPosition и переставляется скачком
     раз в тик. Ровно те ступени по 16.7 мс, ради устранения которых
     ARCHITECTURE.md §3 и вводил интерполяцию.

     МЕХАНИЗМ, ПОСЧИТАННЫЙ, А НЕ УГАДАННЫЙ. SetPosition вычитает из накопителя
     РОВНО один тик за вызов, Update прибавляет реальный Time.deltaTime за
     кадр. Пока тиков ровно столько, сколько реального времени, всё сходится.
     Но RunEntryPoint.Tick ограничен MaxStepsPerFrame = 5 и на переполнении
     делает _accumulator = 0f, то есть ВЫБРАСЫВАЕТ время. Выброшенное время
     из накопителя вьюхи никто не вычитает — он растёт навсегда.
     Первый же тяжёлый кадр забега — загрузка сцены — делает это сразу:
     Time.deltaTime зажат Unity на maximumDeltaTime = 0.3333, пять тиков
     съедают 5/60 = 0.0833, остальные 0.250 остаются в накопителе вьюхи.
     Замерено: maxDt = 0.33333 в первом кадре, и накопитель немедленно
     садится на 0.274 и дальше только колеблется в пределах одного тика
     (minSec 0.27396, maxSec 0.29052 за 200 кадров). Каждая следующая просадка
     добавляет ещё. Это храповик: вниз он не идёт никогда.

     ПОЧЕМУ ЭТОГО НЕ УВИДЕЛ ОТЧЁТ 015. Там замерена фаза 0.860 — значит на тот
     момент накопитель был меньше тика. Замер был снят раньше, чем набежала
     первая просадка, и совпадение позиции с Lerp было честным. Сегодня то же
     совпадение (0.0000000) не значит ничего: при фазе 1.000 Lerp вырождается
     в _currentPosition, и формула совпадает сама с собой.

     ГДЕ ЧИНИТЬ: ViewInterpolator.SetPosition / ResolvePosition — код блока 3
     шага 2, из них ResolvePosition заполнял разработчик (отчёт 014).
     Направления, БЕЗ ВЫБОРА: (а) зажимать накопитель в SetPosition, чтобы
     он не мог уйти выше тика; (б) не вычитать фиксированный тик, а
     пересчитывать фазу от последнего SetPosition; (в) убрать выброс времени
     в RunEntryPoint и вместо _accumulator = 0f оставлять остаток. Вариант (в)
     чинит симптом у вьюх, но меняет поведение симуляции под просадкой, то
     есть это уже другое решение.

10. ОСТАВЛЕННЫЕ ДЫРКИ И ИХ КОНТРАКТЫ (CLAUDE.md §2)

ПОРЯДОК ЗАПОЛНЕНИЯ. В отличие от блока 1, дырки НЕ отравляют друг друга: все

Рекомендуемый порядок — 1, 2, 3. Он не обязателен, но обратный заставит ждать

--------------------------------------------------------------------------
ДЫРКА 1 — SpawnWaveSystem.ResolveSpawnCount(
              ref float accumulator, float ratePerSecond, float deltaSeconds,
              int liveCount, int liveLimit)
          Assets/_Project/Simulation/Systems/SpawnWaveSystem.cs:159
--------------------------------------------------------------------------

Что на входе:
  accumulator   — ПО ССЫЛКЕ, дробный остаток этого потока. Метод обязан его
                  обновить: это единственное место, где он меняется.
  ratePerSecond — темп потока, врагов в секунду. Может быть 0 и не может быть
                  отрицательным (в конфиге отрицательное никто не запрещает,
                  но и смысла не имеет).
  deltaSeconds  — длительность тика, SimulationClock.Delta.
  liveCount     — число живых врагов, СВЕЖЕЕ, снятое фильтром прямо перед
                  вызовом.
  liveLimit     — верхняя граница живых для ЭТОГО потока: для основного это
                  потолок волны, для дозаправки — пол волны.

Что должно оказаться на выходе:
  Сколько врагов заспавнить в этом тике, число >= 0. Вызывающий спавнит ровно
  столько раз.

ВЫЗЫВАЕТСЯ ДВАЖДЫ ЗА ТИК, с разными накопителями и разными limit — это не
случайность, а причина, по которой у метода такая сигнатура: правила дробей у
основного потока и у дозаправки одинаковые, разная только граница. Не
разносить в два метода.

Что трогать нельзя:
  * метод не спавнит и не трогает мир — ни пулов, ни _world, ни фильтров.
    Он только считает число;
  * крутится КАЖДЫЙ ТИК ДВАЖДЫ: ни LINQ, ни new, ни замыканий, ни боксинга
    (CLAUDE.md §7);
  * обнулять накопитель «на всякий случай» нельзя: потерянный остаток смещает
    темп. При темпе 5/с и тике 1/60 за тик набегает 0.0833 — обнуление
    превращает 5 врагов в секунду в ноль навсегда;
  * период в целых тиках вместо накопителя не использовать: при темпе 25/с
    период равен 2.4 тика, округление до 2 даёт 30/с, до 3 — 20/с, промах в
    полтора раза.

Как падает незаполненной: NotImplementedException каждый тик, до пяти раз за
кадр, с файлом и строкой (замер 0). Громко.

Варианты решения и цена каждого — БЕЗ ВЫБОРА:

  В1-А. Один враг за тик максимум. Прибавить rate*delta; если накопитель >= 1
        и есть место под потолком — вернуть 1 и вычесть 1; иначе 0.
        ЦЕНА: самый предсказуемый спавн, никаких пачек, поток размазан ровно.
        РАСПЛАТА: темп физически ограничен 60 врагами в секунду, и при темпе
        выше 60 конфиг начинает молча врать — накопитель растёт быстрее, чем
        расходуется, и «100 врагов в секунду» превращается в 60. Ошибки не
        будет. Для этой игры 60/с — не абсурдная граница, но её надо знать.

  В1-Б. Сколько накопилось, столько и за тик: count = (int)accumulator,
        вычесть count.
        ЦЕНА: темп честен при любых значениях, включая 200/с; накопитель
        никогда не разбухает.
        РАСПЛАТА: пачки. При темпе 120/с каждый тик рождается два врага
        одновременно и в одной точке кольца может оказаться несколько сущностей
        подряд; при рваном delta пачки будут неровными. И на 500 врагах пачка
        означает 500 Instantiate в одном тике — просадка кадра ровно там, где
        и без того тяжело.

  В1-В. Пачка, но с потолком на размер пачки (например, не больше 4 за тик).
        ЦЕНА: компромисс — высокий темп работает, катастрофическая пачка
        невозможна.
        РАСПЛАТА: третье число, которого нет в конфиге. Либо константа в коде
        (и тогда её никто не найдёт), либо ещё одно поле в конфиге волн (и
        тогда дизайнер обязан понимать, что оно значит).

  ОТДЕЛЬНЫЙ ВОПРОС, ОБЩИЙ ДЛЯ ВСЕХ ТРЁХ, И ОН ВАЖНЕЕ ВЫБОРА МЕЖДУ НИМИ:
  ЧТО ДЕЛАТЬ С НАКОПИТЕЛЕМ, КОГДА УПЁРЛИСЬ В LIMIT.
    (а) не прибавлять вовсе, пока нет места — темп «замирает» и продолжается
        с той же дроби, когда место появится;
    (б) прибавлять, но не тратить — накопитель растёт, и в момент, когда
        место появится, выплёскивается всё накопленное разом. Это и есть
        «долг копится», который задача запрещает;
    (в) обнулить накопитель — долг не копится вовсе, но теряется и честная
        дробь текущего тика.
  Задача требует «долг не копится». (б) отпадает. Между (а) и (в) разница
  видна только в первый тик после освобождения места, и она порядка одной
  дроби — но выбрать надо осознанно, потому что (в) при частом упоре в
  потолок систематически недодаёт.

ДЫРКА 2 — WeightedEnemyPicker.Pick(IReadOnlyList<WeightedEnemy> entries,
                                   float roll)
          Assets/_Project/Simulation/Services/WeightedEnemyPicker.cs:9
--------------------------------------------------------------------------

Что на входе:
  entries — записи текущей волны, каждая { EnemyConfig Enemy, float Weight }.
            Список может быть пустым. Веса — ВЕСА, не шансы: сумма не обязана
            равняться единице и в общем случае ей не равна. Отдельная запись
            может иметь вес 0 или отрицательный — конфиг этого не запрещает.
            Ссылка Enemy гарантированно не null: проверено в Init (Р8).
  roll    — нормализованное случайное число из SimulationRandom.NextUnit(),
            строго в [0, 1). Единица не достижима: генератор отдаёт 24 бита,
            делённые на 2^24.

Что должно оказаться на выходе:
  EnemyConfig, выбранный пропорционально весам, ЛИБО null.
  null — законный исход, а не недоделка: вызывающий (SpawnFromWave) на null
  просто пропускает спавн. Именно так безопасно отрабатывает волна, у которой
  сумма весов нулевая, — проверено замером 8.

Что трогать нельзя:
  * метод обязан быть ЧИСТЫМ: ни поля, ни состояния между вызовами, ни
    собственного времени, ни обращения к миру. Он существует отдельным классом
    ровно затем, чтобы его можно было проверить на бумаге;
  * вызывается на КАЖДОГО спавнящегося врага, то есть десятки раз в секунду:
    ни LINQ, ни new List, ни замыканий, ни боксинга (CLAUDE.md §7);
  * бросок расходуется вызывающим ДО вызова и расходуется всегда, даже если
    выбор не удался. Не пытаться «переброситься» внутри: генератора здесь нет
    и не должно быть, иначе метод перестанет быть чистым и детерминизм
    станет зависеть от числа неудачных попыток.

Как падает незаполненной: NotImplementedException — но ТОЛЬКО после того, как
дырка 1 вернёт число больше нуля. До этого метод недостижим.

Варианты решения и цена каждого — БЕЗ ВЫБОРА:

  В2-А. Линейный проход с курсором. Просуммировать веса, взять target =
        roll * сумма, идти по записям, накапливая курсор, вернуть первую, у
        которой курсор превысил target.
        ЦЕНА: две простые итерации, ноль состояния, читается с листа, работает
        при любом числе записей.
        РАСПЛАТА: O(n) на каждого врага и ДВА прохода — сумма считается заново
        каждый раз, хотя внутри волны она не меняется. При двух-трёх записях
        это ничто; при двадцати и темпе 50/с это уже 2000 сложений в секунду
        ради числа, которое постоянно.

  В2-Б. Один проход: вычесть вес из target, пока не станет отрицательным.
        ЦЕНА: короче на цикл, та же арифметика.
        РАСПЛАТА: сумму всё равно надо знать заранее, чтобы отмасштабировать
        roll — либо второй проход возвращается, либо roll трактуется как доля
        от суммы, посчитанной снаружи, и тогда сигнатура метода меняется и
        часть решения уезжает в систему.

  В2-В. Предпосчитать кумулятивные веса при смене волны и искать бинарно.
        ЦЕНА: O(log n) на врага и ноль лишних сложений — единственный вариант,
        который не платит за длинный список.
        РАСПЛАТА: у выборщика появляется СОСТОЯНИЕ (массив префиксных сумм) и
        обязанность узнать о смене волны. Он перестаёт быть чистым
        вычислителем, а вместе с этим ломается и место, где он живёт: чистый
        объект в Simulation/Services превращается в кэш с жизненным циклом, и
        кто-то обязан его сбрасывать. За сегодняшнюю одну запись в волне это
        плата ни за что.

  ЧЕГО ДЕЛАТЬ НЕЛЬЗЯ, и это ловушка, ради которой дырка выделена:
  нормализовать веса «чтобы сумма была 1». Задача требует именно весов: новая
  строка в патче не должна заставлять пересчитывать остальные. Любая
  реализация, которая где-то делит на сумму и запоминает результат, вернёт эту
  проблему через дверь для персонала.
  Вторая ловушка: записи с весом 0 обязаны быть НЕДОСТИЖИМЫ. Наивный проход
  «курсор >= target» при target = 0 и первой записи с весом 0 вернёт как раз
  её. Именно поэтому в контракте стоит строгое неравенство, а не нестрогое, —
  но проверить это должен тот, кто пишет тело.

--------------------------------------------------------------------------
ДЫРКА 3 — SpawnWaveSystem.TryAdvanceWave(ref WaveState state,
                                         IReadOnlyList<Wave> waves)
          Assets/_Project/Simulation/Systems/SpawnWaveSystem.cs:164
--------------------------------------------------------------------------

Что на входе:
  state — ПО ССЫЛКЕ, состояние волн из компонента. state.Elapsed В МОМЕНТ
          ВЫЗОВА уже больше либо равен waves[state.Index].DurationSeconds —
          вызывающий проверил это перед вызовом. Превышение (недоспавненный
          хвост времени) равно state.Elapsed − длительность текущей волны и
          в общем случае не равно нулю.
  waves — весь список волн, гарантированно непустой.
  Доступны приватные поля системы: _spawnAccumulator, _refillAccumulator.

Что должно оказаться на выходе:
  true  — таймлайн продолжается; state.Index обязан остаться в диапазоне
          0..waves.Count-1, иначе вызывающий бросит InvalidOperationException
          с внятным текстом (это не дырка, это контрактная проверка);
  false — таймлайн кончился. Вызывающий запоминает это навсегда: метод больше
          не позовут ни разу за забег, спавн прекращается, время в компоненте
          продолжает идти. Возврат false НЕ обязан быть идемпотентным.

Что делает вызывающий ПОСЛЕ true, и на что поэтому не надо тратить тело:
  чистит флаги отработанных гарантированных событий целиком. То есть новая
  волна всегда начинает со всеми гарантиями невыполненными, и это верно даже
  если вернуть тот же самый индекс.

Что трогать нельзя:
  * ни мир, ни пулы, ни фильтры: сущностей здесь не создают и не удаляют;
  * массив _firedGuaranteed — им управляет вызывающий (см. выше);
  * вызывается не чаще раза за тик и обычно раз в десятки секунд, поэтому
    требование по аллокациям здесь мягче остальных — но и делать тут нечего,
    аллокациям взяться неоткуда.

Как падает незаполненной: NotImplementedException, но только когда время
дойдёт до конца первой волны — 30 секунд по сдаваемому конфигу.

Варианты решения и цена каждого — БЕЗ ВЫБОРА, и здесь их два независимых
измерения. Сначала «что с временем и накопителями на границе»:

  В3-Т1. Обнулить Elapsed, хвост выбросить. Обнулить оба накопителя.
         ЦЕНА: волна начинается с чистого листа, пороги гарантий отсчитываются
         от честного нуля, поведение легко читается в отладке.
         РАСПЛАТА: выброшенный хвост — это до одного тика времени и до одной
         дроби спавна на КАЖДОЙ границе. На таймлайне из десяти волн набегает
         систематический недобор. Мал, но односторонний: он всегда в минус.

  В3-Т2. Перенести хвост: Elapsed = превышение, накопители оставить как есть.
         ЦЕНА: суммарное время таймлайна и суммарное число врагов точны,
         дроби не теряются нигде — прямое продолжение той же логики, ради
         которой накопитель вообще существует.
         РАСПЛАТА: накопитель, набранный на темпе 1/с, доживает до волны с
         темпом 20/с и там значит совсем другое; первый тик новой волны может
         неожиданно родить врага «в долг» от предыдущей. И пороги гарантий
         новой волны отсчитываются от ненулевого начала — offset 0 сработает
         в тот же тик, что и переход, что, возможно, и хотелось.

  В3-Т3. Хвост перенести, накопители обнулить (смешанный).
         ЦЕНА: время точно, а темп новой волны стартует чистым.
         РАСПЛАТА: две разные политики для двух видов остатка в одном методе —
         это надо будет объяснять каждому, кто откроет файл, включая себя
         через полгода.

Второе измерение — «что после последней волны»:

  В3-К1. Тишина: вернуть false. Забег продолжается, врагов больше не
         появляется, уже живые доживают.
         ЦЕНА: самое честное отражение того, что таймлайн конечен, и ровно
         то, что описывает GDD.md §6 — забег кончается мини-боссом, а не
         бесконечным потоком.
         РАСПЛАТА: до шага 8 мини-босса нет, поэтому сегодня это означает
         «через полторы минуты на арене становится тихо и ничего не
         происходит». Пустая арена выглядит как баг, хотя багом не является.

  В3-К2. Повторять последнюю волну: вернуть true, индекс оставить, Elapsed
         сбросить (флаги гарантий вызывающий почистит сам, то есть гарантии
         последней волны будут срабатывать снова и снова).
         ЦЕНА: арена не пустеет, играбельность до шага 8 сохраняется, и это
         же готовый механизм для бесконечного режима из GDD.md §11.
         РАСПЛАТА: повторяющиеся «гарантированные» события перестают быть
         гарантиями и становятся периодикой — на элитках это меняет экономику
         ресурса ульты мага (GDD.md §4). И условие победы «убить мини-босса»
         начинает соседствовать с бесконечным потоком, то есть решение
         молча меняет режим забега.

  В3-К3. Конец забега.
         ЦЕНА: единственный вариант, который доводит таймлайн до логического
         конца.
         РАСПЛАТА: реализовать сегодня НЕЧЕМ. Ни компонента «забег окончен»,
         ни экрана итогов, ни пути наружу из симуляции не существует — это
         шаг 8. Вариант назван, чтобы было видно: он не отвергнут, он просто
         вне досягаемости этого блока.
