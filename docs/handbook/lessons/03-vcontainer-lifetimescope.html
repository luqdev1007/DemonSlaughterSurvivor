Блок 1 отвечал на вопрос «кто соединяет слои» и отвечал словами: корень композиции. Этот блок отвечает на вопрос «как он выглядит в коде». У VContainer корень — это MonoBehaviour по имени LifetimeScope, и почти всё неочевидное в нём растёт из одного факта: скоуп — это объект сцены, у которого есть Awake, OnDestroy и своя судьба при смене сцены. Отсюда и порядок инициализации, и правила времени жизни, и способ корректно перезапустить забег.

Теория

1.1 Скоуп: контейнер плюс время жизни

Контейнер из урока 02 — это структура «тип → как его сделать» плюс хранилище уже сделанного. Скоуп добавляет к нему ровно одно, зато определяющее: границу существования. Всё, что скоуп создал, умирает вместе с ним.

В VContainer скоуп представлен классом LifetimeScope — наследником MonoBehaviour. Это решение библиотеки, и оно не косметическое:

Из того, что скоуп — компонентСледует
У него есть Awake Момент построения графа привязан к жизненному циклу Unity, а не к вызову из кода. Он выполняется до Awake обычных компонентов: у LifetimeScope стоит [DefaultExecutionOrder(-5000)].
У него есть OnDestroy Уничтожение объекта или выгрузка сцены автоматически разбирает контейнер. Забыть освободить нельзя — Unity сделает это за вас.
Он живёт в сцене или в префабе Ссылки на префабы и объекты сцены задаются в инспекторе, а не в коде. Взамен появляется целый класс проблем «объект не там, где думали» (см. 2.4).
Он умеет DontDestroyOnLoad Скоуп, переживающий смену сцен, — это ровно то, чем должен быть проектный уровень.

Наследник переопределяет один метод — Configure(IContainerBuilder). Это и есть фаза Register из урока 02. Фазу Resolve VContainer выполняет сам в конце построения, фазу Release — в OnDestroy.

Ключевое различие терминов

LifetimeScope — компонент, объект сцены, то, что видно в иерархии. Контейнер (IObjectResolver) — то, что этот компонент построил и держит в свойстве Container. Скоупов в приложении может быть несколько, и каждый владеет своим контейнером; контейнеры связаны в дерево, скоупы — тоже. Это одно дерево, но два разных объекта на каждом узле, и путать их дорого: «уничтожить скоуп» и «разобрать контейнер» — разные операции с разными последствиями.

1.2 Регистрация: Register и RegisterInstance

Две принципиально разные операции, которые легко перепутать.

  • Register<T>(lifetime) — «когда попросят, создай T сам». Контейнер разбирает конструктор, рекурсивно добывает аргументы, создаёт объект и — если объект IDisposable — берёт на себя его уничтожение.
  • RegisterInstance(obj) — «вот готовый объект, раздавай его». Контейнер ничего не создаёт. И ничего не уничтожает: объекты, отданные через RegisterInstance, исключены из списка на Dispose. Проверено на проекте: IDisposable, зарегистрированный как готовый экземпляр, не получает Dispose() ни при уничтожении скоупа, ни при выходе из Play Mode.

Правило простое: кто создал, тот и уничтожает (ARCHITECTURE.md §1). Отдали контейнеру тип — уборка на нём. Отдали готовый экземпляр — уборка на вас.

Отдельно — под какими именами регистрация видна. Один вызов Register может объявить несколько «лиц» одного объекта: 

// один объект, два имени — так надо
builder.Register<SaveService>(Lifetime.Singleton).As<ISaveService>().AsSelf();

// то же самое, но через AsImplementedInterfaces — все интерфейсы разом
builder.Register<SaveService>(Lifetime.Singleton).AsImplementedInterfaces();

// два отдельных вызова для одного класса — так нельзя
builder.Register<SaveService>(Lifetime.Singleton).As<ISaveService>();
builder.Register<SaveService>(Lifetime.Singleton).AsSelf();  // ← падение при построении

Что именно происходит в третьем случае — проверено: контейнер не собирается и бросает System.ArgumentException: An item with the same key has already been added. Key: (Game.Services.SaveService, ) прямо на построении, то есть внутри Awake скоупа. Это хорошая новость: ошибка громкая и мгновенная. Молчаливый вариант той же беды выглядит иначе — см. подводный камень Две реализации под одним интерфейсом.

1.3 Три времени жизни

Lifetime отвечает на вопрос «сколько экземпляров и кто их убирает». Значений три, и все три в проекте понадобятся.

Сколько экземпляров Кто уничтожает Когда брать
Singleton Один на контейнер, в котором объявлен. Дочерние скоупы получают тот же экземпляр. Контейнер, при своём Dispose. Сервисы проектного уровня: ввод, сейвы, аудио, ContentRegistry.
Scoped Один на каждый скоуп. Два дочерних скоупа — два разных экземпляра. Свой скоуп, при своём Dispose. Всё, что живёт один забег: RunContext, мир ECS, spatial hash, пулы.
Transient Новый на каждый Resolve. Никто. Контейнер его не отслеживает. Мелкие объекты без состояния и без ресурсов. Для IDisposable — опасно.

Проверено на проекте, все три строки таблицы:

  • дочерний скоуп без собственной регистрации отдаёт тот же объект, что и родитель;
  • Scoped стабилен внутри своего скоупа и уничтожается вместе с ним;
  • Transient отдаёт новый объект на каждый Resolve, и при Dispose контейнера его Dispose() не вызывается — ни в корневом контейнере, ни в дочернем.
Ловушка со словом Singleton

Lifetime.Singleton означает «один на контейнер», а не «один на приложение». Если тот же тип с тем же Singleton зарегистрировать ещё раз в дочернем скоупе, дочерний создаст свой экземпляр, а родительский о нём не узнает. Проверено: два объекта, оба «синглтоны», состояние не сходится, ошибок нет. Отсюда правило одного уровня в 2.1.

1.4 Иерархия скоупов

Дочерний скоуп не копирует регистрации родителя. Он ищет у себя, и, если не нашёл, спрашивает родителя — и так вверх до корня. Поиск идёт только в одну сторону. 

// проектный скоуп
ISaveService      // Singleton
IInputService     // Singleton
        │
        ▼  дочерний
// скоуп забега
RunContext        // Scoped
EcsWorld          // Scoped

// забег видит ISaveService  — поиск ушёл вверх и нашёлся у родителя
// проект НЕ видит RunContext — вниз поиск не идёт, будет исключение

Проверено: попытка достать регистрацию дочернего скоупа из родительского даёт VContainerException. Это не недоработка, а несущее свойство: именно оно физически запрещает проектному сервису зависеть от забега.

Что ломается, если зарегистрировать сервис не на том уровне — два симметричных случая, оба тихие:

ОшибкаЧто происходитКак выглядит для игрока
Проектный сервис объявлен в скоупе забега Он умирает вместе с забегом и создаётся заново на следующем. Всё накопленное между забегами теряется. Валюта, набранная за забег, исчезает при возврате в меню — а GDD.md §6 требует обратного.
Объект забега объявлен в проектном скоупе Он переживает забег. Второй забег стартует с состоянием первого: непочищенным миром, старым RunContext, живыми вьюхами из прошлого прогона. Первый забег нормальный, второй — со странностями. Классическое «после рестарта игра ведёт себя иначе».

1.5 Точки входа

Контейнер умеет создавать объекты, но кто-то должен запустить процесс. В Unity этим обычно занимается MonoBehaviour: Start, Update, OnDestroy. Точки входа VContainer — те же события, но у обычных C#-классов, которым не нужен объект сцены.

ИнтерфейсМетодКогда вызывается
IInitializableInitialize() Сразу при построении контейнера, синхронно, внутри Awake скоупа
IPostInitializablePostInitialize() Там же, после всех Initialize
IStartableStart() Следующий кадр, в EarlyUpdate — до Start у MonoBehaviour
IPostStartablePostStart() Тот же кадр, после Start у MonoBehaviour
IFixedTickableFixedTick()Каждый FixedUpdate
ITickableTick()Каждый кадр, в Update
ILateTickableLateTick()Каждый кадр, в LateUpdate
IAsyncStartableStartAsync(token)Тот же момент, что IStartable, но на UniTask
IDisposableDispose()При уничтожении скоупа

Все они регистрируются одним вызовом RegisterEntryPoint<T>() — он объявляет тип под всеми реализованными интерфейсами сразу, поэтому один класс может быть и IStartable, и ITickable, и IDisposable.

Зачем это вместо MonoBehaviour. Точка входа — обычный класс с конструктором, а значит: зависимости видны в сигнатуре (урок 02, 1.6), объект нельзя случайно продублировать перетаскиванием в сцену, порядок вызова задаётся регистрацией, а не полем Script Execution Order, и класс не привязан к тому, есть ли он в текущей сцене.

1.6 Порядок инициализации — с точностью до кадра

Всё ниже снято с живого проекта, а не взято из README. Кадр — значение Time.frameCount. 

кадр 0  Awake скоупа
          Configure(builder)                  // фаза Register
          конструкторы сервисов и точек входа  // фаза Resolve: зависимость раньше зависимого
          IInitializable.Initialize
          IPostInitializable.PostInitialize
кадр 0  Awake обычных MonoBehaviour          // уже с готовым контейнером

кадр 1  IStartable.Start
        MonoBehaviour.Start
        IPostStartable.PostStart
        IFixedTickable.FixedTick → ITickable.Tick → ILateTickable.LateTick

кадр N  OnDestroy скоупа
          IDisposable.Dispose                 // в порядке, обратном созданию

Три следствия, которые стоят того, чтобы их запомнить:

  • Initialize — это ещё Awake. Сцена загружена не полностью, другие компоненты своих Awake ещё не прошли. Всё, что требует готовой сцены, идёт в Start, а не в Initialize.
  • IStartable.Start раньше MonoBehaviour.Start, а IPostStartable.PostStart — позже. Это точный инструмент: если точке входа нужно, чтобы вьюхи уже отработали свой Start, берётся IPostStartable.
  • Уничтожение идёт в обратном порядке создания — проверено: точка входа уничтожается раньше сервиса, от которого зависела. То есть зависимость всегда ещё жива в тот момент, когда зависимый от неё объект убирается за собой.

Привязка к стеку

2.1 Два скоупа проекта

Решение зафиксировано в журнале PROGRESS.md от 2026-08-20 и здесь не пересказывается, а разворачивается в терминах VContainer.

ProjectLifetimeScopeRunLifetimeScope
Чем является для VContainer Корневой скоуп: Parent == null, IsRoot == true, строит собственный Container Дочерний скоуп: строится от контейнера родителя, владеет ScopedContainer
Где физически Префаб, назначенный в VContainerSettings; при старте инстанцируется в DontDestroyOnLoad (см. 2.4) Объект в игровой сцене либо создаётся кодом через CreateChild
Время жизни регистраций Lifetime.Singleton Lifetime.Scoped
Кто уничтожает Никто до выхода из игры Dispose() при завершении забега либо OnDestroy при выгрузке сцены
Что внутри Сервисы, ContentRegistry, мета, сейвы, настройки, постоянные экраны RunContext, EcsWorld, EcsSystems, сервисы симуляции, вьюхи, пулы, HUD
Правило одного уровня

Каждый тип регистрируется ровно на одном уровне. Не «на всякий случай и там, и там» — это ровно тот случай из 1.3, когда получаются два объекта, оба считающие себя единственными. Сомневаетесь, куда положить, — задайте один вопрос: должен ли этот объект пережить рестарт забега? Ответ и есть уровень.

2.2 Рестарт забега

Вся конструкция существует ради этого сценария, поэтому он расписан по шагам. Проверено на живом проекте целиком, включая второй заход. 

// 1. игрок выбирает воспоминание в меню.
//    сценарий старта собирает RunContext и создаёт дочерний скоуп
runScope = projectScope.CreateChild<RunLifetimeScope>(installer);

// 2. забег идёт. RunContext, EcsWorld, пулы — Scoped, живут в этом скоупе

// 3. игрок умирает или добивает мини-босса.
//    итог забега уходит наверх ДАННЫМИ: сколько сфер, что выпало.
//    проектная мета принимает итог и пишет сейв

// 4. разбор
runScope.Dispose();
//    → Dispose у точек входа забега
//    → Dispose у всех Scoped-объектов, включая EcsWorld
//    → проектные синглтоны не тронуты вообще

// 5. «ещё раз» — тот же вызов, что в шаге 1.
//    новый RunContext, новый мир, ТЕ ЖЕ сервисы и та же мета

Обратите внимание, чего в этом списке нет: нигде не написано «очистить мир», «сбросить пулы», «отписаться». Освобождение не пишется руками — оно следует из того, что объект зарегистрирован как Scoped. Это и есть то, что покупается двумя уровнями вместо одного.

Условие, при котором это перестаёт работать

Проектный объект удержал ссылку на объект забега — подписался на его событие, положил в поле, закешировал. Тогда после Dispose ссылка остаётся и указывает на разобранный мир. Отсюда правило владения из журнала решений: ссылка допустима только вниз, от забега к проекту. Итог забега поднимается наверх копией данных, а не ссылкой на живой объект.

2.3 Где рождается EcsWorld

Урок 02 (2.2) объяснил, почему LeoECS Lite DI — не второй контейнер. Здесь видно, где именно проходит стык. 

// Game.Bootstrap — скоуп забега знает конкретные типы, ему можно.
// EcsWorld и EcsSystems создаёт точка входа забега, а не Configure:
// в Configure логики нет, там только регистрации (урок 02, 3.2).

public sealed class RunEntryPoint : IInitializable, ITickable, IDisposable
{
    // Initialize: создать EcsWorld, собрать EcsSystems в порядке ARCHITECTURE.md §10,
    //             отдать системам сервисы через ecsSystems.Inject(...), затем Init()
    // Tick:       ecsSystems.Run() — ровно один вызов, deltaTime приходит параметром
    // Dispose:    ecsSystems.Destroy(), world.Destroy() — в этом порядке
}

Три границы, которые здесь держатся:

  • Game.Simulation не ссылается на VContainer — это записано в asmdef, и это значит, что системы не могут получить контейнер даже намеренно (ARCHITECTURE.md §15).
  • Сервисы попадают в системы только через EcsSystems.Inject(). VContainer их создал, LeoECS Lite DI разложил по полям — владелец один.
  • Один Tick на весь мир. Порядок систем задан списком, а не порядком объектов в иерархии сцены (ARCHITECTURE.md §1, п. 5 о детерминированном порядке).
Про RegisterInstance и EcsWorld

Соблазн: создать мир в Configure и отдать его через RegisterInstance. Два довода против. Первый: Configure перестаёт быть только регистрацией. Второй, более неприятный: как показано в 1.2, объекты из RegisterInstance контейнер не уничтожает — мир останется жив после Dispose скоупа, и это ровно тот баг, ради предотвращения которого скоупа два.

2.4 Решение по запуску не с той сцены

Отложенный вопрос из урока 02, 2.4 закрыт. Решение — четвёртый вариант, которого в списке блока 1 не было, потому что он не про наш код, а про механизм внутри VContainer.

У VContainer есть ассет настроек VContainerSettings с полем RootLifetimeScope. Если положить туда префаб скоупа, а сам ассет — в Project Settings → Player → Preloaded Assets, библиотека при загрузке первой сцены сама инстанцирует префаб и помещает его в DontDestroyOnLoad.

Проверено на живом проекте, оба направления:

  • сцена, в которой лежит только дочерний скоуп, запускается: корневой префаб поднимается сам, оказывается в DontDestroyOnLoad, дочерний скоуп находит его родителем, зависимости резолвятся;
  • без назначенного префаба та же сцена даёт VContainerException: No such registration of type: ... — осиротевший скоуп строится как собственный корень и падает на первой же чужой зависимости.

Почему именно это, а не редакторный хук из варианта (б) и не автономный сценовый скоуп из варианта (в): путь инициализации остаётся один. Корень всегда рождается одинаково, из одного и того же префаба. Варианты (б) и (в) заводят второй путь, а второй путь — это баг, воспроизводимый через раз.

Чего это решение не делает

Оно поднимает сервисы, но не создаёт RunContext — его собирает сценарий старта забега. Значит запуск прямо с Gameplay даст живые сервисы и громкое падение на отсутствующем RunContext. Так и задумано: лучше исключение с внятным текстом, чем забег, тихо стартовавший с дефолтными параметрами и ведущий себя не так, как настоящий. Отладочный RunContext по умолчанию не заводится — это отдельное решение, если оно вообще понадобится.

2.5 Возврат в меню и порядок разрушения

Забег заканчивается двумя способами, и они не эквивалентны с точки зрения VContainer.

СпособЧто происходитРиск
Явный runScope.Dispose() Контейнер разбирается, затем объект скоупа уничтожается. Момент известен и контролируется. Забыть вызвать — тогда старый скоуп доживёт до загрузки следующей сцены и умрёт «когда-нибудь».
Выгрузка сцены со скоупом OnDestroy вызовет разбор сам. Момент задаёт загрузчик сцен, а не игровой код. Если что-то должно произойти до разбора — например записать итог забега, — оно обязано случиться раньше и не в Dispose.

Практический вывод: итог забега уходит в мету до начала разбора, явным шагом завершения. Класть запись сейва в Dispose точки входа — значит поставить сохранение прогресса игрока в зависимость от порядка уничтожения объектов. Порядок этот детерминирован (1.6), но полагаться на него в вопросе «сохранилась ли валюта игрока» не стоит.

Скелет API

Сигнатуры без тел. Состав сервисов по-прежнему не фиксируется наперёд (урок 02, риск Р-2): в блоке 2 появляется только то, без чего не запускается приложение.

3.1 Проектный скоуп

// Assets/_Project/Bootstrap/ProjectLifetimeScope.cs
// namespace Game.Bootstrap

public sealed class ProjectLifetimeScope : LifetimeScope
{
    [SerializeField] private GameObject _loadingScreenPrefab;

    protected override void Configure(IContainerBuilder builder);
}

Три правила из урока 02, 3.2 остаются в силе и здесь проверяются глазами:

  • внутри только Register* и вызовы установщиков — ни одного if по состоянию игры;
  • ни одного Resolve;
  • регистрируется интерфейс (плюс AsSelf, если нужен и класс), а не двумя отдельными вызовами.
Про поле _loadingScreenPrefab

Имя выбрано не случайно: ровно такое поле осталось в сцене от мёртвых скриптов прошлой версии проекта (урок 02, подводный камень Мёртвая ссылка). Если новый скрипт повесить на тот же объект, Unity подставит старое значение в новое поле с совпадающим именем. Объект был удалён и собирается заново именно поэтому — но значение поля в инспекторе всё равно нужно проверить глазами.

Подводные камни

Две реализации под одним интерфейсом

Симптом: контейнер собирается, ошибок нет, но работает «не тот» объект. Проверено: если под одним интерфейсом зарегистрированы две разные реализации, Resolve отдаёт последнюю зарегистрированную, а IReadOnlyList<T> отдаёт обе. Это не ошибка библиотеки — так устроена поддержка коллекций, — но при случайной двойной регистрации выглядит как мистика. Дважды зарегистрировать один и тот же класс, наоборот, нельзя: построение падает с ArgumentException (1.2).

Transient с ресурсом не освобождается

Симптом: утечка, которую не видно: файловые хендлы, подписки, нативные буферы копятся, пока приложение не начнёт тормозить. Проверено: контейнер не отслеживает Transient-объекты и не вызывает им Dispose(). Правило: IDisposable — это Singleton или Scoped; если объект действительно нужен во множестве экземпляров, его выдаёт фабрика, и уборка — забота владельца.

RegisterInstance и уборка

Симптом: тот же, что выше, но у объекта, который «точно зарегистрирован в контейнере». Причина: RegisterInstance отдаёт готовый объект, и VContainer сознательно не берёт на себя чужое владение. Проверено на IDisposable-экземпляре: Dispose() не вызывается ни разу.

«Синглтон», которых два

Симптом: один код пишет в сервис, другой читает и не видит записанного. Ошибок нет. Причина: тип с Lifetime.Singleton объявлен и в проектном скоупе, и в скоупе забега. Проверено: дочерний скоуп, повторно объявивший тот же тип, создаёт собственный экземпляр. Лечится удалением лишней регистрации, а не попыткой «сделать его совсем глобальным».

Скоуп без родителя молча ждёт

Симптом: скоуп есть в сцене, а его Configure не вызывался, точки входа не стартовали, консоль чистая. Причина: если у скоупа указан тип родителя, а родителя в сцене нет, VContainer не бросает исключение наружу, а кладёт скоуп в очередь ожидания до появления родителя. Отличать от случая 2.4, где родитель не указан вовсе: там скоуп строится как собственный корень и падает громко.

Initialize, которому нужна сцена

Симптом: NullReferenceException или пустая ссылка в Initialize, при том что тот же код в Start работает. Причина: Initialize выполняется внутри Awake скоупа (1.6), когда остальные компоненты сцены ещё не проснулись. Лечится переносом в IStartable, а если нужно после Start у вьюх — в IPostStartable.

Ассет настроек выпал из Preloaded Assets

Симптом: вчера работало, сегодня при запуске с любой сцены нет ни одного сервиса. Причина: ссылка на VContainerSettings в Project Settings → Player → Preloaded Assets — обычное поле настроек проекта, которое теряется при неаккуратном мердже ProjectSettings.asset и не имеет никакой защиты. Это цена решения 2.4, и она уходит в чек-лист.

Две MonoBehaviour в одном файле

Симптом: компонент добавляется кодом и работает, но после сохранения сцены или префаба превращается в Missing; в YAML у него m_Script: {fileID: 0}. Причина: Unity связывает с файлом скрипта только класс, чьё имя совпадает с именем файла. Наткнулись на это при проверке этого урока на живом проекте. Правило простое и общее: один MonoBehaviour — один файл, имя файла равно имени класса.

Сохранение прогресса в Dispose

Симптом: прогресс теряется в части случаев выхода — например при выходе из игры или при выгрузке сцены загрузчиком. Причина: запись сейва оказалась в Dispose и поехала вместе с порядком уничтожения. Итог забега обязан уходить в мету явным шагом до начала разбора (2.5).

Чек-лист приёмки

Первый блок, где есть что проверять компиляцией и запуском. Пункты, отмеченные галочкой, — те, без которых блок не считается закрытым.

Структура кода

  • ProjectLifetimeScope лежит в Assets/_Project/Bootstrap, namespace Game.Bootstrap, файл назван по классу.
  • Первый интерфейс сервиса лежит в Assets/_Project/Core, его реализация — в Assets/_Project/Services. В сигнатурах интерфейса нет ни одного типа из Game.Services, Game.View, Game.UI.
  • В Configure нет ни одного if по состоянию игры и ни одного Resolve.
  • Ни один класс не регистрируется двумя отдельными вызовами Register; несколько лиц — через As/AsSelf в одном вызове.
  • Ни один IDisposable не зарегистрирован как Lifetime.Transient.
  • В проекте по-прежнему ноль static-полей, ноль FindObjectOfType, ноль Resolve вне Game.Bootstrap.

Сцена и настройки

  • Префаб проектного скоупа создан и назначен в поле RootLifetimeScope ассета VContainerSettings.
  • Ассет VContainerSettings присутствует в Project Settings → Player → Preloaded Assets. Проверять после каждого мерджа ProjectSettings.asset.
  • В сцене Bootstrap нет второго объекта со скоупом — иначе корней окажется два.
  • Поле _loadingScreenPrefab в инспекторе содержит то, что вы туда положили, а не то, что осталось от прошлой версии проекта.
  • Консоль чистая, Missing-компонентов в сцене нет.

Поведение — проверяется запуском, а не чтением кода

  • Play из сцены Bootstrap: объект скоупа появляется в разделе DontDestroyOnLoad, а не в самой сцене.
  • Play из сцены Gameplay: сервисы живы (корень поднялся сам), а падение — только на отсутствующем RunContext, с внятным VContainerException. Молчаливого старта быть не должно.
  • Лог в Initialize точки входа появляется в том же кадре, что и Awake скоупа; лог в Start — в следующем.
  • Выход из Play Mode вызывает Dispose у точек входа и у Singleton-сервисов, причём точка входа уничтожается раньше сервиса, от которого зависела.
  • Второй вход в Play Mode ведёт себя ровно так же, как первый. Разошлось — искать static, а не ошибку в скоупе (урок 02, подводный камень).

Понимание

  • Понятно, почему Lifetime.Singleton — это «один на контейнер», а не «один на приложение», и что произойдёт при регистрации одного типа на двух уровнях (1.3).
  • Понятно, почему рестарт забега не требует ни одной строки «очистить мир» (2.2).
  • Понятно, почему итог забега уходит в мету копией данных, а не ссылкой (2.2, 2.5).
