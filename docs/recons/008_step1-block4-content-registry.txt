П-2. РЕЕСТР СОБИРАЛСЯ ПУСТЫМ, И НИКТО НЕ ЖАЛОВАЛСЯ.
     Сошлись три вещи: _contentDatabase сериализован, но нигде не читался;

     против которого написан раздел 1.4 урока 05.
     Починка: реестр строится вручную в Configure и регистрируется инстансом.

П-6. enum SceneName с .ToString() как имя сцены — отклонено, см. §3.

П-7. У LevelConfig и ContentDatabase не было [CreateAssetMenu] — ассеты

3. ПРИНЯТЫЕ РЕШЕНИЯ
--------------------------------------------------------------------------------

Продублированы в журнал PROGRESS.md записью от 2026-08-27.

3.1. ID ЛЕЖИТ ВНУТРИ ЗАПИСИ, А НЕ КЛЮЧОМ В ТАБЛИЦЕ РЕЕСТРА.
     Почему: дроп, сейв и UI постоянно ходят в обратную сторону — «вот
     выпавший предмет, запиши его ID». Если запись не знает своего ID, для
     обратного направления нужен второй словарь, и его рассинхронизация с
     первым — вопрос времени.
     Цена: возможны дубликаты и пустые ID, поэтому валидация обязательна.
     Отклонено отдельно: [field: SerializeField]. Сериализованное поле
     называется <Id>k__BackingField, к нему не применить
     [FormerlySerializedAs], а ID — ровно то значение, которое нельзя
     потерять никогда. Ассетов на момент правки было ноль, момент идеальный.

3.2. РЕЕСТР СТРОИТСЯ ВРУЧНУЮ В Configure И РЕГИСТРИРУЕТСЯ ИНСТАНСОМ.
     Почему: см. П-2. Ручная сборка возвращает падение туда, где ему место —
     в построение проектного скоупа, до первого кадра. Заодно там же
     проверяются обе ссылки на ассеты из префаба корня.

3.3. СЦЕНЫ РАЗВЕДЕНЫ НА ДВА МЕХАНИЗМА: арены — LevelConfig.SceneName через
     реестр, загрузочный поток — ScenesConfig с явными полями.
     Почему: главное меню не единица контента. У него нет ID в сейве, оно не
     выпадает из дропа и не приезжает в DLC. Складывать его в реестр — соврать
     про то, чем оно является.
     ОТКЛОНЕНО ЖЁСТКО: enum со списком сцен и .ToString() как имя сцены.
     Три причины. (а) Это возвращает список сцен в код, то есть переносит
     техдолг §8, а не снимает: новый уровень = правка Game.Configs и
     пересборка. (б) .ToString() привязывает имя сцены к имени элемента enum,
     а переименование элемента — это рефакторинг, который IDE делает молча:
     имя сцены меняется, загрузка ломается в рантайме. (в) enum сериализуется
     как int, поэтому перестановка значений переводит все конфиги на чужие
     сцены — та же ловушка, о которой урок писал применительно к ID.
     Опечатки в имени сцены ловятся не типом, а валидацией.

3.4. Get КИДАЕТ ОДНО ИСКЛЮЧЕНИЕ С ДВУМЯ ФОРМАМИ СООБЩЕНИЯ.
     Промах по ID и промах по типу — разные ошибки, и текст обязан это
     говорить, иначе поиск начинается с несуществующей опечатки. Отдельный
     третий класс исключения заводить не стали: TryGet возвращает false в обоих
     случаях, поэтому пара Get/TryGet остаётся симметричной.

3.5. All<T>() РАБОТАЕТ ПО ТОЧНОМУ ТИПУ, БЕЗ ПОТОМКОВ.
     Записано в XML-док метода, чтобы через полгода не выяснять
     экспериментом. Проверено: All<ContentConfig>() возвращает 0 при живом
     LevelConfig в базе.
     Техническая деталь, ради которой это стоило внимания: List<IContentEntry>
     НЕЛЬЗЯ привести к IReadOnlyList<T>. Ковариантность IReadOnlyList<out T>
     работает только вверх, и компилятор здесь прав. Взят ленивый кэш:
     Dictionary<Type, object>, список нужного типа строится при первом вызове
     All<T>() и переиспользуется. Проверено: два вызова подряд возвращают
     один и тот же экземпляр.

3.6. ВАЛИДАЦИЯ СОБИРАЕТ ВСЕ ОШИБКИ И КИДАЕТ ОДНО ИСКЛЮЧЕНИЕ СПИСКОМ.
     Падать на первой — значит чинить десять пустых ID за десять
     перезапусков. В тексте каждой ошибки есть номер ячейки; имя ассета
     берётся из entry.ToString(), который у ScriptableObject даёт
     «ИмяАссета (Тип)» — то есть Game.Core называет ассет, не зная про Unity.

6. ОСТАЛОСЬ НЕЗАКРЫТЫМ И ВЫЛЕЗШИЕ РИСКИ
--------------------------------------------------------------------------------

Р-1. ШАГ СИМУЛЯЦИИ — РЕШЕНИЕ НЕ ПРИНЯТО. Сейчас Time.deltaTime в ITickable,
     то есть забег по сиду не воспроизводится: тот же сид при другом
     фреймрейте даст другой забег. Seed при этом уже лежит в RunContext.
     Шов на месте — фиксированный шаг ставится вокруг _clock.Advance в
     RunEntryPoint.Tick и больше нигде.
     Рекомендация прежняя: детерминизм в MVP не нужен и это надо записать
     явно, а фиксированный шаг всё равно взять — он убирает класс багов
     «на слабой машине враги проходят сквозь».
     Пункт заведён в «Ближайшие шаги» PROGRESS.md.

Р-2. ОШИБКА ВНУТРИ StartAsync НЕ ДОХОДИТ ДО ВЫЗЫВАЮЩЕГО САМА.
     Обнаружено при проверке: StartAsync — async UniTask, поэтому
     ContentNotFoundException при неверном LevelId не бросается на месте
     вызова, а уезжает в возвращённый UniTask. Если его не дождались, ошибка
     всплывает только логом через обработчик необработанных исключений
     UniTask — то есть громкое падение реестра становится тихой строчкой в
     консоли. Когда появится UI, вызов обязан быть await с обработкой.

Р-3. ИМЯ СЦЕНЫ ОСТАЛОСЬ НЕПРОВЕРЯЕМОЙ СТРОКОЙ. Заведено в CLAUDE.md §8 как
     суженный наследник закрытого пункта. Условие возврата: редакторный
     валидатор против списка Build Settings либо типизированная ссылка на
     сцену. Валидатор обязан быть под #if UNITY_EDITOR: EditorBuildSettings —
     редакторный тип, см. П-1.

Р-4. ВЫЗЫВАТЬ IRunLauncher ПО-ПРЕЖНЕМУ НЕКОМУ. UI нет, забег стартует только
     руками из Play Mode. Это нормально до шага 9, но каждая последующая
     приёмка будет требовать ручного прогона.

Р-5. РАСХОЖДЕНИЕ УРОКА 04 С КОДОМ. Разделы 2.4 и 3.6 урока показывают
     SimulationClock с публичными полями; в коде теперь Advance и private
     set. Фактической ошибкой урока это не является (правило «один писатель»
     то же), поэтому под политику HANDBOOK_ERRATA формально не подпадает.
     Решение за разработчиком: оставить, поправить два блока кода в уроке
     или добавить строку в errata. Не трогалось.

Р-6. В ГЛОССАРИИ НЕТ СТАТЕЙ по терминам урока 05 — «стабильный ID», «реестр
     контента», «fail fast». Уроки 01–04 свои термины туда добавляли.

Р-7. Из §0 остаются неразобранными Р-Б (MovementComponents вне доков) и
     Р-Г (артефакты Addressables и дубль «Configs .asset»).

Р-8. ContentDatabase.Entries возвращает сам массив: вызывающий может привести
